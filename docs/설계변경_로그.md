<a id="log-01"></a>
## LOG-01. 운동 기록 데이터 구조

### 기존 버전

계획서 4.4의 주요 엔티티 목록에 다음과 같이 기재되어 있었다.

| 엔티티 | 설명 |
|---|---|
| workout_logs | 운동 기록(사용자·종목·중량·세트·횟수·일자) |

즉 운동 기록을 단일 테이블로 두고, 한 행이 하나의 기록을 나타내는 구조였다.

### 기존 버전의 문제점

기록을 세션 단위로 묶는 개념이 없어, 다음 세 가지를 산출할 수 없었다.

1. **총 운동 시간** — 친구 그룹 활동 공유(기능명세 2.6)는 "멤버별 주간 운동 횟수와 총 운동 시간"을 표시하기로 되어 있으나, 개별 기록 행만으로는 "한 번의 운동"이 어디서 시작해 어디서 끝났는지 알 수 없다.
2. **주간 운동 횟수** — 같은 날 여러 종목을 기록하면 행이 여러 개 생기므로, 행 수로는 운동 횟수를 셀 수 없다. 날짜 중복 제거로 근사할 수는 있으나 개념이 불명확하다.
3. **루틴 실제 수행률** — 계획서 7장의 실사용자 검증 항목인 "추천 루틴 실제 수행률(사용 로그 기반 자동 측정)"은 "이번 운동이 어느 추천 루틴에서 시작되었는가"의 연결을 요구하는데, 이를 걸 대상이 없었다.

또한 세트를 한 행에 묶어 저장하는지 세트마다 나누어 저장하는지가 명확하지 않아, 세트별 강도(%) 표시(분석 설계서 1.3)의 구현 가능 여부가 불확실했다.

### 수정 버전

기록을 **세션 — 세트** 2계층으로 분해하였다.

| 엔티티 | 설명 |
|---|---|
| workout_sessions | 하루 한 번의 운동. 수행 일자, 루틴 연결, 세션 상태, 운동 시간 |
| workout_sets | 세트 1개 = 1행. 종목, 세트 순번, 중량, 횟수, 워밍업 여부, 저장 시각 |

컬럼 정의는 「운동기록_방식_설계서.md」 2장에 정리하였다.

### 수정한 이유와 방식

**이유**: 계획서 단계에서는 "운동 기록을 저장한다"는 수준으로만 기술했으나, 지도교수 피드백에 따라 기록 방식을 구체화하는 과정에서 **분석·그룹·검증 기능이 실제로 요구하는 데이터를 역산**한 결과 단일 테이블로는 충족되지 않음이 드러났다.

**방식**: 각 기능이 필요로 하는 데이터를 표로 정리한 뒤(설계서 1장), 그 요건을 모두 만족하는 최소 구조를 도출하였다. 세션 개념은 운동 시간·주간 횟수·수행률 세 가지를 한꺼번에 해결하므로 추가 비용 대비 효용이 크다고 판단하였다.

**주의**: 데이터 구조는 기록이 쌓인 뒤에는 되돌리기 어렵다. 9월 구현 후 10월에 문제를 발견하면 이미 쌓인 데이터를 복구할 수 없으므로, 구현 착수 전 설계 단계에서 확정하였다.

**계획서 반영 여부**: 반영하지 않는다. 계획서는 제출·승인이 완료되어 계획 시점의 기록으로 두고, 변경 사항은 본 로그와 최종 보고서에 담는다.

## LOG-02. 세트 집계 시 워밍업 세트 제외

### 기존 버전

「운동 분석 로직 설계서」 1.2에서 세트 카운팅 기준을 다음과 같이 정하였다.

> 한 운동이 여러 근육을 사용하더라도, 해당 운동의 주동근에만 세트를 집계한다.

즉 **어느 근육에 세트를 배정할 것인가**만 정하고, **어떤 세트를 셀 것인가**는 정하지 않았다. 사실상 기록된 모든 세트를 세는 것과 같았다.

### 기존 버전의 문제점

1. **기준값과 계산 단위의 불일치.** ACSM의 "부위별 주 4/10~20세트" 기준은 실패 근처까지 수행하는 본세트를 센 값이다. 워밍업을 함께 집계하면 앱의 계산 단위가 기준값의 단위와 달라지므로, "4세트 미만이면 부족"이라는 판정의 근거가 성립하지 않는다. 설계서 0장이 내건 "기준값은 문헌에서, 계산 방법은 직접 설계한다"는 원칙에서, 계산 방법이 기준값과 어긋나는 경우이다.
2. **오판의 방향이 나쁘다.** 워밍업을 포함하면 볼륨이 부풀려져 실제로 부족한 부위가 "권장 이하"나 "최적"으로 올라온다. 즉 **약점을 놓치는 방향**으로 틀리는데, 이는 "사용자가 인지하지 못하는 약점을 짚어 준다"는 이 앱의 존재 이유를 직접 훼손한다.
3. **균형 판정도 왜곡된다.** 워밍업은 부위에 고르게 분포하지 않고 스쿼트·벤치프레스 같은 고중량 복합운동에 집중되므로, 밀기·하체 볼륨이 상대적으로 과대 계상되어 2배 임계 판정에 영향을 준다.

### 수정 버전

- `workout_sets`에 `is_warmup` 불리언 컬럼을 두고, 기본값을 false로 한다.
- 부위별 볼륨 집계 시 `is_warmup = false`인 세트만 센다.
- 기록 화면에 워밍업 토글을 제공하되, "본세트만 기록해도 무방하다"고 안내한다.

### 수정한 이유와 방식

**이유**: 위 세 가지 문제 중 특히 2번이 결정적이었다. 판정이 틀리더라도 "과하다고 잘못 알리는" 방향이면 사용자가 확인 후 넘어갈 수 있지만, "부족한데 충분하다고 알리는" 방향은 사용자가 문제를 인지할 기회 자체를 없앤다.

**방식**: 세 가지 선택지를 비교하였다.

| 선택지 | 판단 |
|---|---|
| 구분 없이 전부 카운트 | 구현이 가장 단순하나 위 문제를 그대로 안는다 |
| 본운동만 기록하도록 안내 | 안내에만 의존하므로 실효성이 없고, 워밍업을 기록하려는 사용자를 막게 된다 |
| **토글 제공 + 집계 제외 (채택)** | 불리언 컬럼 하나와 집계 조건 한 줄. 비용 대비 정합성 확보 효과가 크다 |

**한계 인지**: 사용자가 워밍업을 표시하지 않으면 여전히 과대 집계된다. 자동 판별(그날 최고 중량의 일정 비율 미만인 선행 세트를 워밍업으로 간주하는 방식)도 검토했으나, 임계 비율의 근거를 대기 어렵고 오탐 시 사용자가 이유를 이해할 수 없어 채택하지 않았다. 설계서 0장의 "과한 정밀도를 피한다"는 원칙에 따른 판단이며, 확장 아이디어로 기록해 두었다.

## LOG-03. 운동 시간 기록 방식

### 기존 버전

기능명세서 2.6에 그룹 활동 공유 항목으로 "주 운동 횟수, 총 운동 시간"을 표시한다고만 기재되어 있었다. 이 시간을 **어떻게 얻을 것인지**는 정해지지 않았고, 「운동 분석 로직 설계서」 7.2에서 검토 항목으로만 남아 있었다.

### 기존 버전의 문제점

방식을 정하지 않으면 구현 단계에서 임기응변으로 결정하게 되는데, 어느 방식을 택하든 데이터 구조에 영향을 준다.

- 명시적 시작/종료 버튼 방식 → 세션 테이블에 시작·종료 시각이 필요
- 세트 시각 기반 자동 산출 → 세트마다 저장 시각이 필요
- 사용자 직접 입력 → 세션에 입력값 컬럼이 필요

즉 이 결정이 늦어지면 데이터 구조를 확정할 수 없다. 또한 이 값은 그룹 멤버에게 공개되므로 이상치 방어가 필요한데, 그 규칙도 함께 정해야 했다.

### 수정 버전

**세트 저장 시각 기반 자동 산출**로 확정하였다.

```
duration_sec = Σ(연속한 두 세트의 간격, 단 15분 초과 시 15분으로 캡)
             + 90초 (마지막 세트 수행 시간 보정)
상한: 세션당 4시간
```

- 사후 입력(BACKFILL) 세션은 저장 시각이 실제 운동 시각과 무관하므로 시간을 산출하지 않고, 그룹의 총 시간 집계에서 제외한다. 단 주간 운동 **횟수** 집계에는 포함한다.
- `duration_override_sec` 컬럼을 미리 확보해 두고, 수동 보정 UI는 필요 시 추가한다.

### 수정한 이유와 방식

**이유**: 세 가지 방식을 비교한 결과이다.

| 방식 | 문제 |
|---|---|
| 명시적 시작/종료 버튼 | 운동 중에 종료를 누르는 것을 잊기 쉽다. 잊으면 데이터가 유실되거나 비정상적으로 길어진다 |
| 사용자가 총 시간 직접 입력 | 추가 입력 부담이 생기고 값이 부정확하다 |
| **세트 시각 자동 산출 (채택)** | 추가 조작이 전혀 없다. 세트 기록이라는 이미 하는 행위에서 부수적으로 얻어진다 |

이 값은 그룹 표시용이므로 분 단위 정밀도면 충분하다는 점도 고려하였다. 정밀도 요구가 낮은 값을 위해 사용자에게 조작을 요구하는 것은 비용 대비 효용이 낮다.

**방식**: 자동 산출의 약점은 이상치이므로 보정 규칙을 함께 설계하였다. 앱을 닫고 나갔다가 몇 시간 뒤 마지막 세트를 입력하는 경우가 실제로 흔하므로, 세트 간격에 상한(15분)을 두어 이탈 구간이 운동 시간에 포함되지 않게 하였다. 15분은 일반적인 세트 간 휴식(1~5분)보다 충분히 크되 이탈로 볼 만한 수준으로 설정하였다.

**보류 항목**: `duration_override_sec` 컬럼은 만들되 보정 UI는 만들지 않는다. 실사용자 배포 후 시간이 부정확하다는 피드백이 나올 가능성에 대비해, 스키마 변경 없이 화면만 추가할 수 있도록 자리를 남겨 둔 것이다.

## LOG-04. 운동 종목 데이터에 측정 유형 추가

### 기존 버전

계획서 4.4와 「운동 분석 로직 설계서」 6장에서, 운동 종목 데이터(exercises)는 free-exercise-db를 기반으로 **운동명(한글) + 주동근 + 밀기/당기기 구분**을 확보하는 것으로 계획되어 있었다.

### 기존 버전의 문제점

기록 화면을 설계하면서, 종목마다 입력해야 할 항목이 다르다는 점이 드러났다.

- 푸시업·크런치 같은 맨몸운동에는 중량 입력이 의미가 없다
- 플랭크 같은 시간 기반 종목에는 횟수 입력이 의미가 없다
- 중량 딥스·중량 턱걸이는 추가 중량만 기록되므로 추정 1RM 산출에 넣으면 값이 왜곡된다

이 구분이 데이터에 없으면 모든 종목에 동일한 입력 폼을 제공하게 되어, 입력 부담이 늘고 의미 없는 값(중량 0 등)이 저장되어 분석 데이터가 오염된다.

### 수정 버전

`exercises`에 `measure_type` 필드를 추가한다.

| measure_type | 입력 항목 | 예시 | 1RM 추정 |
|---|---|---|---|
| WEIGHT_REPS | 중량 + 횟수 | 벤치프레스, 스쿼트 | 대상 |
| BODYWEIGHT_REPS | 횟수 | 푸시업, 크런치 | 제외 |
| WEIGHTED_BODYWEIGHT | 추가 중량 + 횟수 | 중량 딥스 | 제외 |
| TIME | 시간(초) | 플랭크 | 제외 |

### 수정한 이유와 방식

**이유**: 이 필드가 없으면 기록 화면을 종목별로 분기할 수 없고, 추정 1RM 산출 대상을 걸러낼 수도 없다.

**방식**: free-exercise-db에는 이 정보가 없으므로 **8월 2주 운동 종목 DB 정제 작업에 포함**한다. 이미 한글 명칭과 부위 매핑을 수작업으로 정제할 예정이므로, 같은 작업에 필드 하나를 더 채우는 형태로 흡수한다. 별도 작업으로 분리하면 종목 목록을 두 번 훑게 되어 비효율적이다.

**일정 영향**: 계획서 8장 (3)에서 종목 데이터 정제 시간을 위험 요소로 인식하고 "자주 쓰이는 종목을 우선 정제"하는 대응을 두었다. 이 대응은 그대로 유효하며, 우선 정제 대상 종목에 `measure_type`을 함께 채우면 된다.

<a id="log-05"></a>
## LOG-05. 루틴 계획 세트의 저장 시점

### 기존 버전

추천 루틴을 받아 운동을 수행하는 흐름에서, 루틴의 계획 세트가 언제 기록으로 저장되는지가 정해져 있지 않았다. 기능명세서 2.1은 루틴 생성까지만 다루고, 그 루틴을 수행하며 기록하는 과정은 별도로 기술되지 않았다.

### 기존 버전의 문제점

루틴 진입 시점에 계획된 세트를 모두 저장하는 방식(구현하기 쉬운 방식)을 택하면 심각한 문제가 발생한다.

> 예: 등 3세트를 계획한 루틴에서 1세트만 수행하고 이탈한 경우, 등 볼륨이 3세트로 집계된다.

즉 **수행하지 않은 운동이 수행한 것으로 기록**되며, 이는 LOG-02와 같은 방향의 오류(약점을 놓치는 방향)이다. 게다가 추천 루틴을 따를수록 오차가 커지므로, 앱을 성실히 사용하는 사용자일수록 판정이 부정확해지는 역전이 발생한다.

또한 이 방식에서는 실제 수행률을 측정할 수 없다. 계획과 기록이 항상 일치하기 때문이다.

### 수정 버전

- 루틴에서 진입한 경우 계획 세트가 화면에 행으로 표시되지만, 이는 **화면 상태(계획)일 뿐 저장된 기록이 아니다.**
- 사용자가 **완료 체크를 하는 순간에만** `workout_sets` 행을 INSERT 한다.
- 따라서 `is_completed` 같은 별도 컬럼이 필요 없다. 행의 존재 자체가 "수행함"을 의미한다.

이로부터 수행률이 자연스럽게 산출된다.

```
수행률 = 세션에 실제 저장된 세트 수 ÷ 연결된 루틴이 계획한 세트 수
```

### 수정한 이유와 방식

**이유**: 기록 데이터의 무결성 문제이다. 분석 로직이 아무리 정확해도 입력 데이터가 사실과 다르면 결과가 무의미하다.

**방식**: "계획"과 "기록"을 저장 위치로 분리하였다. 계획은 `routines` / `routine_items`에, 기록은 `workout_sessions` / `workout_sets`에 있으며, 둘은 세션의 `routine_id`로만 연결된다. 이 분리 덕분에 계획서 7장의 실사용자 검증 항목인 "추천 루틴 실제 수행률(사용 로그 기반 자동 측정)"이 **별도 로깅 없이** 두 테이블의 세트 수 비교만으로 산출된다.

**부수 결정**: 루틴 후보정(기능명세 2.4)으로 운동을 교체한 경우, 수행률의 분모는 후보정 **이후**의 계획을 사용한다. 사용자에게 실제로 제시된 계획이 후보정된 루틴이기 때문이다.

<a id="log-06"></a>
## LOG-06. 기록 수정·누락 처리 방침

### 기존 버전

유스케이스 정의서 UC-02-02에 "운동 기록 수정 / 삭제"가 있었으나, 흐름과 처리 방침은 정의되지 않았다. 운동 중 앱을 벗어나는 경우, 과거 기록을 나중에 입력하는 경우, 기록을 삭제했을 때 이미 지급된 뱃지를 어떻게 할지는 정해진 바가 없었다.

### 기존 버전의 문제점

1. **미완료 세션**: 운동 중 앱을 닫는 것은 예외가 아니라 일상이다. 처리 방침이 없으면 기록이 유실되거나, 며칠 뒤 열었을 때 이전 세션에 세트가 추가되는 등의 오동작이 생긴다.
2. **기록 누락**: 운동은 했으나 기록하지 못한 경우를 보정할 수단이 없으면, 분석이 이를 "볼륨 부족"으로 판정한다. 판정 정확도가 사용자의 기록 성실성에 전적으로 좌우된다.
3. **수정 후 재집계**: 기록을 수정했을 때 이미 산출된 분석 결과를 어떻게 갱신할지 정해져 있지 않았다.
4. **뱃지와 기록 삭제**: 3대 500 뱃지를 받은 뒤 해당 기록을 삭제하면 뱃지를 회수할지 여부가 불분명했다. 구현 중에 마주치면 애매해지는 지점이다.

### 수정 버전

| 상황 | 처리 |
|---|---|
| 미완료 세션 | 세션에 DRAFT / DONE 상태를 둔다. 재진입 시 "이어서 기록 / 종료" 선택. 자정 경과 시 마지막 세트 시각 기준으로 자동 완료. **분석은 DONE 세션만 집계** |
| 과거 기록 입력 | 날짜를 지정한 사후 입력(BACKFILL)을 허용한다. 볼륨 집계에는 포함하고, 운동 시간 집계에서만 제외 |
| 수정·삭제 | 허용한다. 분석을 **온디맨드 집계**로 구현하여 수정이 자동 반영되게 한다 |
| 뱃지 | 이미 지급된 뱃지는 **회수하지 않는다** |
| 기록 희박 | 최근 4주 완료 세션이 임계(예: 6회) 미만이면 "판정 신뢰도 낮음"을 함께 표시 |

### 수정한 이유와 방식

**미완료 세션 — DONE만 집계하는 이유**: 진행 중인 세션이 판정에 섞이면, 운동 도중 루틴 추천을 요청할 때마다 결과가 달라진다. 오늘의 루틴은 "그때까지 쌓인 기록"을 근거로 하므로, 완료된 것만 근거로 삼아야 결과가 안정적이다.

**사후 입력을 허용하는 이유**: 직관적으로는 "정확한 실시간 기록만 받는 것"이 데이터 품질에 좋아 보이지만, 실제로는 반대다. 누락된 운동은 분석에서 부족으로 오판되므로, **누락을 방치하는 것이 부정확한 사후 입력보다 나쁘다.** 정확도보다 누락 방지를 우선한 선택이며, 대신 시간 데이터만 신뢰도가 낮으므로 그 항목에서만 제외하였다.

**온디맨드 집계를 택한 이유**: 집계 결과를 미리 저장해 두면 기록 수정 시 재계산 로직이 필요하고, 갱신 누락으로 화면마다 값이 다른 문제가 생긴다. 개인당 최근 4주 기록이 수백~수천 행 규모여서 매번 집계해도 성능 문제가 없으므로, 단순한 쪽을 택하였다. 통계 화면이 느려지는 경우에 한해 일별 집계 테이블 도입을 검토한다(현 시점 보류).

**뱃지를 회수하지 않는 이유**: 회수하려면 "어느 시점의 어떤 기록이 그 뱃지의 근거였는가"를 추적해야 하므로 구현 비용이 크다. 뱃지는 달성 순간의 기록이라는 성격이 강하고 프로필 전시용이므로, 엄밀한 정합성보다 단순함을 택하였다.

<a id="log-07"></a>
## LOG-07. 추정 1RM 산출 대상 세트 제한

### 기존 버전

「운동 분석 로직 설계서」 1.3은 추정 1RM 방식을 채택하며 다음과 같이 한계를 인지하였다.

> 추정 1RM은 공식 기반 추정치이며, 특히 고반복 구간에서 오차가 커진다. 따라서 정확한 1RM이 아니라 강도 경향 파악 용도로 사용한다.

그러나 한계를 인지했을 뿐, 그에 대한 처리는 정해두지 않았다. 모든 세트를 추정 계산에 넣는 것과 다름없었다.

### 기존 버전의 문제점

오차가 크다는 것을 알면서 오차가 큰 데이터를 그대로 사용하는 상태였다. 특히 20회 이상의 고반복 세트는 추정값이 실제와 크게 벌어지는데, 이 값이 그대로 추정 1RM 추이 그래프에 반영되면 사용자에게 잘못된 성장 추세를 보여주게 된다. 세트별 강도(%)는 추정 1RM을 분모로 쓰므로 그 값까지 함께 왜곡된다.

또한 하루에 같은 종목을 여러 세트 수행했을 때 어느 값을 그날의 대표값으로 삼을지도 정해져 있지 않았다.

### 수정 버전

- 중량·횟수를 기록하는 종목(`measure_type = WEIGHT_REPS`)의 세트만 대상으로 한다.
- **`반복 횟수 ≤ 12`인 세트만** 추정 계산에 사용한다.
- 하루에 같은 종목의 세트가 여럿이면 각 세트 추정값 중 **최댓값**을 그날의 추정 1RM으로 채택한다.

### 수정한 이유와 방식

**이유**: 인지한 한계를 실제 처리로 옮긴 것이다. 오차가 큰 구간을 사후에 보정하기보다, 애초에 계산에 넣지 않는 편이 단순하고 방어하기 쉽다.

**방식**: 12회를 경계로 삼은 것은 Epley 등 추정 공식이 대체로 10~12회 이내 구간에서 실측과 근접하다고 알려져 있기 때문이다. 다만 이 값 자체는 정밀한 근거를 갖는 수치가 아니므로, 설정값으로 두어 조정 가능하게 한다.

**부수 효과**: 워밍업 세트는 중량이 낮아 추정값이 최댓값이 되지 않으므로, 최댓값 채택 규칙에 의해 자동으로 배제된다. LOG-02의 워밍업 처리와 별도의 조건을 걸 필요가 없다.

<a id="log-08"></a>
## LOG-08. 운동 종목 데이터에 기구 정보 추가

### 기존 버전

운동 종목 데이터(`exercises`)에 확보하기로 한 항목은 다음과 같았다.

- 운동명(한글) + 주동근 + 밀기/당기기 구분 (계획서 4.4, 분석 로직 설계서 8장)
- 측정 유형 `measure_type` (LOG-04에서 추가)

한편 기능명세 2.4의 루틴 후보정은 운동 교체 시 **"같은 부위의 다른 운동 후보를 제시"** 한다고만 기술되어 있었다.

### 기존 버전의 문제점

후보 선정 기준이 `body_part` 하나뿐이면, 사용자가 운동을 교체하려는 **실제 이유를 해소하지 못하는 후보**가 제시된다.

기능명세 1장과 2.4는 "부상 부위·보유 기구 등 개별 제약은 입력받지 않고 후보정으로 조정한다"는 방침을 명시하고 있다. 그런데 교체를 원하는 상황은 대부분 다음과 같다.

- 해당 기구가 사용 중이거나 그 시설에 없다
- 부상 때문에 특정 동작을 피해야 한다

바벨 스쿼트를 교체하려는 사용자에게 같은 하체 운동이라며 **다시 바벨 종목**을 제시하면, 교체 기능이 의도한 역할을 하지 못한다. 즉 후보정이 제약 미입력 방침을 보완하는 장치로 설계되었음에도, 정작 후보를 고르는 데 필요한 정보가 데이터에 없었다.

### 수정 버전

`exercises`에 `equipment` 필드를 추가한다.

| equipment | 예시 종목 |
|---|---|
| BARBELL | 벤치프레스, 바벨 스쿼트 |
| DUMBBELL | 덤벨 컬, 덤벨 플라이 |
| MACHINE | 랫풀다운, 레그프레스 |
| CABLE | 케이블 크로스오버 |
| BODYWEIGHT | 푸시업, 크런치 |
| PULLUP_BAR | 턱걸이 |

루틴 후보정의 대체 운동 후보는 **같은 `body_part`이면서 `equipment`가 다른 종목을 우선 제시**한다.

### 수정한 이유와 방식

**이유**: 후보정 기능의 실효성 문제이다. 후보정은 이 앱이 사용자 제약을 입력받지 않기로 한 결정(기능명세 1장)을 지탱하는 장치이므로, 이것이 제 역할을 못 하면 제약 미입력 방침 자체가 약해진다.

**방식**: 세 가지 선택지를 비교하였다.

| 선택지 | 판단 |
|---|---|
| 사용자에게 보유 기구를 입력받는다 | 진입장벽을 낮춘다는 기능명세 1장의 방침과 정면으로 충돌한다 |
| 부위만으로 후보를 제시한다 | 구현은 단순하나 교체 사유를 해소하지 못한다 |
| **종목에 기구 정보를 부여한다 (채택)** | 필드 하나로 후보 선정의 실효성을 확보한다. 사용자 입력은 늘지 않는다 |

**시점을 8월 2주로 잡은 이유**: `equipment`가 실제로 쓰이는 것은 10월 루틴 추천 구현 시점이다. 그럼에도 지금 확보하는 것은 비용의 비대칭 때문이다.

| | 지금 추가 | 10월에 추가 |
|---|---|---|
| 스키마 | 컬럼 1개 | 마이그레이션 (경미) |
| **데이터** | 정제 시 필드 1개 추가 매핑 | **800여 종목 재검토** |

free-exercise-db 원본에 `equipment` 필드가 이미 존재하므로, 정제 과정에서 한글 매핑만 수행하면 된다. `measure_type`처럼 값을 새로 만들어야 하는 항목이 아니어서 추가 부담이 더 작다. LOG-04에서 `measure_type`을 같은 논리로 정제 작업에 흡수시킨 것과 동일한 판단이다.

**미확정 사항**: 후보정의 트리거 방식(사용자가 교체 버튼을 누르는가, 시스템이 자동 판단하는가)과 대체 후보의 정렬 기준은 10월 루틴 추천 설계에서 확정한다. 본 로그는 그때 필요한 데이터를 미리 확보하는 결정만을 다룬다.

**한계 인지**: 기구 분류가 다르다고 해서 반드시 대체 가능한 운동인 것은 아니다. 예컨대 부상으로 특정 동작 자체를 피해야 하는 경우에는 기구를 바꿔도 해결되지 않는다. 후보를 제시할 뿐 최종 선택은 사용자가 한다는 2.4의 성격("확정된 정답이 아니라 근거 있는 초안")은 그대로 유지된다.

<a id="log-09"></a>
## LOG-09. 판정 부위 단위 정의

### 기존 버전

「운동 분석 로직 설계서」 2장은 부족 판정의 임계값(주 4/10~20세트), 집계 기간(최근 4주 평균), 집계 조건(완료 세션의 본세트), 카운팅 원칙(주동근 기준)을 모두 확정하였다.

그러나 **그 "부위"가 무엇이며 몇 개인지는 어느 문서에도 정의되어 있지 않았다.** 계획서 4.3 역시 "부위별 집계한 뒤"라고만 기술하고 목록을 제시하지 않았다.

### 기존 버전의 문제점

**1. 저장용 분류를 판정 단위로 오인한 채 작업이 진행되었다.**

계획서 4.4의 `exercises` 테이블 설명에 등장하는 `body_part` 6종(CHEST / BACK / LEGS / SHOULDERS / ARMS / CORE)을 판정 단위로 간주하고, 운동 종목 정제(2026-08-08)의 선정 기준축을 "부위 × 동작패턴 × 기구"로 잡았다. 이는 저장·검색용 분류를 판정 단위로 착각한 것이다.

**2. 설계서 4.3의 균형 판정이 구현 불가능하다.**

4.3은 균형 판정의 계산 재료를 다음과 같이 명시하고 있다.

```
밀기   = 가슴 + 전면어깨 + 삼두
당기기 = 등 + 후면어깨 + 이두
하체   = 대퇴사두 + 햄스트링 + 둔근 + 종아리
```

즉 설계서가 요구하는 입자는 처음부터 `body_part` 6종보다 잘았다. `body_part = ARMS`로는 삼두를 밀기에, 이두를 당기기에 배분할 수 없고, `SHOULDERS`로는 전면·후면을 구분할 수 없다. 확정 기능인 균형 판정이 동작하지 않는다.

**3. 부족 판정도 왜곡된다.**

이두만 주 12세트, 삼두 0세트인 사용자에게 "팔 12세트, 최적" 판정이 내려진다. 삼두를 전혀 하지 않는데 충분하다고 알리는 것이므로, **약점을 놓치는 방향**의 오판이다. LOG-02(워밍업 제외)에서 결정적 근거로 삼았던 것과 동일한 성격의 문제다.

### 수정 버전

판정 단위를 `body_part`가 아니라 **`primary_muscle` 기반 근육군 9종**으로 정의한다. `body_part` 6종은 저장·검색·차트용으로 그대로 유지한다.

| 판정 부위 | 구성 `primary_muscle` | 종목 수 |
|---|---|---|
| CHEST | chest | 18 |
| BACK | lats, middle back, traps, lower back | 17 |
| DELT_FRONT | shoulders (오버헤드 프레스·전면 레이즈·측면 레이즈) | 10 |
| DELT_REAR | shoulders (후면 델트) | 3 |
| TRICEPS | triceps | 14 |
| BICEPS | biceps | 7 |
| QUADS | quadriceps, abductors, adductors | 11 |
| POSTERIOR | hamstrings, glutes | 7 |
| CORE | abdominals | 16 |
| **판정 대상 계** | | **103** |

**판정 제외 (표시만)**: calves 3, forearms 3

균형 판정에서의 취급:
```
하체   = 대퇴사두 + 햄스트링 + 둔근 + 종아리   ← 종아리 포함 (4.3 계산식 유지)
당기기 = 등 + 후면어깨 + 이두                  ← 전완 미포함 (4.3에 없음)
```

### 수정한 이유와 방식

**이유**: 위 세 문제 중 2번이 결정적이었다. 균형 판정은 설계서 5장에 "확정"으로 기재된 핵심 기능이며, 계산식이 이미 근육 단위를 전제하고 있었다. 따라서 이는 새로운 설계 결정이 아니라 **설계서에 암묵적으로 존재하던 단위를 명시화하는 작업**이다.

**방식**: 세 가지 선택지를 비교하였다.

| 선택지 | 판단 |
|---|---|
| `body_part` 6종 유지, 근육은 부가 설명으로만 사용 | 4.3의 균형 판정을 구현할 수 없다. 확정 기능을 포기하게 된다 |
| `body_part` enum을 근육 단위로 확대 | 계획서 4.4 스키마 변경 필요. 검색·차트 UI도 함께 재설계해야 한다 |
| **판정 단위와 저장 단위를 분리 (채택)** | 스키마 무변경. `primary_muscle`에 필요한 값이 이미 존재한다 |

CSV 7개 컬럼 중 어느 것도 재작성이 필요하지 않았다. 판정 로직이 읽는 컬럼만 달라진다.

**종아리·전완을 부족 판정에서 제외한 근거**

부족 판정은 "하지 않으면 문제"라는 진술이므로, ACSM 권고 단위에 해당하고 미수행이 실제 문제인 부위에만 적용해야 한다. 두 부위는 어느 조건도 충족하지 않는다.

- ACSM 권고는 큰 근육군 단위로 제시되며 종아리·전완을 별도 단위로 다루지 않는다.
- 다수의 사용자가 별도 훈련하지 않으며, 하지 않는다고 약점으로 부르기 어렵다.
- 포함할 경우 대부분의 사용자가 매주 "전완 부족" 경고를 받게 되어 경고의 신뢰도가 떨어진다.

설계서 0장 "근거로 방어할 수 없는 정밀도를 피한다"에 따른 판단이다. 오판 방향도 안전하다 — 약점을 놓치는 쪽이 아니라 언급하지 않는 쪽으로 틀린다.

**어깨 전면·후면 분리 방식**

free-exercise-db는 `primaryMuscles`를 `shoulders` 하나로만 제공하고 세부를 나누지 않는다. 따라서 종목 정제 시 부여한 동작 패턴을 기준으로 배분하였다.

| 패턴 | 배분 | 근거 |
|---|---|---|
| 오버헤드 프레스 | 전면 | `force = push` |
| 전면 레이즈 | 전면 | 명시적 |
| 측면 레이즈 | 전면 | 아래 별도 근거 |
| 후면 델트 | 후면 | 명시적 |

측면 레이즈(중간 삼각근)는 4.3의 계산식에 대응 항목이 없어 배정이 필요했다. 밀기로 배정한 이유는 두 가지다. 실제 훈련에서 어깨 프레스와 함께 밀기 세션에 배치되는 것이 일반적이며, 당기기에 넣을 경우 당기기 볼륨이 부풀려져 **당기기 부족을 놓치는 방향**으로 오판하게 된다.

**업라이트 로우 처리**

`body_part`는 SHOULDERS로 예외 지정하였으나(승모근이 주동근이지만 측면 삼각근을 타겟), 판정은 `primary_muscle = traps`를 따라 BACK으로 집계한다. 두 축이 어긋나지만, 업라이트 로우가 승모 상부를 주로 사용하는 것은 사실이므로 왜곡이 크지 않고, 예외 목록을 이중으로 관리하지 않는 편이 낫다고 판단하였다.

### 한계 인지

- **DELT_REAR가 3종목으로 얇다.** 판정과 후보정의 최소선(3개 기구 계열)은 충족하나, 후보 다양성이 부족하다. 후보 풀 402개에 후면 델트 종목이 더 존재하므로 보강 1순위로 둔다.
- **어깨 전·후면 배분은 원본 데이터에 없는 판단이다.** 동작 패턴 기반 추정이므로, 개별 종목 단위로 보면 이견이 있을 수 있다. 근거를 위 표에 명시하여 검증 가능하게 하였다.
- **판정 단위(9종)와 저장 단위(6종)가 다르다.** 화면에 표시되는 부위 분류와 판정 결과의 부위 명칭이 달라 사용자 혼란 가능성이 있다. 분석 결과 화면에서 명칭을 어떻게 노출할지는 시각화 설계 시 별도 검토한다. → **[LOG-10](#log-10)에서 2계층 구성으로 해소.**

<a id="log-10"></a>
## LOG-10. 판정·표시 부위의 2계층 구성

### 기존 버전

LOG-09에서 판정 단위를 `primary_muscle` 기반 9종으로 확정하였으나, 그 결과를 화면에 어떻게 노출할지는 정하지 않고 한계 인지 항목으로 남겨두었다.

> 판정 단위(9종)와 저장 단위(6종)가 다르다. 분석 결과 화면에서 명칭을 어떻게 노출할지는 시각화 설계 시 별도 검토한다.

8월 3주에 제작한 프론트엔드 목업은 홈·분석·통계 화면 전체를 `body_part` 6종으로 구성하였다. 미해결 항목에 대해 "6종으로 표시한다"는 답을 낸 상태였다.

### 기존 버전의 문제점

**1. 균형 판정이 설계서대로 동작하지 않는다.**

목업의 계산식은 다음과 같았다.

```
밀기   = 가슴 + 어깨 전체 + 팔 × 0.5
당기기 = 등 + 팔 × 0.5
```

설계서 4.3이 정한 `밀기 = 가슴 + 전면어깨 + 삼두`, `당기기 = 등 + 후면어깨 + 이두`와 다르다. 6종만으로는 삼두를 밀기에, 이두를 당기기에 배분할 수 없어 0.5씩 기계적으로 나누는 근사치를 쓴 것이다.

이 계수 0.5는 근거가 없다. 설계서 0장의 "근거로 방어할 수 없는 정밀도를 피한다"에 어긋나며, 실제로도 이두만 수행한 사용자와 삼두만 수행한 사용자가 동일한 균형 판정을 받는다. 후면 어깨 볼륨이 밀기로 집계되어 **당기기 부족을 놓치는 방향**의 오판도 발생한다.

**2. 부족 판정이 LOG-09가 지적한 상태로 되돌아간다.**

이두 12세트·삼두 0세트인 사용자에게 "팔 12세트, 최적"이 표시된다. 약점을 놓치는 방향의 오판이며, LOG-02에서 결정적 근거로 삼았던 것과 동일한 성격의 문제이다.

**3. 그렇다고 9종을 그대로 노출하기도 어렵다.**

"전면 삼각근", "후면 삼각근" 같은 명칭은 일반 사용자가 구분하지 못한다. 계획서 7장의 실사용자 검증은 지인 약 10명을 대상으로 하는데, 화면 용어를 이해하지 못하면 만족도 평가 자체가 유효하지 않게 된다.

### 수정 버전

판정 단위 9종을 유지하되, 화면은 **표시 6종(상위) — 판정 9종(하위)** 의 2계층으로 구성한다.

| 표시 부위 (상위) | 판정 부위 (하위) | 화면 표기 |
|---|---|---|
| 가슴 | CHEST | 가슴 |
| 등 | BACK | 등 |
| 어깨 | DELT_FRONT / DELT_REAR | 어깨(앞) / 어깨(뒤) |
| 팔 | TRICEPS / BICEPS | 삼두 / 이두 |
| 하체 | QUADS / POSTERIOR | 앞허벅지 / 뒤허벅지·둔근 |
| 코어 | CORE | 코어 |

- 상위 6종은 `body_part`와 일치하므로 종목 검색·필터·차트 분류에 그대로 쓴다.
- 하위 9종이 실제 판정 단위이며, 4단계 부족 판정과 균형 계산은 모두 이 단위로 수행한다.
- 상위가 하위 하나만 갖는 가슴·등·코어는 펼침이 없다. 계층이 갈리는 것은 **어깨·팔·하체 3개뿐**이다.
- 종아리·전완은 판정 대상이 아니므로 계층에 포함하지 않고 별도 "표시만" 영역에 둔다.

**라벨 규칙**: 상위 항목에는 판정 라벨을 붙이지 않는다. 세트 수만 표시하고 부족/권장 이하/최적/과다 판정은 하위에만 붙인다. 하위가 둘인 부위는 상위에 요약 배지(예: "일부 부족")를 표시한다. 상세는 「운동 분석 로직 설계서」 2.4에 둔다.

균형 판정 계산식은 설계서 4.3을 그대로 사용한다.

```
밀기   = CHEST + DELT_FRONT + TRICEPS
당기기 = BACK + DELT_REAR + BICEPS
상체   = CHEST + BACK + DELT_FRONT + DELT_REAR + TRICEPS + BICEPS
하체   = QUADS + POSTERIOR + 종아리
```

### 수정한 이유와 방식

**이유**: 판정 정확도와 사용자 이해도가 충돌하는 상황이었다. 9종을 그대로 노출하면 정확하지만 이해되지 않고, 6종으로 판정하면 이해되지만 확정 기능인 균형 판정이 성립하지 않는다. 계층을 나누어 **판정은 9종으로 정확하게, 요약 표시는 6종으로 익숙하게** 처리함으로써 양쪽을 함께 만족시킨다.

**방식**: LOG-09가 "판정 단위와 저장 단위를 분리"를 채택한 논리를 화면에 연장한 것이다. LOG-09가 스키마 수준에서 두 단위를 분리했다면, 본 항목은 화면 수준에서 같은 분리를 수행한다. 새로운 원칙을 도입하지 않으므로 근거를 별도로 세울 필요가 없다.

세 선택지를 비교하였다.

| 선택지 | 판단 |
|---|---|
| 판정·표시 모두 9종 | 설계서와 완전 일치하나, 명칭의 이해도가 낮아 실사용자 검증이 흐려진다 |
| 판정·표시 모두 6종 | LOG-09를 3주 만에 되돌리는 결정이며, 균형 판정이 근거 없는 계수에 의존하게 된다 |
| **판정 9종 · 표시 2계층 (채택)** | 판정 정확도를 유지하면서 요약 화면의 이해도를 확보한다. 계층이 갈리는 부위가 3개뿐이라 화면 부담이 작다 |

**발견 경위**: 본 항목은 8월 3주 프론트엔드 목업을 설계 문서와 대조하는 과정에서 드러났다. 목업이 미확정 사항(화면 표시 단위)에 대해 암묵적으로 답을 내고 있었고, 그 답이 확정 기능과 충돌하는 것을 확인하여 명시적 결정으로 승격하였다.

### 한계 인지

- **상위 항목의 세트 수는 하위의 단순 합이다.** 사용자가 상위 숫자만 보고 판단할 경우 LOG-09가 지적한 오해("팔 12세트니까 충분하다")가 여전히 발생할 수 있다. 라벨 규칙으로 완화하되 완전히 제거되지는 않는다.
- **QUADS의 화면 명칭이 부정확하다.** 이 부위는 `quadriceps` 외에 `abductors`·`adductors`를 포함하므로 "앞허벅지"라는 표기가 정확하지 않다. 해당 종목 수가 적어 실사용 영향이 작다고 보고 감수하되, 종목 정제 결과를 확인한 뒤 재검토한다.
- **요약 배지의 문안이 미확정이다.** 하위 둘이 서로 다른 방향으로 벗어난 경우(한쪽 부족·한쪽 과다)의 표기를 포함해 화면 구현 시 확정한다.

## 최종 보고서 작성 시 활용 방법

계획서 8장은 예상되는 어려움을 미리 정리한 장이고, 최종 보고서에서는 실제로 무엇이 달라졌는지를 쓰게 된다. 본 로그의 각 항목은 다음과 같이 대응한다.
