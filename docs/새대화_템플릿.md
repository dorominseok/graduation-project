# 새 대화 시작 템플릿

> 대화가 길어지면 새 세션으로 옮기고, 이 문서에서 상황에 맞는 프롬프트를 복사해 쓴다.
> 파일만 첨부하면 맥락이 복원되므로 내용 손실은 거의 없다.

---

## 공통 — 매번 앞에 붙일 기본 정보

```
컴퓨터공학과 졸업작품으로 헬스 웹앱(PWA)을 만들고 있어.

[프로젝트]
운동 기록을 분석해 약점 부위를 자동 판정하고, 그에 맞는 오늘의 루틴을 추천하는 앱.
친구 그룹끼리 서로의 운동 활동(주간 횟수·시간)도 공유함.

[스택]
React (PWA) / Spring Boot (Java) / PostgreSQL
Docker → AWS EC2, GitHub Actions (CI/CD), FCM(푸시, 추가 기능)

[일정]
8월: 설계 확정 → 환경 구축 + 운동 DB 정제 → 프론트엔드 → LLM 사전 실험
9월: 백엔드 기초 → 운동 기록 → 통계
9월 말~10월 초: 약점 분석 로직
10월 중~말: 루틴 추천
11월: 뱃지·그룹 → 배포·테스트 → 피드백·개선

[핵심 설계 원칙]
- 약점 판정은 자체 로직(ACSM 기준), LLM은 후보 안에서 조합만 담당
- RAG 미사용 (정형 데이터라 조건 조회로 대체)
- 사용자 제약(부상·기구)은 입력받지 않고, 생성된 루틴을 후보정으로 조정
- 기록은 세션(하루 한 번 운동) — 세트(1개 = 1행) 2계층 구조
- 볼륨 집계는 완료 세션의 본세트만 (워밍업 제외), 운동 시간은 세트 저장 시각으로 자동 산출

[지도교수 피드백 — 개발 순서]
1. 운동 기록 방식을 구체화해 충실한 기록 확보
2. 기록 기반 분석 제공 (그래프 시각화 + LLM 평가·해설)
3. 마지막으로 부족한 부분 추천
→ 기존 일정과 순서 일치. 단 '기록 방식 구체화'와 'LLM 분석 평가'를 보강함.
```

**첨부**: `운동_분석로직_설계서.md`, `운동기록_방식_설계서.md`, `개발환경_구축_기록.md`

```
[공통 정보]

운동 종목 DB를 만들려고 해. free-exercise-db(퍼블릭 도메인, 800개+)를 쓸 예정이야.
https://github.com/yuhonas/free-exercise-db

JSON에서 필요한 필드만 뽑고, PostgreSQL COPY로 적재할 수 있는 CSV 형태로 만들어줘.
자주 쓰이는 종목부터 우선 정제하는 방향으로.
```

## 팁

- **관련 파일만 첨부한다.** 전부 올리면 대화가 흐려진다.
- **새 대화에서 정한 내용은 문서에 반영해 둔다.** 그래야 다음 대화로 넘어갈 때도 같은 방식이 통한다.
- **기존 설계를 바꿨다면 `설계변경_로그.md`에 항목을 추가한다.** 기존 버전 / 문제점 / 수정 버전 / 이유와 방식 네 부분으로 남기면, 최종 보고서의 "계획과 달라진 부분"을 그대로 쓸 수 있다.
- **파일 교체 방식**: Claude는 프로젝트 파일을 직접 수정할 수 없으므로, 수정본을 받아 다운로드한 뒤 프로젝트의 기존 파일을 교체한다.
- **주제가 바뀌면 대화를 나눈다.** "분석 로직 구현" → "AWS 배포"처럼 성격이 다르면 새 대화가 낫다.
- 지금까지의 결정과 근거는 설계서에 기록돼 있으므로, **"왜 이렇게 했더라?" 싶을 때 문서를 먼저 본다.**
