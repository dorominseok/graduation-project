## 1. 무엇을 알리나

| 알림 | 언제 | 받는 사람 |
|---|---|---|
| **운동 리마인더** | 사용자가 고른 **요일·시각**에, 그날 기록이 없을 때 | 본인 |
| **주간 요약** | 사용자가 고른 **요일·시각**(기본 일요일 저녁 8시), 주 1회 | 본인 |
| **응원 받음** | 그룹 멤버가 내 기록에 응원하는 즉시 | 응원받은 사람 |
| **그룹 소식** | 새 멤버가 들어올 때 / 방장이 넘어올 때 즉시 | 새 멤버 → 방장만, 방장 위임 → 새 방장만 |

**알리지 않는 것**

| 후보 | 이유 |
|---|---|
| 멤버 운동 소식("OO님이 운동했어요") | 멤버가 많으면 하루에 여러 번 온다 |
| 회복 완료("가슴 회복이 끝났어요") | 거의 매일 온다. 회복 지도로 충분하다 |
| 루틴 만족도 질문 | 우리 데이터를 위한 것이라 알림까지 보낼 일이 아니다. 홈 카드로 충분하다 |
| 약점 보완 제안 | 따로 보내면 잔소리가 된다. 리마인더·주간 요약 문구에 이미 들어간다 |
| 연속 운동 끊김 | 앱에 연속 기록 기능이 없다 |
| 휴식 타이머 종료 | 알림으로 띄우지 않는다. 앱 안에서 소리·진동으로 알리고, 휴식 중에는 화면이 꺼지지 않게 잡아 둔다(Screen Wake Lock) — 서버가 필요 없는 별도 작업 |

## 2. 결정

| 항목 | 결정 | 이유 |
|---|---|---|
| 리마인더를 보내는 날 | **사용자가 고른 요일에만**. 쉬는 날은 보내지 않는다 | 앱은 오늘이 쉬려던 날인지 알 수 없다. 기록으로 짐작하면 쉬는 날에도 온다 |
| 리마인더 요일 기본값 | 처음 켤 때 최근 4주 자주 운동한 요일을 미리 골라 둔다. 기록이 없으면 월·수·금 | 사용자는 확인만 하면 된다 |
| 리마인더 시각 | 사용자가 고른다. 기본 저녁 7시, 30분 단위 | 사람마다 운동 시간이 다르다 |
| 리마인더 문구 | **오늘의 루틴을 만드는 규칙 그대로** — `SlotPlanner`로 그날 묶음을 계산하고 "왜 오늘 이 부위인지" 문장(`RoutineReason`, 루틴 설계서 7.3)을 쓴다. LLM은 부르지 않는다 | 알림과 루틴이 다른 말을 하지 않는다. 판정·불균형·모자란 양·쉰 기간이 이 규칙에 이미 순서대로 들어 있다. 다른 기준(가장 모자란 부위 등)을 따로 쓰면 회복 중이라 루틴이 빼는 부위를 알림이 권한다 |
| 오늘 루틴을 이미 만들었으면 | 다시 계산하지 않고 저장된 루틴의 이유(`routines.reason`)를 쓴다 | 같은 날 같은 말 |
| 루틴이 비는 날 | 보내지 않는다 | 모든 부위가 회복 중이거나 과다 경계에 걸린 날이다. 권할 게 없는데 보내면 잔소리다 |
| 주간 요약 요일·시각 | 사용자가 고른다. 기본 **일요일 20:00**. 요일 하나 | 사용자 요청 |
| 리마인더와 요약이 같은 날 | 각자 보낸다(하루 2건이 될 수 있다) | 둘 다 사용자가 고른 것이고 요약은 주 1회다 |
| 조용한 시간 | **22:00\~08:00에는 보내지 않는다.** 1차에서는 고정. 리마인더·요약 시각은 08:00\~21:30 안에서만 고를 수 있다 | 고르는 시각과 조용한 시간이 부딪치지 않게 |
| 조용한 시간에 생긴 응원·그룹 소식 | 버린다(아침에 몰아 보내지 않는다) | 그룹 화면에서 보인다. 몰아 보내려면 보낼 목록을 쌓는 장치가 따로 필요하다 |
| 시간대 | 한국 시간(Asia/Seoul) | 사용자가 한국에 있다 |
| 종류별 켜기·끄기 | 네 종류 각각 | |
| 권한 요청 | 설정에서 "알림 받기"를 눌렀을 때만 브라우저 권한을 묻는다 | 처음 열자마자 묻으면 대부분 거절한다. iOS는 사용자가 누른 순간에만 물을 수 있다 |
| 누르면 | 리마인더 → 홈(`/`), 주간 요약 → 분석 탭(`/analysis`), 응원·그룹 소식 → 그 그룹(`/group/{id}`) | |

## 3. 문구

| 알림 | 제목 | 본문 예시 |
|---|---|---|
| 운동 리마인더 | 오늘 운동할 날이에요 | 어제 한 밀기는 쉬고, 어깨 후면이 주 3세트로 부족해서 오늘은 당기기 날이에요. |
| 〃 (기록 없음) | 〃 | 아직 기록이 없어서 큰 근육부터 시작해요. 오늘은 밀기 날이에요. |
| 주간 요약 | 이번 주 운동 | 이번 주 4일 운동했어요. 더 채우면 좋은 부위: 어깨 후면, 종아리 |
| 〃 (모자란 부위 없음) | 〃 | 이번 주 4일 운동했어요. 모든 부위를 충분히 채웠어요. |
| 〃 (이번 주 기록 없음) | 〃 | 이번 주는 운동 기록이 없어요. 다음 주에 다시 시작해 봐요. |
| 응원 받음 | 응원을 받았어요 | 민석님이 11월 15일 운동에 응원했어요. |
| 그룹 소식 — 새 멤버 | 새벽 헬스 | 지수님이 그룹에 들어왔어요. |
| 그룹 소식 — 방장 위임 | 새벽 헬스 | 이제 이 그룹의 방장이에요. |

- 주간 요약의 "이번 주"(운동한 날 수)는 월요일부터 보내는 날까지다. 더 채울 부위는 분석 탭과 같은 판정(보내는 날 기준)의 부족 · 권장 이하에서 최대 두 개 — 부족 먼저, 같으면 주당 세트가 적은 순.
- 응원 알림은 응원한 사람의 닉네임과 그 기록의 날짜를 쓴다. 한 기록에 한 사람은 한 번만 응원할 수 있다(`uq_cheers`).

## 4. 구성

### 4.1 화면

- **서비스워커는 알림 전용**(`src/sw.ts`) — `push`(알림 띄우기)와 `notificationclick`(눌렀을 때 이동)만 처리하고 **요청을 가로채지 않는다(fetch 처리 없음, 캐시 없음)**. 지금 서비스워커를 끈 이유("배포한 새 화면이 캐시에 막혀 늦게 보인다")를 다시 만들지 않기 위해서다. 서비스워커를 켜도 `/licenses/`는 앱 화면으로 돌려보내지 않는다(fetch를 처리하지 않으므로 그대로 둔다).
  - 빌드: vite-plugin-pwa를 workbox가 만드는 서비스워커(generateSW) 대신 직접 쓴 파일을 빌드만 하게(`injectManifest`, `injectionPoint` 없음 — 미리 받아 둘 파일 목록을 넣지 않는다) 바꿨다. 결과는 `/sw.js` 하나(1kB 안쪽), 일반 스크립트(iife). 검사는 `tsconfig.sw.json`이 따로 한다(전역이 `window`가 아니라서)
  - **등록은 알림을 켤 때만**. 켜지 않은 사람에게는 서비스워커가 없다. 끄면 구독과 함께 등록도 지운다
  - 누르면: 열린 앱 창이 있으면 앞으로 가져와 그 창의 라우터로 옮긴다(새로 불러오면 메모리의 로그인 상태부터 다시 하므로). 없으면 새 창. 앱 밖 주소는 열지 않는다(홈으로) — 글자가 `/`로 시작하는지가 아니라 브라우저처럼 주소를 풀어 출처가 같을 때만 그 경로를 쓴다(`safeAppPath`). `/\evil.example`·`/(탭)/evil.example`은 브라우저가 `//evil.example`로 읽기 때문이다
  - 안드로이드 상태 표시줄 그림은 `icons/badge-96.png`(파비콘의 흰 덤벨, 투명 바탕)
- **설정 › 운동 알림**(`/settings/notifications`):
  - 위: **이 기기에서 알림 받기** — 누르면 그 순간 권한을 묻고(아이폰은 누른 직후에만 물을 수 있다) → 서비스워커 등록 → 구독 → 서버 등록. 아래 한 줄에 상태: 켜짐(다른 기기 수), 꺼짐, 받을 수 없는 환경
  - 아래: **계정 설정**(모든 기기에 같이) — 운동 리마인더(요일 여러 개·시각), 주간 요약(요일 하나·시각), 응원 받음, 그룹 소식. 바꾸면 저장 버튼 없이 0.5초 뒤 저장(요일을 여러 번 누르면 한 번). 리마인더 요일은 하나 이상 남긴다. 시각은 08:00\~21:30, 30분 단위 목록. 맨 아래 조용한 시간 안내 한 줄
  - 처음(저장 전)이면 "요일은 최근 4주에 자주 운동한 요일로 골라 두었어요"
- **받을 수 없는 환경**은 켜기를 막고 이유를 적는다 — 아이폰 브라우저 탭(홈 화면에 추가한 앱에서만, iOS 16.4 이상), iOS가 낮음, 지원하지 않는 브라우저(카카오톡 안 브라우저 등), 권한 거절(브라우저·휴대폰 설정에서 풀어야 한다), 서버에 키가 없음
- **이 기기와 계정**: 브라우저 구독은 계정을 모르므로 어느 계정이 켰는지를 브라우저에 적어 둔다(`balancefit.push.user`)
  - 로그아웃하면 이 기기의 알림을 끈다(서버에서 지우고 구독·서비스워커 삭제, 3초까지만 기다림). 탈퇴는 서버가 이미 지웠으니 브라우저 쪽만
  - 로그인이 만료된 뒤 **다른 계정**이 들어오면 앞 계정의 구독을 버린다 — 앞 계정의 알림이 이 기기로 오지 않게. 서버의 옛 기록은 다음 발송에서 푸시 서버가 "없다"(410)고 답해 지워진다. 같은 계정이 다시 들어오면 그대로 둔다(리마인더는 앱을 오래 안 연 사람에게 더 필요하다)
  - 설정을 열었는데 이 기기는 켜져 있고 계정의 기기 수가 0이면 같은 구독을 다시 등록한다
  - **비밀번호를 바꾸면 계정의 알림 기기를 모두 지운다** — 비밀번호 변경은 모든 기기를 로그아웃시키고, 로그아웃한 기기에는 알림을 보내지 않는다. 바꾼 그 기기도 로그아웃하며 꺼지므로, 다시 로그인한 뒤 설정 › 알림에서 켠다

### 4.2 서버

- **표준 웹 푸시(VAPID, RFC 8292) — 라이브러리 없이** JDK만으로 만든다. 본문 암호화(RFC 8291 aes128gcm)는 JDK의 ECDH·HMAC·AES-GCM, 서명(ES256)은 이미 쓰는 jjwt, 발송은 `java.net.http.HttpClient`. 암호화는 RFC 8291 부록 A의 예시 값으로 테스트한다(`WebPushEncryptionTest`). 웹 푸시 라이브러리들이 끌고 오는 BouncyCastle·오래된 HTTP 클라이언트를 들이지 않기 위해서다.
- **키**: 공개키는 화면이 구독할 때 쓰고(설정 조회 응답의 `vapidPublicKey`), 비밀키는 서버 `.env`에만 둔다. `./gradlew vapidKeys`가 한 쌍을 찍어 주면 사용자가 서버 `.env`의 `VAPID_PUBLIC_KEY` · `VAPID_PRIVATE_KEY`에 넣는다 — 값은 대화·로그·커밋에 남기지 않는다. 둘 다 비면(로컬 기본) 보내지 않고 예약 작업도 돌지 않으며 화면에는 `pushAvailable: false`. 하나만 있거나 짝이 맞지 않으면 서버가 시작하지 않는다(모든 알림이 거절되기 전에 멈춘다).
- 저장(V14):
  - `push_subscriptions` — 사용자, 푸시 주소(endpoint, 유일), 암호화 키(p256dh·auth), 만든 때. 한 사용자가 여러 기기를 쓸 수 있고, 같은 브라우저로 다른 계정이 등록하면 그 줄의 주인이 바뀐다
  - `notification_settings` — 사용자당 한 줄: 네 종류 켜기·끄기, 리마인더 요일(월 1 · 화 2 … 일 64 비트)·시각, 요약 요일(1\~7)·시각. 시각은 DB 제약으로도 08:00\~21:30 · 30분 단위
  - 처음 기기를 등록할 때 설정을 기본값(네 종류 켜짐, 2장의 요일·시각)으로 저장한다. 설정 줄이 없는 사용자는 모두 켜진 것으로 본다
- API(「API_명세서」 12장): `GET` · `PUT /users/me/notification-settings`, `POST` · `DELETE /users/me/push-subscriptions`.
- **푸시 주소는 브라우저 회사의 푸시 서버만 받는다**(`PushEndpointPolicy`, 2026-11-17). 주소는 화면이 보내는 값이고 서버는 알림 때마다 그 주소로 요청을 보낸다 — 아무 주소나 받으면 로그인한 누구나 서버가 내부망·남의 서버를 부르게 할 수 있고, 응답이 느린 주소를 여럿 등록해 하나뿐인 예약 스레드를 기기당 최대 10초씩 붙잡을 수 있다.
  - 받는 호스트: `fcm.googleapis.com`, `*.push.services.mozilla.com`, `*.push.apple.com`, `*.notify.windows.com`. https, 포트는 443만, 주소에 계정 정보(`user:pw@`)가 붙으면 거절
  - 등록할 때 확인해 `400 VALIDATION_ERROR`("이 브라우저의 알림은 아직 지원하지 않습니다")로 거절하고, **거절한 호스트를 warn 로그로 남긴다**(`허용하지 않는 푸시 서버라 등록을 거절: host=…`). 처음 보는 브라우저의 푸시 서버가 찍히면 확인한 뒤 목록에 더한다
  - 보낼 때도 확인한다(`WebPushGateway`). 목록이 생기기 전에 저장된 주소가 남아 있으면 요청을 보내지 않고 그 구독을 지운다(warn 로그)
  - **한 계정에 기기 10개까지**. 넘으면 `400 VALIDATION_ERROR`. 이미 등록한 기기를 다시 보내는 것은 센 것으로 치지 않는다
- **브라우저 공개키(`p256dh`)는 P-256 곡선 위의 점이어야 받는다**(`EcKeys.publicKey`, 2026-11-18). JDK는 곡선 밖의 점도 키로 만들어 주고 보낼 때 암호화(ECDH)에서야 실패한다 — 그대로 두면 그 사람에게 보낼 때마다 예외로 멈춰 그 사람의 다른 기기에도 못 보낸다. 등록할 때는 `400 VALIDATION_ERROR`, 검사가 생기기 전에 저장된 키는 보낼 때 걸러 그 구독을 지운다
- **예약 작업**(`NotificationScheduler`): 30분마다(정각·30분, Asia/Seoul) 돌며 그 칸이 리마인더·요약 시각인 사용자(기기가 하나라도 있는)에게 보낸다. 서버는 한 대라 중복 발송 걱정이 적다. 서버가 꺼져 있던 회차는 나중에 몰아 보내지 않는다. 한 사람에서 실패해도 다음 사람으로 넘어간다.
- **리마인더 문구**: `RoutineService.reminderReason` — 오늘 저장된 루틴이 있으면 그 `reason`, 없으면 `createToday`와 같은 계획(`SlotPlanner` → `RoutineReason`)을 저장 없이 계산한다. 계획이 비면 보내지 않는다. 저장된 루틴이 항목 없는 빈 루틴이어도 보내지 않는다(2026-11-17, #58 — 전에는 "담을 부위가 없어요" 문장으로 나갔다).
- **즉시 알림**: `GroupService`가 응원 저장(새로 저장될 때만 — 이미 응원한 기록을 또 눌러도(연타) 한 번이고, 취소한 뒤 다시 누르면 다시 간다. 같은 `tag`라 기기에 떠 있는 알림을 바꾼다), 그룹 참여, 방장 위임 뒤 이벤트를 내고(`group/event/GroupEvents`), `GroupNotificationListener`가 **커밋된 뒤 다른 스레드에서** 보낸다(`@TransactionalEventListener(AFTER_COMMIT)` + `@Async`). 알림이 느리거나 실패해도 원래 요청은 기다리지 않고 성공한다.
- 유효 시간(TTL): 즉시 알림 24시간, 리마인더·요약 3시간 — 휴대폰이 꺼져 있다가 늦게 받으면 의미 없는 알림은 버려지게.
- 발송이 "구독이 없어졌다"(404·410)로 오면 그 구독을 지운다. 회원 탈퇴 시 구독·설정도 같이 지운다(외래키 연쇄 삭제).
- 알림 본문(서비스워커가 받는 JSON): `{ "title", "body", "url", "tag" }`. `tag`는 같은 종류가 쌓이지 않고 바뀌게 — `reminder`, `summary`, `cheer-{그룹}`, `group-{그룹}`.

## 5. 개인정보

- 새로 저장하는 것: 브라우저 푸시 주소와 암호화 키, 알림 설정. 개인정보처리방침(`PrivacyScreen`)에 항목·목적·보관(끄거나 로그아웃하면 그 기기 주소 삭제, 탈퇴 시 전부 삭제)·관리 방법을 더했다(시행일 2026-11-15).
- 알림 본문은 브라우저 회사의 푸시 서버(Google·Apple·Mozilla)를 거친다. 웹 푸시는 본문을 암호화해서 보내므로 그 서버는 내용을 읽지 못한다 — 이 점도 방침에 적는다.

## 6. 완료 기준

**서버**
- 리마인더: 고른 요일·시각에만, 그날 기록이 있거나 루틴이 비면 보내지 않음, 문구가 `RoutineReason`과 같음(저장된 루틴이 있으면 그 문장)
- 주간 요약: 고른 요일·시각에 주 1회, 이번 주 운동한 날 수와 부족 부위
- 응원·그룹 소식: 받는 사람이 맞음(새 멤버 → 방장만, 위임 → 새 방장만), 조용한 시간에는 보내지 않음, 알림 실패가 원래 동작을 막지 않음
- 종류별 끄기, 조용한 시간, 만료 구독 삭제, 탈퇴 시 삭제 — 테스트로 고정. 시각 계산은 `Clock`을 바꿔 가며 테스트
- API 명세 반영, 백엔드 전체 테스트 통과

**화면**
- 설정 › 알림(권한 요청 → 구독 → 종류·요일·시각), 받을 수 없는 환경 안내
- 서비스워커가 요청을 가로채지 않음(배포한 새 화면이 바로 보임)
- 알림을 누르면 정한 화면으로 감
- 유리 테마 폭 360·390·430 캡처, `npm run lint`·`npm run build` 통과

**운영**
- VAPID 키를 만들어 비밀키를 서버 `.env`에 넣기(사용자), 배포 뒤 실제 휴대폰(안드로이드 크롬, 홈 화면에 설치한 아이폰)에서 네 종류를 받아 보기
