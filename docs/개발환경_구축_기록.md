### 1.2 WSL2 설정

Windows용 Docker Desktop이 WSL2 기반으로 동작하므로 선행 설치가 필요하다.

```powershell
wsl --install --no-distribution
```

`--no-distribution` 옵션을 사용해 Ubuntu 등 배포판 없이 WSL2 기반만 설치하였다. 본 프로젝트에서 리눅스 셸을 직접 사용할 일이 없으므로 불필요한 구성 요소를 배제한 것이다.

### 1.3 PowerShell 인코딩

한국어 Windows의 PowerShell 기본 코드 페이지(949)와 Git의 UTF-8 출력이 충돌해 한글 파일명이 깨진다. 세션마다 아래를 적용한다.

```powershell
chcp 65001
```

파일 자체는 손상되지 않으며 출력만 깨지는 문제이다. 항구적 해결이 필요하면 Windows Terminal 또는 PowerShell 7로 전환한다.

## 2. 빌드 도구 선택 — Gradle

### 2.1 결정

Gradle(Groovy DSL)을 채택하였다.

### 2.2 근거

| 항목 | 판단 |
|---|---|
| 참고 자료 | Spring Initializr 및 공식 문서 기본값이 Gradle이다. 문제 해결 시 참조할 예제를 그대로 적용할 수 있다 |
| 빌드 속도 | 증분 빌드가 빨라 9~10월 반복 실행 구간에서 체감 이점이 있다 |

Maven은 XML 기반이라 구조가 명시적이고 초심자 가독성이 낫다는 장점이 있으나, 그 이점은 주로 팀 협업 상황에서 유효하다. 개인 개발 조건에서는 위 세 항목의 비중이 더 크다고 판단하였다.

### 2.3 Kotlin DSL 배제

`build.gradle.kts` 대신 `build.gradle`(Groovy)을 선택하였다. Kotlin DSL은 IDE 자동완성 품질이 우수하나, Kotlin 문법을 모르는 상태에서는 빌드 오류 메시지 해석이 어렵고 검색 가능한 예제가 적다.

## 3. 저장소 구조

### 3.1 모노레포 채택

백엔드·프론트엔드·문서를 단일 저장소에 둔다.

```
graduation-project/
├─ backend/            # Spring Boot
├─ frontend/           # React (Vite, PWA)
├─ docs/               # 설계 문서
├─ .github/workflows/  # CI
├─ docker-compose.yml
├─ .env                # 로컬 전용 (gitignore)
├─ .env.example        # 공유용 견본
├─ .gitignore
└─ README.md
```

**근거**
- CI 워크플로우를 하나로 관리할 수 있다
- 설계 문서가 코드와 같은 저장소에 있어 변경 이력이 커밋 로그로 남는다. 「설계 변경 로그」를 별도 관리하는 본 프로젝트의 성격과 부합한다
- 코드 수정 시 관련 문서를 같은 커밋에서 갱신하는 습관이 유도된다
- 저장소가 백업 역할을 겸한다

### 3.2 문서 포함 범위

`docs/`에 포함한 것은 **프로젝트 산출물**로 한정하였다.

| 포함 | 제외 |
|---|---|
| 기능명세서 | 새대화 템플릿 |
| 유스케이스 정의서 | |
| 운동기록 방식 설계서 | |
| 운동 분석로직 설계서 | |
| 설계 변경 로그 | |

새대화 템플릿은 개발 과정에서 사용하는 작업 도구이지 산출물이 아니므로 제외하였다.

`.md` 파일은 Git이 줄 단위 변경을 추적하므로 이력 관리의 이점이 온전히 발휘된다. `.docx` 계획서는 바이너리라 변경 내용이 표시되지 않아 백업 목적 외의 실익이 적다.

### 3.3 Git 설정

기본 브랜치를 `main`으로 통일하였다(GitHub 기본값과 일치).

```powershell
git branch -M main
```

한글 파일명 출력 문제 대응:

```powershell
git config --global core.quotepath false
```

> **주의**: 문서 파일명의 한글은 허용하되, **코드 파일명은 영문으로 통일**한다. EC2(Linux) 배포 및 CI 환경에서 인코딩 문제가 발생할 수 있다.

### 3.4 저장소 공개 설정

Public으로 생성하였다. 이에 따라 **API 키·비밀번호를 코드에 직접 기재하지 않는 원칙**을 반드시 지켜야 한다. 8월 4주 LLM API 연동 실험 시 특히 유의한다.

## 4. 환경변수 분리 — .env / .env.example

### 4.1 구조

| 파일 | 내용 | Git 추적 |
|---|---|---|
| `.env` | 실제 접속 정보 | 제외 (gitignore) |
| `.env.example` | 항목명만, 값은 공란 | 포함 |

### 4.2 `.env` 항목

```
POSTGRES_DB=fitness
POSTGRES_USER=fitness
POSTGRES_PASSWORD=(로컬 개발용)
POSTGRES_PORT=5432
```

### 4.3 `.env.example`을 두는 이유

`.env`가 Git에서 제외되면 저장소만 받은 환경에서는 **해당 파일이 필요하다는 사실 자체를 알 수 없다.** 값을 비운 견본을 공개해 필요한 항목을 알린다.

본 프로젝트에서 이 파일이 실제로 쓰이는 시점은 두 가지이다.
- EC2 배포 시 서버에서 `.env`를 새로 작성할 때 (10월 중순)
- PC 교체·포맷 후 환경을 재구성할 때

## 5. PostgreSQL Docker 구성

### 5.1 DB만 컨테이너화 — 애플리케이션은 제외

개발 단계에서는 **PostgreSQL만 컨테이너로 띄우고 Spring Boot는 IDE에서 직접 실행**한다.

**근거**

| 항목 | DB만 컨테이너 (채택) | 애플리케이션까지 컨테이너 |
|---|---|---|
| 코드 수정 후 반영 | IDE 재실행, 수 초 | 이미지 재빌드, 수십 초~수 분 |
| 디버깅 | IDE 브레이크포인트 직접 사용 | 원격 디버깅 설정 필요 |
| 장애 원인 후보 | 코드 / DB 컨테이너 | + 컨테이너 간 네트워크, 이미지 빌드 시점, 환경변수 전달 |
| 현 시점 이점 | — | 없음 (로컬 단독 개발) |

컨테이너화의 본질적 이점은 실행 환경의 재현성이며, 이는 배포 시점에 발생한다. 개인이 단일 PC에서 개발하는 현 단계에서는 비용만 발생한다.

애플리케이션 컨테이너화는 배포 준비 시 `Dockerfile` 추가와 compose 서비스 확장으로 진행한다. 현재 구성을 확장하는 형태이므로 이번에 익힌 내용이 그대로 이어진다.

> **시점 변경 (LOG-15)**: 배포를 11월에서 **10월 중순**으로 앞당겼으므로, 이 작업은 **9월 말**에 착수한다. 실사용자 검증 4주가 압축 불가능한 벽시계 시간이고, 분석이 의미를 가지려면 기록이 먼저 4주 쌓여야 하기 때문이다.

### 5.2 docker-compose.yml 주요 설정

| 항목 | 값 | 의도 |
|---|---|---|
| `image` | `postgres:16` | 버전 고정 |
| `restart` | `unless-stopped` | 재부팅 후 자동 기동 |
| `TZ` | `Asia/Seoul` | **`performed_on` 일자 귀속에 직접 영향** |
| `ports` | `5432:5432` | PostgreSQL 표준 포트 |
| `volumes` | `postgres-data` | 컨테이너 삭제 시 데이터 유실 방지 |
| `healthcheck` | `pg_isready` | 접속 가능 상태 확인 |

`TZ` 설정은 단순 표시 문제가 아니다. 「운동기록 방식 설계서」 2.1에서 `performed_on`을 "자정을 넘겨 운동한 경우에도 시작 일자로 귀속"한다고 정하였으므로, DB 시간대가 어긋나면 분석 집계의 기준 일자가 틀어진다.

`volumes` 설정이 없으면 컨테이너를 삭제할 때 데이터가 함께 소멸한다.

### 5.3 상시 사용 명령

```powershell
docker compose up -d          # 기동
docker compose down           # 중지 (데이터 유지)
docker compose ps             # 상태 확인
docker compose logs postgres  # 로그 확인
```

> `docker compose down -v` 는 볼륨까지 삭제하여 **데이터가 전부 소멸**한다. 스키마를 초기화하고 재구축할 때만 사용한다.

### 5.4 검증

```powershell
docker exec -it fitness-postgres psql -U fitness -d fitness
```

접속 후 `\dt`로 테이블 부재를 확인하였다(4단계에서 생성 예정).

## 6. Spring Boot 구성

### 6.1 프로젝트 메타데이터

| 항목 | 값 |
|---|---|
| Group | `com.fitness` |
| Artifact | `backend` |
| Package | `com.fitness.backend` |
| Packaging | Jar |
| Configuration | **YAML** |
| Java | 21 |

Configuration을 Properties가 아닌 YAML로 선택한 것은, 프로필별 설정(local/prod)을 계층 구조로 한 파일에 표현할 수 있어 배포 시 환경 분리가 용이하기 때문이다. 프로필 분리는 9월 말 배포 준비에서 수행한다 — `application-prod.yaml`에서 actuator `show-details`를 `when-authorized`로 내리고 DB 접속 정보를 주입한다.

### 6.2 의존성

| 의존성 | 용도 |
|---|---|
| Spring Web | REST API |
| Spring Data JPA | ORM |
| PostgreSQL Driver | DB 드라이버 |
| Validation | 입력값 검증 |
| **Flyway Migration** | 스키마 버전 관리 |
| Lombok | 보일러플레이트 축소 |
| Spring Boot Actuator | 상태 점검 엔드포인트 |

### 6.3 Flyway 채택 — ddl-auto는 validate

**스키마는 Flyway가 전담하고, Hibernate는 검증만 수행한다.**

```yaml
jpa:
  hibernate:
    ddl-auto: validate
```

**근거**
- `ddl-auto: update`는 컬럼 삭제·타입 변경을 반영하지 못하며, 운영 중 예측 불가능한 스키마 변형을 일으킨다
- 스키마 변경이 SQL 파일로 남아 이력이 추적된다. 「설계 변경 로그」를 운영하는 본 프로젝트의 방향과 일치한다
- EC2 배포 시 마이그레이션이 자동 적용된다
- Hibernate가 테이블을 임의 생성하면 Flyway 관리 스키마와 충돌한다

### 6.4 open-in-view 비활성화

```yaml
jpa:
  open-in-view: false
```

Spring Boot 기본값은 `true`이나, DB 커넥션을 HTTP 요청 종료 시점까지 점유하여 커넥션 풀 고갈을 유발한다. 기동 시 경고 로그도 출력된다. 비활성화가 표준 권장 사항이다.

### 6.5 검증 — /actuator/health

```
GET http://localhost:8080/actuator/health
```

응답에서 다음을 확인하였다.

```json
"db": { "details": { "database": "PostgreSQL" }, "status": "UP" }
```

`db.status = UP`은 Spring Boot가 Docker 컨테이너의 PostgreSQL에 실제로 연결되었음을 의미한다. 3단계의 완료 조건으로 설정한 항목이다.

4단계의 완료 조건이 "테이블 생성"이 아니라 "집계 쿼리 동작"인 이유는, 스키마가 분석 요구사항을 실제로 지탱하는지를 이 시점에 확인해야 하기 때문이다. 「운동기록 방식 설계서」 0.1에서 지적한 대로, 구조 결함은 데이터가 쌓인 뒤에는 되돌릴 수 없다.

## 8. DB 스키마 (4단계)

### 8.1 users 테이블 포함

당초 `exercises` / `workout_sessions` / `workout_sets` 3개 테이블만 생성할 계획이었으나, `workout_sessions.user_id`가 `users`를 참조하므로 FK 성립을 위해 **최소 형태의 `users` 테이블이 함께 필요**하였다.

```
users (id, email, password_hash, nickname, created_at, updated_at)
```

인증 기능 구현은 9월이지만, 스키마상의 자리는 이번 마이그레이션에 포함하였다.

### 8.2 구현 결정

| 항목 | 결정 | 근거 |
|---|---|---|
| 파일 | `backend/src/main/resources/db/migration/V1__init.sql` | Flyway 기본 탐색 경로 |
| ENUM | PostgreSQL 네이티브 타입 대신 `VARCHAR + CHECK` | JPA `@Enumerated(STRING)` 매핑이 단순하고, 값 추가 시 마이그레이션이 가볍다 |
| 인덱스 | 설계서 2.2의 3개 생성 | 최근 4주 조회 / 세션 상세 / 종목별 1RM 추이 |
| `ON DELETE CASCADE` | 세션→세트에만 적용 | 세션 삭제 시 세트가 고아로 남는 것을 방지. 종목 삭제로 기록이 소실되면 안 되므로 `exercise_id`에는 미적용 |

| 보류 컬럼 | `duration_override_sec` 등 확보 | 설계서 4.4 방침에 따라 UI 미구현 항목도 컬럼은 미리 확보 |

`body_part` 등 코드값은 영문 대문자로 저장하고 화면 표시 시 한글로 변환한다. Java enum과 직접 매핑되며, DB에 표시 문자열이 섞이는 것을 피한다.

### 8.3 exercises.equipment 채택

검토 중이던 `equipment` 컬럼을 **추가하기로 결정**하였다. 상세 근거는 「설계 변경 로그」 LOG-08에 기록하였다.

- 루틴 후보정(기능명세 2.4)의 대체 후보를 `body_part`만으로 고르면 교체 사유를 해소하지 못한다

### 8.4 검증 결과

테이블 생성만으로는 완료로 보지 않고, 설계서 2.2의 부위별 세트 집계 쿼리가 실제로 동작하는지 확인하였다.

더미 데이터 구성:

집계 결과:

-----------+------------

## 9. React(Vite) PWA 구성 (5단계)

5단계부터 Claude Code로 진행하였다. 프론트엔드 뼈대와 백엔드 연동 확인 페이지를 작성하고, 개발 서버에서 `/actuator/health` 응답이 화면에 표시되는 것을 완료 조건으로 두었다(커밋 `1339004`).

### 9.1 스택 — Vite + React + TypeScript

Vite + React를 채택하고, 언어는 **TypeScript**로 하였다.

**TypeScript 채택 근거**

`measure_type` 4종(`WEIGHT_REPS` / `BODYWEIGHT_REPS` / `WEIGHTED_BODYWEIGHT` / `TIME`)에 따른 분기가 기록·히스토리·사후입력·루틴 프리필 4개 화면에 반복해서 나타난다. 이 값을 union 타입으로 정의하면 분기 케이스 누락을 컴파일 단계에서 잡을 수 있다. 런타임에 특정 종목 유형에서만 화면이 깨지는 문제를 사전에 차단하는 것이 목적이다.

같은 이유가 `workout_sets`에도 적용된다. `weight_kg` / `reps` / `duration_sec`는 종목 유형에 따라 배타적으로 `NULL`이며(8.2), 이 배타성을 타입으로 표현해 두면 잘못된 필드 접근이 컴파일 시점에 드러난다.

union 타입의 값은 V1 마이그레이션의 `ck_exercises_measure_type` CHECK 목록과 정확히 일치시킨다. DB 제약과 프론트 타입이 어긋나면 타입 검사의 의미가 없어진다.

### 9.2 JavaScript → TypeScript 전환 (8월 29일)

최초 구성은 JavaScript + Oxlint였다. 그러나 이는 `npm create vite` 기본 흐름을 그대로 따른 결과였을 뿐 의식적 선택이 아니었다. 소스가 `App.jsx` / `main.jsx` 2개뿐인 시점이 전환 비용이 가장 낮다고 판단해 8월 29일에 TypeScript로 전환하였다(커밋 `8bbdf35`).

**전환 시 확정한 사항**

| 항목 | 결정 | 근거 |
|---|---|---|
| TypeScript 버전 | `^6`로 고정 (6.0.3) | `typescript-eslint@8`의 peer 범위가 `<6.1.0`이라 TS 7과 충돌한다. `typescript-eslint`를 빼면 `.tsx` 린트 자체가 불가능하므로 6.x로 내렸다. TS 7 지원이 들어오면 재검토한다 |
| `src/vite-env.d.ts` | 추가 (`/// <reference types="vite/client" />`) | `tsconfig`의 `noUncheckedSideEffectImports` 하에서 `import './App.css'` 같은 CSS 부수효과 import가 타입 오류(TS2882)를 낸다. Vite 클라이언트 타입을 참조해 해소한다 |
| `tsconfig` 구성 | root / app / node 3분할 (Vite react-ts 템플릿 기준) | app(브라우저)과 node(설정 파일)의 `lib`·`target`이 다르므로 분리한다 |
| `noUnusedLocals` / `noUnusedParameters` | `false` | 뼈대 작성 단계에서 미사용 변수로 빌드가 깨지는 것을 막는다. 화면 구현이 진행되면 `true`로 되돌린다 |
| `build` 스크립트 | `tsc -b && vite build` | 타입 오류를 빌드 실패로 처리한다. `vite build` 단독은 타입을 검사하지 않는다 |
| `vite.config.js` | 삭제하고 `vite.config.ts`로 이전 | 9.4 참조 |

### 9.3 Oxlint → ESLint 교체

린터를 Oxlint에서 ESLint(flat config)로 교체하고, `lint` 스크립트를 `eslint .`로 변경하였다.

**근거**

- 6단계 CI가 `npm run lint`를 통과 조건으로 강제한다(12장). 린트 규칙의 실효성이 곧 CI의 실효성이다.
- 9~10월에 TanStack Query와 `useEffect`를 본격적으로 쓰게 되는데, 이때 필요한 것은 `eslint-plugin-react-hooks`의 hooks 규칙(의존성 배열 검증, 조건부 호출 금지)이다. Oxlint는 속도는 빠르나 이 규칙 커버리지가 목적에 못 미친다.
- 구성: ESLint flat config + `typescript-eslint`(파서·규칙) + `eslint-plugin-react-hooks` + `eslint-plugin-react-refresh`. 마지막 플러그인은 기존 Oxlint 설정의 `only-export-components` 규칙을 대체한다.

### 9.4 기록 누락 사건

8월 4일에 5~7단계를 실제로 완료하였으나 0장의 진행 표를 갱신하지 않았다. 그 결과 8월 29일에 이 문서만 보고 미착수로 오인해 프론트엔드를 다시 스캐폴딩하려 시도하였고, 기존 `node_modules`·`package-lock.json`과 충돌해 `npm install`이 ERESOLVE로 실패하였다.

더 위험했던 것은 `vite.config.js`와 `vite.config.ts`가 공존한 상태였다. Vite는 `.js`를 먼저 탐색하므로, 새로 작성한 `.ts` 설정이 조용히 무시된 채 넘어갈 뻔하였다. 설치가 실패해 이 상황이 조기에 드러난 것이 오히려 다행이었다.

`git log`로 기존 구현을 발견해 `git checkout`으로 복구한 뒤, 방향을 "재구축"에서 "JS→TS와 Oxlint→ESLint 두 항목만 조정"으로 바꾸었다.

**교훈**

기록되지 않은 완료는 미완료와 구별되지 않는다. 0장이 밝힌 목적(재현 가능한 환경 정보와 판단 근거)은 완료 표시 없이는 성립하지 않는다. 복구 판단에 직접 쓰인 자료가 코드 주석과 커밋 메시지였다는 점도 함께 기록한다. 단계 완료 시 진행 표(0장)와 완료 조건 표(7장)를 같은 커밋에서 갱신하는 것을 절차로 둔다.

### 9.5 검증

`docker compose up -d` → 백엔드 기동 → `frontend`에서 `npm run dev` 후, 개발 서버(`localhost:5173`)에서 `/actuator/health` 응답이 화면에 그대로 표시되는 것을 확인하였다. 응답의 `db.status = UP`이 프록시를 거쳐 전달됨을 확인하였다(프록시 구성은 10장). CI에서도 동일 절차(`npm ci` → `npm run lint` → `npm run build`)가 통과함을 확인하였다.

## 10. 개발 중 API 호출 경로 — 프록시와 환경변수

### 10.1 Vite server.proxy

`vite.config.ts`의 `server.proxy`로 `/api`와 `/actuator`를 `http://localhost:8080`(백엔드)으로 전달한다(`changeOrigin: true`).

```
/api      → localhost:8080
/actuator → localhost:8080   # actuator health 확인용 (5단계 완료 조건)
```

프록시가 없으면 브라우저가 `5173`에서 `8080`으로 직접 요청해 CORS가 발생한다. 프록시를 두면 요청이 같은 오리진(`5173`)으로 나가므로 개발 중 CORS 설정이 불필요하다. 프론트 코드는 항상 상대경로(`fetch('/actuator/health')`)로 호출한다.

### 10.2 배포 시 연속성

배포(10월 중순)는 정적 파일과 API를 한 도메인에 두는 **동일 오리진** 구성으로 한다. 상대경로 호출은 그대로 이어지며, 개발용 프록시가 하던 역할은 배포 시 리버스 프록시(nginx 등)가 맡는다. 절대 URL을 코드에 박지 않는 것이 배포까지의 연속성을 보장한다.

### 10.3 VITE_ 접두사 변수

Vite는 `VITE_` 접두사가 붙은 환경변수만 클라이언트 번들에 노출한다. 이 값들은 번들에 평문으로 포함되므로 **프론트 `.env`에 비밀값을 두어서는 안 된다.** API 키·토큰은 전부 백엔드를 경유한다. 3.4의 Public 저장소 원칙에 대응하는 프론트 쪽 규칙이다.

## 11. PWA 설정 범위 — 지금과 11월의 분리

> **배포는 10월 중순으로 앞당겨졌지만(LOG-15) 서비스워커·FCM은 11월에 그대로 둔다.** 개발 중 서비스워커가 정적 자원을 캐시하면 코드 수정이 반영되지 않는다는 11.1의 이유가 배포 시점과 무관하기 때문이다. 다만 **HTTPS는 배포와 함께 9월 말로 당겨진다** — 이유는 11.3.

### 11.1 현재 범위 — manifest만

`vite-plugin-pwa`를 넣되 현재는 **manifest만 등록**하고 서비스워커는 생성하지 않는다(`devOptions.enabled = false`, 기본값).

**이유**

개발 중 서비스워커가 정적 자원을 캐시하면 코드 수정이 브라우저에 반영되지 않는다. 이 문제를 피하기 위해 개발 단계에서는 서비스워커를 등록하지 않는다. manifest만으로도 9~10월 실기기 테스트(홈 화면 설치, 앱 아이콘·이름·전체화면 표시)는 가능하다.

### 11.2 11월로 미루는 것

| 항목 | 현재 | 11월 (2주) |
|---|---|---|
| manifest | 등록 | 유지 |
| 서비스워커 | 없음 | 등록 |
| 오프라인 캐싱 | 없음 | 캐싱 전략 수립 |
| 설치 프롬프트 | 없음 | `beforeinstallprompt` 처리 |
| FCM | 없음 | 서비스워커에 푸시 수신 통합 |
| 휴식 타이머 알림 | 표시만 (9월) | 소리·진동 추가. **FCM과 같은 알림 권한 하나**를 쓴다 (기록 방식 3.7) |

### 11.3 리스크 — HTTPS는 PWA가 아니라 인증의 선행 조건

초판은 이 절을 PWA 관점으로만 적었다. 서비스워커는 HTTPS에서만 등록되므로(`localhost`는 예외) IP 주소로만 배포하면 PWA 설치도 FCM 푸시도 동작하지 않는다 — 여기까지는 맞다.

**그러나 더 앞선 차단 요인이 있다.** API 명세서 2.3이 정한 리프레시 토큰 쿠키는 `Secure` 속성을 갖는데, `Secure` 쿠키는 http:// 오리진에서 브라우저가 **저장하지 않는다**(`localhost`만 예외). IP나 http로 배포하면 리프레시 토큰이 저장되지 않아 액세스 토큰 30분이 지나면 전원 로그아웃되고, 재로그인해도 30분 뒤 반복된다.

PWA는 없어도 앱이 돌지만 **인증은 없으면 앱이 돌지 않는다.** 따라서 도메인 확보와 Let's Encrypt 인증서 발급은 PWA 완성의 선행 조건이 아니라 **배포 자체의 선행 조건**이며, 배포 일정(10월 중순)의 가장 앞에 둔다. 상세는 LOG-15.

### 12.1 트리거

### 12.2 잡 구성

| 잡 | 실행 조건 | 내용 |
|---|---|---|
| `changes` | 항상 | `dorny/paths-filter`로 변경 경로를 판정해 `backend` / `frontend` 불리언을 출력한다 |
| `backend` | `changes.outputs.backend == 'true'` | `postgres:16` 서비스 컨테이너를 띄우고 `./gradlew test --no-daemon` 실행. JDK 21(Temurin), `gradle/actions/setup-gradle` 캐시 |
| `frontend` | `changes.outputs.frontend == 'true'` | Node 24, `npm ci` → `npm run lint` → `npm run build` |

### 12.3 paths-filter를 두는 이유

`backend/**`만 바뀐 PR에서 프론트 잡을, `frontend/**`만 바뀐 PR에서 백엔드 잡을 돌리는 것은 낭비이며 실패 지점만 늘린다. `changes` 잡이 경로를 판정하고 두 잡은 각자의 조건에서만 실행된다. 문서만 바뀐 PR에서는 두 잡 모두 건너뛴다.

`backend` 잡의 DB 접속 정보(`DB_URL` / `DB_USERNAME` / `DB_PASSWORD`)는 `application.yaml`의 기본값과 동일하게 두어(4장, 커밋 `84181f4`) 워크플로에 별도 시크릿 없이 통과하도록 하였다. 로컬 개발용 값이므로 공개되어도 무방하다.

### 12.4 JS→TS 전환의 CI 영향

`frontend` 잡이 `oxlint`·`vite`·`tsc`를 직접 부르지 않고 `npm run lint` / `npm run build`만 호출하므로, 스크립트 내용(9.2, 9.3)을 바꾸는 것만으로 워크플로 수정 없이 전환이 반영되었다. 로컬에서 `npm ci` → `npm run lint` → `npm run build`를 실행해 CI와 동일 절차가 통과함을 확인하였다.

문서 상단에 CI 배지를 두어 `main`의 최신 빌드 상태가 저장소 첫 화면에서 보이도록 하였다. 배지는 Actions 워크플로 실행 페이지로 연결된다.

### 13.2 실행 섹션

| 순서 | 내용 |
|---|---|
| 0. 환경변수 | `.env.example` → `.env` 복사. `DB_*` 오버라이드가 필요한 경우와 불필요한 경우를 구분해 안내 |

| 2. 백엔드 실행 | `./gradlew bootRun`, `/actuator/health`의 `db.status: UP` 확인 |

## 14. 유의 사항

- **Docker Desktop을 먼저 실행**해야 `docker` 명령이 동작한다. 미실행 시 `cannot connect to the Docker daemon` 오류가 발생한다
