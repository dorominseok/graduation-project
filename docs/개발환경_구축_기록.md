| IDE | IntelliJ IDEA 2026.2.0.1 | |

| Spring Boot | 4.1.0 | |

이 표는 11월 AWS EC2 배포 시 서버 환경을 맞추는 기준이 된다. 로컬과 서버의 런타임 버전이 어긋나 배포 직전에 문제가 드러나는 상황을 방지하기 위해 명시적으로 고정한다.

### 1.2 WSL2 설정

Windows용 Docker Desktop이 WSL2 기반으로 동작하므로 선행 설치가 필요하다.

```powershell
wsl --install --no-distribution
```

`--no-distribution` 옵션을 사용해 Ubuntu 등 배포판 없이 WSL2 기반만 설치하였다. 본 프로젝트에서 리눅스 셸을 직접 사용할 일이 없으므로 불필요한 구성 요소를 배제한 것이다.

### 1.3 PowerShell 인코딩

한국어 Windows의 PowerShell 기본 코드 페이지(949)와 Git의 UTF-8 출력이 충돌해 한글 파일명이 깨진다. 세션마다 아래를 적용한다.

```powershell
chcp 65001
```

파일 자체는 손상되지 않으며 출력만 깨지는 문제이다. 항구적 해결이 필요하면 Windows Terminal 또는 PowerShell 7로 전환한다.

## 2. 빌드 도구 선택 — Gradle

### 2.1 결정

Gradle(Groovy DSL)을 채택하였다.

### 2.2 근거

| 항목 | 판단 |
|---|---|
| 참고 자료 | Spring Initializr 및 공식 문서 기본값이 Gradle이다. 문제 해결 시 참조할 예제를 그대로 적용할 수 있다 |
| 빌드 속도 | 증분 빌드가 빨라 9~10월 반복 실행 구간에서 체감 이점이 있다 |
| CI 구성 | `gradle/actions/setup-gradle` 액션으로 캐시 설정이 간결하다 |

Maven은 XML 기반이라 구조가 명시적이고 초심자 가독성이 낫다는 장점이 있으나, 그 이점은 주로 팀 협업 상황에서 유효하다. 개인 개발 조건에서는 위 세 항목의 비중이 더 크다고 판단하였다.

### 2.3 Kotlin DSL 배제

`build.gradle.kts` 대신 `build.gradle`(Groovy)을 선택하였다. Kotlin DSL은 IDE 자동완성 품질이 우수하나, Kotlin 문법을 모르는 상태에서는 빌드 오류 메시지 해석이 어렵고 검색 가능한 예제가 적다.

## 3. 저장소 구조

### 3.1 모노레포 채택

백엔드·프론트엔드·문서를 단일 저장소에 둔다.

```
graduation-project/
├─ backend/            # Spring Boot
├─ frontend/           # React (Vite, PWA)
├─ docs/               # 설계 문서
├─ .github/workflows/  # CI
├─ docker-compose.yml
├─ .env                # 로컬 전용 (gitignore)
├─ .env.example        # 공유용 견본
├─ .gitignore
└─ README.md
```

**근거**
- CI 워크플로우를 하나로 관리할 수 있다
- 설계 문서가 코드와 같은 저장소에 있어 변경 이력이 커밋 로그로 남는다. 「설계 변경 로그」를 별도 관리하는 본 프로젝트의 성격과 부합한다
- 코드 수정 시 관련 문서를 같은 커밋에서 갱신하는 습관이 유도된다
- 저장소가 백업 역할을 겸한다

### 3.2 문서 포함 범위

`docs/`에 포함한 것은 **프로젝트 산출물**로 한정하였다.

| 포함 | 제외 |
|---|---|
| 기능명세서 | 새대화 템플릿 |
| 유스케이스 정의서 | |
| 운동기록 방식 설계서 | |
| 운동 분석로직 설계서 | |
| 설계 변경 로그 | |

새대화 템플릿은 개발 과정에서 사용하는 작업 도구이지 산출물이 아니므로 제외하였다.

`.md` 파일은 Git이 줄 단위 변경을 추적하므로 이력 관리의 이점이 온전히 발휘된다. `.docx` 계획서는 바이너리라 변경 내용이 표시되지 않아 백업 목적 외의 실익이 적다.

### 3.3 Git 설정

기본 브랜치를 `main`으로 통일하였다(GitHub 기본값과 일치).

```powershell
git branch -M main
```

한글 파일명 출력 문제 대응:

```powershell
git config --global core.quotepath false
```

> **주의**: 문서 파일명의 한글은 허용하되, **코드 파일명은 영문으로 통일**한다. EC2(Linux) 배포 및 CI 환경에서 인코딩 문제가 발생할 수 있다.

### 3.4 저장소 공개 설정

Public으로 생성하였다. 이에 따라 **API 키·비밀번호를 코드에 직접 기재하지 않는 원칙**을 반드시 지켜야 한다. 8월 4주 LLM API 연동 실험 시 특히 유의한다.

## 4. 환경변수 분리 — .env / .env.example

### 4.1 구조

| 파일 | 내용 | Git 추적 |
|---|---|---|
| `.env` | 실제 접속 정보 | 제외 (gitignore) |
| `.env.example` | 항목명만, 값은 공란 | 포함 |

### 4.2 `.env` 항목

```
POSTGRES_DB=fitness
POSTGRES_USER=fitness
POSTGRES_PASSWORD=(로컬 개발용)

```

### 4.3 `.env.example`을 두는 이유

`.env`가 Git에서 제외되면 저장소만 받은 환경에서는 **해당 파일이 필요하다는 사실 자체를 알 수 없다.** 값을 비운 견본을 공개해 필요한 항목을 알린다.

본 프로젝트에서 이 파일이 실제로 쓰이는 시점은 두 가지이다.
- 11월 EC2 배포 시 서버에서 `.env`를 새로 작성할 때
- PC 교체·포맷 후 환경을 재구성할 때

## 5. PostgreSQL Docker 구성

### 5.1 DB만 컨테이너화 — 애플리케이션은 제외

개발 단계에서는 **PostgreSQL만 컨테이너로 띄우고 Spring Boot는 IDE에서 직접 실행**한다.

**근거**

| 항목 | DB만 컨테이너 (채택) | 애플리케이션까지 컨테이너 |
|---|---|---|
| 코드 수정 후 반영 | IDE 재실행, 수 초 | 이미지 재빌드, 수십 초~수 분 |
| 디버깅 | IDE 브레이크포인트 직접 사용 | 원격 디버깅 설정 필요 |
| 장애 원인 후보 | 코드 / DB 컨테이너 | + 컨테이너 간 네트워크, 이미지 빌드 시점, 환경변수 전달 |
| 현 시점 이점 | — | 없음 (로컬 단독 개발) |

컨테이너화의 본질적 이점은 실행 환경의 재현성이며, 이는 배포 시점에 발생한다. 개인이 단일 PC에서 개발하는 현 단계에서는 비용만 발생하고 이점은 11월에야 실현된다.

애플리케이션 컨테이너화는 11월 배포 준비 시 `Dockerfile` 추가와 compose 서비스 확장으로 진행한다. 현재 구성을 확장하는 형태이므로 이번에 익힌 내용이 그대로 이어진다.

### 5.2 docker-compose.yml 주요 설정

| 항목 | 값 | 의도 |
|---|---|---|
| `image` | `postgres:16` | 버전 고정 |
| `restart` | `unless-stopped` | 재부팅 후 자동 기동 |
| `TZ` | `Asia/Seoul` | **`performed_on` 일자 귀속에 직접 영향** |
| `ports` | `5432:5432` | PostgreSQL 표준 포트 |
| `volumes` | `postgres-data` | 컨테이너 삭제 시 데이터 유실 방지 |
| `healthcheck` | `pg_isready` | 접속 가능 상태 확인 |

`TZ` 설정은 단순 표시 문제가 아니다. 「운동기록 방식 설계서」 2.1에서 `performed_on`을 "자정을 넘겨 운동한 경우에도 시작 일자로 귀속"한다고 정하였으므로, DB 시간대가 어긋나면 분석 집계의 기준 일자가 틀어진다.

`volumes` 설정이 없으면 컨테이너를 삭제할 때 데이터가 함께 소멸한다.

### 5.3 상시 사용 명령

```powershell
docker compose up -d          # 기동
docker compose down           # 중지 (데이터 유지)
docker compose ps             # 상태 확인
docker compose logs postgres  # 로그 확인
```

> `docker compose down -v` 는 볼륨까지 삭제하여 **데이터가 전부 소멸**한다. 스키마를 초기화하고 재구축할 때만 사용한다.

### 5.4 검증

```powershell
docker exec -it fitness-postgres psql -U fitness -d fitness
```

접속 후 `\dt`로 테이블 부재를 확인하였다(4단계에서 생성 예정).

## 6. Spring Boot 구성

### 6.1 프로젝트 메타데이터

| 항목 | 값 |
|---|---|
| Group | `com.fitness` |
| Artifact | `backend` |
| Package | `com.fitness.backend` |
| Packaging | Jar |
| Configuration | **YAML** |
| Java | 21 |

Configuration을 Properties가 아닌 YAML로 선택한 것은, 프로필별 설정(local/prod)을 계층 구조로 한 파일에 표현할 수 있어 11월 배포 시 환경 분리가 용이하기 때문이다.

### 6.2 의존성

| 의존성 | 용도 |
|---|---|
| Spring Web | REST API |
| Spring Data JPA | ORM |
| PostgreSQL Driver | DB 드라이버 |
| Validation | 입력값 검증 |
| **Flyway Migration** | 스키마 버전 관리 |
| Lombok | 보일러플레이트 축소 |
| Spring Boot Actuator | 상태 점검 엔드포인트 |

### 6.3 Flyway 채택 — ddl-auto는 validate

**스키마는 Flyway가 전담하고, Hibernate는 검증만 수행한다.**

```yaml
jpa:
  hibernate:
    ddl-auto: validate
```

**근거**
- `ddl-auto: update`는 컬럼 삭제·타입 변경을 반영하지 못하며, 운영 중 예측 불가능한 스키마 변형을 일으킨다
- 스키마 변경이 SQL 파일로 남아 이력이 추적된다. 「설계 변경 로그」를 운영하는 본 프로젝트의 방향과 일치한다
- 11월 EC2 배포 시 마이그레이션이 자동 적용된다
- Hibernate가 테이블을 임의 생성하면 Flyway 관리 스키마와 충돌한다

### 6.4 open-in-view 비활성화

```yaml
jpa:
  open-in-view: false
```

Spring Boot 기본값은 `true`이나, DB 커넥션을 HTTP 요청 종료 시점까지 점유하여 커넥션 풀 고갈을 유발한다. 기동 시 경고 로그도 출력된다. 비활성화가 표준 권장 사항이다.

### 6.5 검증 — /actuator/health

```
GET http://localhost:8080/actuator/health
```

응답에서 다음을 확인하였다.

```json
"db": { "details": { "database": "PostgreSQL" }, "status": "UP" }
```

`db.status = UP`은 Spring Boot가 Docker 컨테이너의 PostgreSQL에 실제로 연결되었음을 의미한다. 3단계의 완료 조건으로 설정한 항목이다.

구현을 단계별로 끊고 각 단계마다 눈으로 확인 가능한 조건을 두었다. 여러 요소를 동시에 구성한 뒤 통합하면 장애 발생 시 원인 지점을 특정하기 어렵기 때문이다.

| 단계 | 완료 조건 | 결과 |
|---|---|---|
| 0 | JDK/Node/Git/Docker 버전 출력 확인 | ✅ |
| 1 | GitHub에 저장소 구조·문서 반영 | ✅ |
| 2 | `psql` 접속 및 컨테이너 재기동 후 데이터 유지 | ✅ |

## 8. DB 스키마 (4단계)

### 8.1 users 테이블 포함

당초 `exercises` / `workout_sessions` / `workout_sets` 3개 테이블만 생성할 계획이었으나, `workout_sessions.user_id`가 `users`를 참조하므로 FK 성립을 위해 **최소 형태의 `users` 테이블이 함께 필요**하였다.

```
users (id, email, password_hash, nickname, created_at, updated_at)
```

인증 기능 구현은 9월이지만, 스키마상의 자리는 이번 마이그레이션에 포함하였다.

### 8.2 구현 결정

| 항목 | 결정 | 근거 |
|---|---|---|
| 파일 | `backend/src/main/resources/db/migration/V1__init.sql` | Flyway 기본 탐색 경로 |
| ENUM | PostgreSQL 네이티브 타입 대신 `VARCHAR + CHECK` | JPA `@Enumerated(STRING)` 매핑이 단순하고, 값 추가 시 마이그레이션이 가볍다 |
| 인덱스 | 설계서 2.2의 3개 생성 | 최근 4주 조회 / 세션 상세 / 종목별 1RM 추이 |
| `ON DELETE CASCADE` | 세션→세트에만 적용 | 세션 삭제 시 세트가 고아로 남는 것을 방지. 종목 삭제로 기록이 소실되면 안 되므로 `exercise_id`에는 미적용 |
| `routine_id` FK | **보류** | `routines` 테이블 미생성. 컬럼만 확보하고 10월에 제약 추가 |
| `set_no` UNIQUE | **미적용** | 한 세션에서 같은 종목을 나누어 수행하는 경우가 실제로 존재하므로, 제약을 걸면 정상 사용을 방해한다 |
| 보류 컬럼 | `duration_override_sec` 등 확보 | 설계서 4.4 방침에 따라 UI 미구현 항목도 컬럼은 미리 확보 |

`body_part` 등 코드값은 영문 대문자로 저장하고 화면 표시 시 한글로 변환한다. Java enum과 직접 매핑되며, DB에 표시 문자열이 섞이는 것을 피한다.

### 8.3 exercises.equipment 채택

검토 중이던 `equipment` 컬럼을 **추가하기로 결정**하였다. 상세 근거는 「설계 변경 로그」 LOG-08에 기록하였다.

요지는 두 가지이다.
- 루틴 후보정(기능명세 2.4)의 대체 후보를 `body_part`만으로 고르면 교체 사유를 해소하지 못한다
- 비용이 비대칭이다. 지금은 컬럼 1개와 정제 시 매핑 1개이나, 나중에는 800여 종목 재검토가 필요하다

### 8.4 검증 결과

테이블 생성만으로는 완료로 보지 않고, 설계서 2.2의 부위별 세트 집계 쿼리가 실제로 동작하는지 확인하였다.

더미 데이터 구성:
- 벤치프레스 3세트 (그중 1세트는 `is_warmup = true`)
- 랫풀다운 1세트, 스쿼트 1세트
- `status = DRAFT`인 별도 세션에 벤치프레스 1세트

집계 결과:

```
 body_part | total_sets
-----------+------------
 BACK      |          1
 CHEST     |          2
 LEGS      |          1
```

벤치프레스 세트는 총 4개였으나 CHEST가 2로 집계되었다. 워밍업 세트(LOG-02)와 DRAFT 세션(설계서 5.1)이 각각 제외된 결과이며, **두 제외 규칙이 스키마 수준에서 실제로 동작함**을 확인하였다.

이 검증을 환경 구축 단계에서 수행한 이유는, 구조 결함은 데이터가 축적된 뒤에는 되돌릴 수 없기 때문이다(「운동기록 방식 설계서」 0.1). 검증 후 더미 데이터는 `TRUNCATE ... RESTART IDENTITY CASCADE`로 제거하였다.

## 9. 유의 사항

- **Docker Desktop을 먼저 실행**해야 `docker` 명령이 동작한다. 미실행 시 `cannot connect to the Docker daemon` 오류가 발생한다
- PowerShell 신규 세션마다 `cd` 및 `chcp 65001`이 필요하다
- 저장소가 Public이므로 **비밀 정보를 코드에 기재하지 않는다**. 8월 4주 LLM API 실험 시 반드시 `.env` 경유
- IntelliJ Ultimate 30일 평가판 사용 중. 만료 전 학생 라이선스 신청 또는 Community 전환 필요
