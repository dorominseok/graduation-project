# 유스케이스 정의서
### 운동 습관 분석 기반 맞춤 루틴 추천 헬스 웹앱(PWA)

> 졸업작품 계획서 3장(시스템 요구사항)용 문서
> 우선순위: **기본 기능** / **핵심 기능** / **추가 기능**

---

## 1. 액터(Actor) 정의

| 액터 | 구분 | 설명 |
|---|---|---|
| **사용자** | 주 액터 | 운동을 기록하고 분석 결과와 추천 루틴을 받으며, 그룹에 참여하는 이용자. 그룹을 생성한 사용자도 동일 액터로 본다 |
| **LLM API** | 부 액터 (외부) | 선정된 후보 운동을 바탕으로 루틴을 구성하는 외부 서비스 |
| **FCM** | 부 액터 (외부) | 푸시 알림 발송을 담당하는 외부 서비스 (추가 기능) |

> 분석 모듈·추천 엔진·스케줄러는 시스템 내부 구성 요소이므로 액터로 두지 않으며, 시스템이 자동으로 수행하는 흐름으로 표기한다.

## 3. 주요 유스케이스 상세 명세

> 2026-09-12 LOG-19로 전수 상세화 — 기존 7개(UC-02-01·06, UC-03-01·03·05, UC-05-02, UC-04-01)에 나머지 16개를 더했고, 이후 LOG-20이 UC-01-04(회원 탈퇴)를, LOG-21이 UC-01-05(비밀번호 변경)를 신설했다. 현재 **활성 유스케이스 24개 전부** 기본/대체/예외 흐름을 갖췄다(제외된 UC-04-01은 참고용으로 보존). 배치 순서는 2장 목록과 같은 ID 순으로 정렬한다.

### UC-01-01 회원가입

| 항목 | 내용 |
|---|---|
| **액터** | 사용자 |
| **개요** | 이메일·비밀번호·닉네임으로 계정을 생성하고, 가입과 동시에 로그인 상태로 전환한다 |
| **사전 조건** | 없음 (비로그인 상태에서 진입) |
| **사후 조건** | 계정이 생성되고, 액세스 토큰과 리프레시 쿠키가 발급되어 즉시 로그인 상태가 됨 |

**기본 흐름**
1. 사용자가 회원가입 화면에서 이메일·비밀번호·닉네임을 입력한다
2. 시스템이 이메일 형식·중복, 비밀번호 길이(8~72자), 닉네임 길이(1~50자)를 검증한다
3. 시스템이 비밀번호를 BCrypt로 해시하여 저장한다
4. 시스템이 액세스 토큰(JWT)과 리프레시 토큰을 발급한다
5. 리프레시 토큰은 `HttpOnly·Secure` 쿠키로, 액세스 토큰은 응답 본문으로 내려간다
6. 사용자는 별도 로그인 없이 홈 화면으로 이동한다

**예외 흐름**
- 2a. 이메일 중복 → `409 EMAIL_ALREADY_EXISTS`, 로그인 화면으로 안내
- 2b. 형식 오류 → `400 VALIDATION_ERROR`, 필드별 오류 메시지 표시

> API 명세서 4.1 참조. 가입 직후 별도 로그인 왕복이 없도록 설계했다.

### UC-01-02 로그인 / 로그아웃

| 항목 | 내용 |
|---|---|
| **액터** | 사용자 |
| **개요** | 이메일·비밀번호로 인증해 토큰을 발급받거나, 리프레시 토큰을 폐기해 세션을 종료한다 |
| **사전 조건** | (로그인) 가입된 계정 보유 / (로그아웃) 로그인 상태 |
| **사후 조건** | (로그인) 액세스 토큰·리프레시 쿠키 발급 / (로그아웃) 리프레시 토큰이 폐기(`revoked_at`)되고 쿠키 만료 |

**기본 흐름 (로그인)**
1. 사용자가 이메일·비밀번호를 입력한다
2. 시스템이 자격 증명을 검증한다
3. 시스템이 액세스 토큰과 리프레시 쿠키를 발급한다

**기본 흐름 (로그아웃)**
1. 사용자가 로그아웃을 선택한다
2. 시스템이 리프레시 토큰에 폐기 표시를 남기고 쿠키를 만료시킨다(`Max-Age=0`)

**대체 흐름**
- 액세스 토큰 만료(30분) 시 클라이언트가 자동으로 `POST /auth/refresh`를 호출해 재발급받는다 — 사용자에게 보이지 않는 흐름

**예외 흐름**
- 1a. 이메일 없음 / 비밀번호 불일치 → `401 INVALID_CREDENTIALS` (계정 존재 여부를 구분하지 않음)
- 재발급 중 폐기된 토큰 재사용 감지 → 유예 창(30초) 밖이면 전체 리프레시 토큰 폐기, 재로그인 필요(LOG-16)

> API 명세서 4.2~4.4, LOG-16(유예 창) 참조.

### UC-01-03 프로필 설정 (훈련 목표)

| 항목 | 내용 |
|---|---|
| **액터** | 사용자 |
| **개요** | 훈련 목표 1종을 설정·조회·수정한다 |
| **사전 조건** | 로그인 상태 |
| **사후 조건** | 프로필의 `goal` 값이 갱신되어 이후 조회와 (10월) 루틴 생성에 사용됨 |

**기본 흐름**
1. 사용자가 프로필 화면에서 현재 훈련 목표를 조회한다(`GET /users/me`)
2. 사용자가 훈련 목표를 선택해 저장한다(`PATCH /users/me`)
3. 시스템이 포함된 필드만 갱신하고 전체 프로필을 반환한다

**대체 흐름**
- `goal`을 `null`로 보내면 미설정 상태로 되돌린다

> 계획 시점엔 키·체중·경력·목표 4종이었으나 근력 판정이 이 값들을 참조하지 않아 목표 1종으로 축소했다(LOG-11, LOG-14). 현재는 저장만 하고 실제 사용처는 10월 루틴 추천(「루틴생성_로직_설계서」, 미작성)에서 확정한다.

### UC-01-04 회원 탈퇴

| 항목 | 내용 |
|---|---|
| **액터** | 사용자 |
| **개요** | 계정과 그에 딸린 모든 기록을 되돌릴 수 없게 삭제한다 |
| **사전 조건** | 로그인 상태 |
| **사후 조건** | 계정이 삭제되고, 리프레시 쿠키가 만료되며, 남은 액세스 토큰도 이후 모든 요청에서 `401`이 됨 |

**기본 흐름**
1. 사용자가 계정 설정에서 "회원 탈퇴"를 선택한다
2. 시스템이 확인 다이얼로그를 표시하고, 현재 비밀번호 재입력을 요구한다
3. 사용자가 비밀번호를 입력하고 확정한다
4. 시스템이 비밀번호를 검증한 뒤 `users` 행을 삭제한다 — 리프레시 토큰·즐겨찾기·세션·세트가 `ON DELETE CASCADE`로 함께 삭제됨
5. 시스템이 리프레시 쿠키를 만료시킨다

**예외 흐름**
- 3a. 비밀번호 불일치 → `401 INVALID_CREDENTIALS`
- 3b. 비밀번호 누락 → `400 VALIDATION_ERROR`

> API 명세서 4.7 참조. **소프트 삭제를 쓰지 않는다** — 목적이 개인정보를 남기지 않는 것이므로 실제로 행을 지운다. 종목(`exercises`)은 사용자 소유 데이터가 아니라 영향받지 않는다. 목업 계정 화면의 삭제 버튼(대조 평가 C-23, 미연결)이 이 유스케이스로 연결될 예정이다.
>
> **LOG-20에서 신설**: 목업(8월, 계정 삭제 버튼) → 대조 평가 C-23("연결 안 됨") → API 명세서 4.7(LOG-13) → 구현, 순서로 이미 계보가 있던 기능이다. 유스케이스 정의서만 이 계보를 못 따라갔던 것이라 이번에 채운다.

### UC-01-05 비밀번호 변경

| 항목 | 내용 |
|---|---|
| **액터** | 사용자 |
| **개요** | 현재 비밀번호를 확인한 뒤 새 비밀번호로 바꾼다 |
| **사전 조건** | 로그인 상태 / 현재 비밀번호를 알고 있음 |
| **사후 조건** | 비밀번호가 갱신되고, 해당 사용자의 리프레시 토큰이 전부 폐기되어 재로그인이 필요함 |

**기본 흐름**
1. 사용자가 계정 설정에서 "비밀번호 변경"을 선택한다
2. 사용자가 현재 비밀번호와 새 비밀번호를 입력한다
3. 시스템이 현재 비밀번호를 검증하고 새 비밀번호 형식(8~72자)을 확인한다
4. 시스템이 새 비밀번호를 BCrypt로 해시해 저장한다
5. 시스템이 그 사용자의 리프레시 토큰을 전부 폐기하고 쿠키를 만료시킨다
6. 사용자는 새 비밀번호로 다시 로그인한다

**예외 흐름**
- 3a. 현재 비밀번호 불일치 → `401 INVALID_CREDENTIALS`
- 3b. 새 비밀번호가 형식에 맞지 않거나 현재와 동일 → `400 VALIDATION_ERROR`

> API 명세서 4.8 참조. **5단계에서 세션을 전부 끊는 이유**: 비밀번호를 바꾸는 동기 중 하나가 "내 계정이 털린 것 같다"인데, 바꿔도 기존 리프레시 토큰이 살아 있으면 침입자가 그대로 남는다.
>
> **비밀번호를 잊어버린 경우(재설정)는 이 유스케이스가 아니다.** 그 경로는 아직 없으며 d1(배포 준비) 이후로 유예했다 — 재설정 링크를 보낼 HTTPS 도메인이 그때 생기기 때문이다(LOG-21). 그 전까지는 운영으로 대응한다.

### UC-02-01 운동 세션 기록 ⭐

| 항목 | 내용 |
|---|---|
| **유스케이스 ID** | UC-02-01 |
| **명칭** | 운동 세션 기록 |
| **액터** | 사용자 |
| **개요** | 운동을 수행하며 종목별 세트를 기록한다. 분석·추천의 원천 데이터를 생성하는 유스케이스이다 |
| **사전 조건** | 로그인 상태 |
| **사후 조건** | 완료된 세션과 세트 기록이 저장되고, 운동 시간이 산출됨 (뱃지 판정은 LOG-18로 제외) |

**기본 흐름**
1. 사용자가 운동 기록을 시작한다 (홈 화면 또는 추천 루틴 화면에서 진입)
2. 시스템이 진행 중인 세션을 생성한다
3. 사용자가 운동 종목을 선택한다
4. 시스템이 해당 종목의 직전 수행 기록을 세트 행에 자동으로 채운다
5. 사용자가 중량·횟수를 확인·수정하고 완료 체크한다
6. 시스템이 체크된 세트를 저장하고 저장 시각을 함께 기록한다
7. 3~6을 반복한다
8. 사용자가 운동 종료를 선택한다
9. 시스템이 세션을 완료 처리하고, 세트 저장 시각으로부터 총 운동 시간을 산출한다

> ~~10. 시스템이 뱃지 달성 여부를 판정한다 (UC-04-01)~~ — 뱃지 시스템 자체가 범위에서 제외되어(LOG-18) 이 단계는 없다.

**대체 흐름**
- 1a. 추천 루틴에서 진입한 경우 → 루틴의 종목과 세트 수만큼 행이 미리 표시된다. 표시된 행은 계획이며, 완료 체크한 세트만 저장된다
- 5a. 워밍업 세트인 경우 → 사용자가 워밍업으로 표시하며, 해당 세트는 볼륨 집계에서 제외된다
- 5b. 맨몸운동·시간 기반 종목인 경우 → 종목의 측정 유형에 따라 입력 항목이 달라진다

**예외 흐름**
- 8a. 사용자가 종료하지 않고 앱을 벗어난 경우 → 세션이 진행 중 상태로 유지되며, 재진입 시 "이어서 기록 / 종료"를 선택하게 한다
- 8b. 진행 중 상태로 자정이 지난 경우 → 마지막 세트 시각을 기준으로 자동 완료 처리한다
- 6a. 저장 실패(네트워크) → 입력값을 화면에 유지하고 재시도를 안내한다

### UC-02-02 운동 기록 수정 / 삭제

| 항목 | 내용 |
|---|---|
| **액터** | 사용자 |
| **개요** | 저장된 세션·세트의 메모·날짜·시간을 수정하거나, 세션·세트 단위로 삭제한다 |
| **사전 조건** | 로그인 상태 / 본인 소유의 세션·세트 존재 |
| **사후 조건** | 수정·삭제 내용이 반영됨. 분석·통계는 온디맨드 재집계라 별도 처리 없이 다음 조회부터 자동 반영됨 |

**기본 흐름 (세션 수정)**
1. 사용자가 히스토리에서 세션을 선택한다
2. 메모, (`BACKFILL` 세션이면) 날짜, 운동 시간 보정값을 수정한다
3. 시스템이 부분 수정을 반영한다(`PATCH /workout-sessions/{id}`)

**기본 흐름 (세트 수정 / 삭제)**
1. 사용자가 세션 상세에서 특정 세트를 수정하거나 삭제한다
2. `LIVE` 세션이면 시스템이 운동 시간을 재산출한다

**대체 흐름**
- 세션을 삭제하면 세트도 함께 삭제된다(`ON DELETE CASCADE`)
- 세트를 모두 삭제해도 세션 자체는 남는다(히스토리에 `setCount: 0`으로 표시)

**예외 흐름**
- `LIVE` 세션의 `performedOn`(수행 날짜) 변경 시도 → `400` (`LIVE`는 날짜 변경 불가, `BACKFILL`만 허용)
- 삭제된 세트의 `setNo`는 재부여하지 않는다 — 화면은 서버 `setNo`가 아니라 배열 순번(1..N)으로 표시해 구멍을 감춘다

> API 명세서 6.9~6.12 참조. 분석이 온디맨드 집계이므로 수정·삭제 시 별도 재계산 배치가 필요 없다.

### UC-02-04 통계 조회 (부위별 볼륨, 추정 1RM 추이, 세트별 강도)

| 항목 | 내용 |
|---|---|
| **액터** | 사용자 |
| **개요** | 종목 하나의 추정 1RM 추이(kg, 시간축)와 특정 세션의 세트별 강도(%, 그날 스냅샷)를 조회한다 |
| **사전 조건** | 로그인 상태 / 해당 종목의 `DONE` 기록 존재 |
| **사후 조건** | 그래프·수치가 표시됨 |

**기본 흐름 (1RM 추이)**
1. 사용자가 종목을 선택해 통계 화면에 진입한다
2. 시스템이 `reps ≤ 12`인 세트에서 Epley 공식으로 날짜별 추정 1RM을 산출한다(그날 최댓값)

**기본 흐름 (세션 강도)**
1. 사용자가 완료한 세션을 선택한다
2. 시스템이 그날 종목별 추정 1RM 대비 각 세트 중량의 비율(%)을 계산해 표시한다

**예외 흐름**
- `measureType`이 `WEIGHT_REPS`가 아닌 종목으로 1RM 추이 요청 → `400 VALIDATION_ERROR`
- 추정 1RM을 낼 수 없는 세트(맨몸·시간 종목)는 `intensityPct`가 `null`로 표시됨

> API 명세서 7.1·7.2 참조.

### UC-03-01 운동 습관 약점·불균형 분석

| 항목 | 내용 |
|---|---|
| **액터** | 시스템 자동 |
| **개요** | 사용자의 운동 기록을 집계해 부위별 부족·과다와 밀기/당기기·상하체 불균형을 판별한다 |
| **사전 조건** | 분석 대상 기간(최근 4주)의 운동 기록 존재 |
| **사후 조건** | 부족·불균형 판정 결과가 산출되어 추천의 근거 및 조회 화면에 사용됨 |

**기본 흐름**
1. 최근 4주의 완료된 세션에서 본세트 기록을 조회한다 (진행 중 세션·워밍업 세트 제외)
2. 각 기록을 주동근 기준으로 부위별 분류한다 (가슴/등/하체/어깨/팔/코어)
3. 부위별 주간 평균 세트 수를 집계한다
4. 판정 기준에 따라 상태를 분류한다
   - 주 4세트 미만 → 부족
   - 주 4세트 이상 10세트 미만 → 권장 이하
   - 주 10세트 이상 20세트 이하 → 최적
   - 주 20세트 초과 → 과다
5. 밀기·당기기 및 상·하체 볼륨 비율을 계산해, 한쪽이 2배를 초과하면 불균형으로 판정한다
6. 판정 결과를 반환한다

**예외 흐름**
- 5a. 비교하는 양쪽 세트가 모두 0인 경우 → 불균형이 아니라 `INSUFFICIENT_DATA`(데이터 부족)로 판정한다. 기록이 없는 것과 균형이 잡힌 것을 구분하기 위함이다
- 5b. 한쪽만 0인 경우 → `IMBALANCED`로 판정하되 비율 수치는 `null`(계산 불가)로 반환한다

> LOG-20에서 보강: 「운동 분석 로직 설계서」에도 없던 엣지 케이스다 — 어떤 상위 문서도 미리 정하지 않았고, `BalanceEvaluation.of`를 구현하며 실제로 마주쳐 처리한 뒤 이번에 문서로 역반영했다(LOG-07·LOG-13과 같은 패턴).

### UC-03-02 약점 분석 결과 조회

| 항목 | 내용 |
|---|---|
| **액터** | 사용자 |
| **개요** | UC-03-01이 산출한 부위별 볼륨 판정과 밀기/당기기·상하체 균형 판정을 화면에서 조회한다 |
| **사전 조건** | 로그인 상태 |
| **사후 조건** | 상위 6종/하위 9종 2계층 판정과 균형 판정이 표시됨 |

**기본 흐름**
1. 사용자가 분석 결과 화면에 진입한다
2. 시스템이 최근 4주 부위별 볼륨 판정(상위 6종은 요약 배지, 하위 9종은 4단계 판정)을 조회한다(`GET /analysis/muscle-volume`)
3. 시스템이 밀기/당기기·상체/하체 균형 판정(비율·불균형 여부)을 조회한다(`GET /analysis/balance`)
4. 화면은 값을 그대로 표시할 뿐 합산·구간 분류·배지 계산을 하지 않는다(서버가 완성)

**예외 흐름**
- 최근 4주 완료 세션이 임계(기본 6회) 미만이면 `confidence.level = LOW`와 함께 "판정 신뢰도 낮음" 안내를 함께 표시한다
- 균형 판정에서 작은 쪽이 0이면 `ratio`는 `null`이며 화면은 "비율 계산 불가"로 표기한다

> API 명세서 8.1~8.3 참조. 판정 기준(경계값·배지 우선순위)은 서버가 단위 테스트로 고정한 것이라 화면은 재계산하지 않는다.

### UC-03-03 오늘의 루틴 추천 요청 ⭐

5. 시스템이 운동 종목 DB에서 해당 부위의 운동 후보를 조회한다
6. 시스템이 분석 결과와 운동 후보를 LLM API에 전달해 루틴 구성을 요청한다
7. LLM API가 오늘의 루틴(운동·세트·횟수)을 반환한다
8. 시스템이 반환된 루틴을 정량 규칙으로 검증한다 (UC-03-04)
9. 검증을 통과하면 루틴을 저장하고 사용자에게 표시한다
10. 사용자는 필요에 따라 운동을 교체하거나 세트를 조정한다 (UC-03-05)

**대체 흐름**
- 3a. 부족·불균형이 없는 경우 → 현재 균형을 유지하는 루틴을 생성한다
- 8a. 검증 실패 시 → 최대 N회까지 재생성을 시도한다
- 8b. 재시도 후에도 실패 시 → 규칙 기반 기본 루틴을 대체 제공하고 사용자에게 안내한다

**예외 흐름**
- 2a. 운동 기록이 부족한 경우 → 추천 불가 안내 및 기록 유도 화면으로 이동
- 6a. LLM API 호출 실패(네트워크·한도 초과) → 규칙 기반 기본 루틴으로 대체하고 안내

### UC-03-04 추천 루틴 품질 자동 검증

| 항목 | 내용 |
|---|---|
| **액터** | 시스템 자동 |
| **개요** | LLM이 생성한 오늘의 루틴이 정량 규칙을 만족하는지 자동으로 검사한다 |
| **사전 조건** | LLM이 루틴 후보를 반환함 (UC-03-03의 6~7단계 이후) |
| **사후 조건** | 통과 시 루틴이 저장되고, 실패 시 재생성 또는 대체 루틴으로 전환됨 |

**기본 흐름**
1. 시스템이 부위별 세트 수가 권고 범위(4단계 판정 기준) 내에 있는지 검사한다
2. 시스템이 밀기/당기기·상하체 볼륨이 한쪽으로 치우치지 않았는지 검사한다
3. 시스템이 제공한 후보 목록·세트 수 범위를 LLM이 그대로 준수했는지 검사한다
4. 전부 통과하면 루틴을 저장하고 통과 처리한다

**대체 흐름**
- 실패 시 최대 N회까지 재생성을 요청한다(N은 서버 설정값)
- N회 재생성 후에도 실패하면 규칙 기반 기본 루틴으로 대체하고 사용자에게 안내한다

> 기능명세서 2.3 참조. 검증 통과율은 검증 계획(5장)의 정량 지표로 쓰인다. 세부 규칙 임계값은 10월 「루틴생성_로직_설계서」(미작성)에서 확정한다.

```
                  │  (활동 현황 조회 05-03) (그룹 탈퇴 05-04)            │
                  │                                                    │
                  │  ┌ 추가 기능(점선) ────────────────────────┐        │
                  │  │ (알림 설정 06-01)                       │        │
                  │  │ (미운동 알림 06-02) ─ extend ▶ (약점 보완 알림 06-03)  ────── FCM
                  │  └─────────────────────────────────────────┘        │
                  │                                                    │
                  └────────────────────────────────────────────────────┘
```

**원본 계획서 그림과 달라지는 지점** — 계획서(`졸업작품_계획서.docx`)의 다이어그램은 아래 네 곳에서 원 하나가 여러 유스케이스를 묶고 있고, 회원 탈퇴는 원 자체가 없다. 작도 시 쪼갠다.

| 계획서 원본의 원 | 쪼갠 뒤 |
|---|---|
| 계정 관리 (회원가입·로그인) | UC-01-01 / UC-01-02 |
| 운동 기록 관리 (등록·수정·삭제) | UC-02-01 / UC-02-02 |
| 히스토리 · 통계 조회 | UC-02-03 / UC-02-04 |
| 그룹 생성 · 참여 · 탈퇴 | UC-05-01 / UC-05-02 / UC-05-04 |
| *(원 없음)* | UC-01-04 회원 탈퇴 **신설**(LOG-20) |
| *(원 없음)* | UC-01-05 비밀번호 변경 **신설**(LOG-21) |

**관계 표기**
- `오늘의 루틴 추천 요청(03-03)` → `약점·불균형 분석(03-01)` : **include** (항상 수행)
- `오늘의 루틴 추천 요청(03-03)` → `추천 품질 검증(03-04)` : **include** (항상 수행)
- `미운동 알림(06-02)` → `약점 보완 알림(06-03)` : **extend** (분석 결과에 부족·불균형이 있을 때만)
- 알림(UC-06)은 추가 기능이므로 점선으로 구분 표기한다
- 뱃지(UC-04)는 범위에서 제외됐으므로(LOG-18) 작도 시 그리지 않는다
- `약점·불균형 분석(03-01)`·`추천 품질 검증(03-04)`은 시스템 자동 수행이라 사용자와 직접 연결선을 긋지 않는다

> 원 24개 = 3장의 활성 명세 24개 (UC-01 5 · UC-02 6 · UC-03 6 · UC-05 4 · UC-06 3). 작도 도구는 draw.io, StarUML 중 택1.
