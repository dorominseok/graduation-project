# 유스케이스 정의서
### 운동 습관 분석 기반 맞춤 루틴 추천 헬스 웹앱(PWA)

> 졸업작품 계획서 3장(시스템 요구사항)용 문서
> 우선순위: **기본 기능** / **핵심 기능** / **추가 기능**

---

## 1. 액터(Actor) 정의

| 액터 | 구분 | 설명 |
|---|---|---|
| **사용자** | 주 액터 | 운동을 기록하고 분석 결과와 추천 루틴을 받으며, 그룹에 참여하는 이용자. 그룹을 생성한 사용자도 동일 액터로 본다 |
| **LLM API** | 부 액터 (외부) | 선정된 후보 운동을 바탕으로 루틴을 구성하는 외부 서비스 |
| **Google 인증** | 부 액터 (외부) | 구글 계정 로그인과 탈퇴 시 본인 확인을 맡는 외부 서비스(LOG-37) |
| ~~FCM~~ | ~~부 액터 (외부)~~ | 푸시 알림 발송 — **알림(UC-06) 미구현으로 제외 (LOG-45)** |

> 분석 모듈·추천 엔진·스케줄러는 시스템 내부 구성 요소이므로 액터로 두지 않으며, 시스템이 자동으로 수행하는 흐름으로 표기한다.

## 3. 주요 유스케이스 상세 명세

> 2026-09-12 LOG-19로 전수 상세화 — 기존 7개(UC-02-01·06, UC-03-01·03·05, UC-05-02, UC-04-01)에 나머지 16개를 더했고, 이후 LOG-20이 UC-01-04(회원 탈퇴)를, LOG-21이 UC-01-05(비밀번호 변경)를 신설했다. 2026-10-11 LOG-38이 UC-05-05~07을 신설해 현재 **활성 유스케이스 27개 전부** 기본/대체/예외 흐름을 갖췄다(제외된 UC-04-01은 참고용으로 보존). 같은 날 LOG-39가 기록 단위를 하루로 바꿔 UC-02-01·02·03·05·06, UC-03-01, UC-05-03·05의 흐름을 고쳤다. 2026-11-04 LOG-45가 완성된 코드와 전수 대조해 UC-01·02 전체, UC-03-01·02, UC-05-03을 고치고 UC-06(알림)을 미구현으로 제외해, **활성 유스케이스는 24개**다(제외된 UC-04-01·UC-06은 참고용으로 보존). 배치 순서는 2장 목록과 같은 ID 순으로 정렬한다.

### UC-01-01 회원가입

| 항목 | 내용 |
|---|---|
| **액터** | 사용자 |
| **개요** | 이메일·비밀번호·닉네임으로 계정을 생성하고, 가입과 동시에 로그인 상태로 전환한다 |
| **사전 조건** | 없음 (비로그인 상태에서 진입) |
| **사후 조건** | 계정이 생성되고, 액세스 토큰과 리프레시 쿠키가 발급되어 즉시 로그인 상태가 됨 |

**기본 흐름**
1. 사용자가 회원가입 화면에서 이메일·비밀번호·닉네임을 입력한다
2. 시스템이 이메일 형식·중복, 비밀번호 길이(8~72자), 닉네임 길이(1~50자)를 검증한다
3. 시스템이 비밀번호를 BCrypt로 해시하여 저장한다
4. 시스템이 액세스 토큰(JWT)과 리프레시 토큰을 발급한다
5. 리프레시 토큰은 `HttpOnly·Secure` 쿠키로, 액세스 토큰은 응답 본문으로 내려간다
6. 사용자는 별도 로그인 없이 홈 화면으로 이동한다

**대체 흐름**
- 구글 계정으로 처음 로그인하면 이 과정 없이 그 자리에서 계정이 만들어진다(UC-01-02 구글 로그인)

**예외 흐름**
- 2a. 이메일 중복 → `409 EMAIL_ALREADY_EXISTS`, 이메일 칸 아래에 오류를 표시한다
- 2b. 형식 오류 → `400 VALIDATION_ERROR`, 필드별 오류 메시지 표시

> API 명세서 4.1 참조. 가입 직후 별도 로그인 왕복이 없도록 설계했다.

### UC-01-02 로그인 / 로그아웃

| 항목 | 내용 |
|---|---|
| **액터** | 사용자, Google 인증 |
| **개요** | 이메일·비밀번호 또는 구글 계정으로 인증해 토큰을 발급받거나, 리프레시 토큰을 폐기해 세션을 종료한다 |
| **사전 조건** | (이메일 로그인) 가입된 계정 보유 / (구글 로그인) 구글 계정 보유 / (로그아웃) 로그인 상태 |
| **사후 조건** | (로그인) 액세스 토큰·리프레시 쿠키 발급 / (로그아웃) 리프레시 토큰이 폐기(`revoked_at`)되고 쿠키 만료 |

**기본 흐름 (이메일 로그인)**
1. 사용자가 이메일·비밀번호를 입력한다
2. 시스템이 자격 증명을 검증한다
3. 시스템이 액세스 토큰과 리프레시 쿠키를 발급한다

**기본 흐름 (구글 로그인)**
1. 사용자가 구글 로그인 버튼을 누르고 구글 계정을 고른다
2. 시스템이 구글이 발급한 인증 정보(ID 토큰)를 검증한다
3. 시스템이 계정을 찾는다 — ① 그 구글 계정이 묶인 계정 → ② 같은 이메일로 가입한 계정에 구글을 묶음 → ③ 둘 다 없으면 구글 이름을 닉네임으로 새로 가입
4. 시스템이 액세스 토큰과 리프레시 쿠키를 발급한다

**기본 흐름 (로그아웃)**
1. 사용자가 설정 화면에서 로그아웃을 선택한다
2. 시스템이 리프레시 토큰에 폐기 표시를 남기고 쿠키를 만료시킨다(`Max-Age=0`)

**대체 흐름**
- 액세스 토큰 만료(30분) 시 클라이언트가 자동으로 `POST /auth/refresh`를 호출해 재발급받는다 — 사용자에게 보이지 않는 흐름

**예외 흐름**
- 2a. (이메일) 이메일 없음 / 비밀번호 불일치 / 구글로만 가입해 비밀번호가 없는 계정 → 모두 같은 `401 INVALID_CREDENTIALS` (계정 존재 여부와 가입 방법을 드러내지 않음)
- 3a. (구글) 구글이 이메일 소유를 확인하지 않은 계정 → `GOOGLE_LOGIN_FAILED`. 확인되지 않은 이메일로 기존 계정에 묶으면 남의 기록을 가져갈 수 있다
- 3b. (구글) 같은 이메일의 계정에 이미 다른 구글 계정이 묶여 있음 → `409 EMAIL_ALREADY_EXISTS`
- 재발급 중 폐기된 토큰 재사용 감지 → 유예 창(30초) 밖이면 전체 리프레시 토큰 폐기, 재로그인 필요(LOG-16)

> API 명세서 4.2~4.4·4.9, LOG-16(유예 창), LOG-37(구글 로그인) 참조.

### UC-01-03 개인정보 수정 (닉네임)

| 항목 | 내용 |
|---|---|
| **액터** | 사용자 |
| **개요** | 앱에 보이는 닉네임을 바꾼다 |
| **사전 조건** | 로그인 상태 |
| **사후 조건** | 닉네임이 갱신되어 프로필·그룹 멤버 목록 등에 반영됨 |

**기본 흐름**
1. 사용자가 프로필(또는 설정)에서 "개인정보"를 연다 — 현재 닉네임이 채워져 있다(`GET /users/me`)
2. 사용자가 새 닉네임을 입력하고 저장한다(`PATCH /users/me`)
3. 시스템이 닉네임 길이(1~50자)를 확인하고 저장한 뒤 전체 프로필을 반환한다

**예외 흐름**
- 3a. 길이가 맞지 않음 → `400 VALIDATION_ERROR`, 입력 칸 아래에 오류 표시

> 이전 명칭은 「프로필 설정 (훈련 목표)」였다. 훈련 목표(`profile.goal`)는 API에 남아 있지만 루틴이 반복 범위를 측정 유형으로 정하게 되어 쓰는 곳이 없고, 화면에서 뺐다(2026-09-20). 실제 화면이 바꾸는 것은 닉네임이다(LOG-45).

### UC-01-04 회원 탈퇴

| 항목 | 내용 |
|---|---|
| **액터** | 사용자, Google 인증 |
| **개요** | 계정과 그에 딸린 모든 기록을 되돌릴 수 없게 삭제한다 |
| **사전 조건** | 로그인 상태 |
| **사후 조건** | 계정이 삭제되고, 리프레시 쿠키가 만료되며, 남은 액세스 토큰도 이후 모든 요청에서 `401`이 됨. 방장이던 그룹은 다음 멤버에게 넘어감 |

**기본 흐름**
1. 사용자가 계정 화면에서 "회원 탈퇴"를 선택한다
2. 시스템이 되돌릴 수 없다는 안내와 함께 본인 확인을 요구한다
3. 사용자가 현재 비밀번호를 입력하고 확정한다
4. 시스템이 비밀번호를 검증한다
5. 시스템이 사용자가 방장인 그룹을 남은 멤버 중 가장 먼저 들어온 사람에게 넘긴다. 남은 멤버가 없으면 그 그룹을 삭제한다(UC-05-04와 같은 규칙)
6. 시스템이 `users` 행을 삭제한다 — 리프레시 토큰·즐겨찾기·하루 기록·세트·루틴·그룹 멤버십·응원이 `ON DELETE CASCADE`로 함께 삭제됨
7. 시스템이 리프레시 쿠키를 만료시키고 로그인 화면으로 보낸다

**대체 흐름**
- 3a. 구글로만 가입해 비밀번호가 없는 계정 → 비밀번호 대신 구글 계정으로 다시 확인한다. 비밀번호와 구글을 모두 가진 계정은 어느 쪽으로든 확인할 수 있다

**예외 흐름**
- 4a. 비밀번호 불일치, 또는 이 계정에 묶이지 않은 구글 계정 → `401 INVALID_CREDENTIALS`
- 4b. 비밀번호와 구글 확인이 모두 없음 → `400 VALIDATION_ERROR`

> API 명세서 4.7 참조. **소프트 삭제를 쓰지 않는다** — 목적이 개인정보를 남기지 않는 것이므로 실제로 행을 지운다. 종목(`exercises`)은 사용자 소유 데이터가 아니라 영향받지 않는다. 구글 확인(LOG-37)과 방장 넘기기(LOG-38)는 이 명세를 처음 쓴 뒤에 들어왔다.
>
> **LOG-20에서 신설**: 목업(8월, 계정 삭제 버튼) → 대조 평가 C-23("연결 안 됨") → API 명세서 4.7(LOG-13) → 구현, 순서로 이미 계보가 있던 기능이다. 유스케이스 정의서만 이 계보를 못 따라갔던 것이라 이번에 채운다.

### UC-01-05 비밀번호 변경

| 항목 | 내용 |
|---|---|
| **액터** | 사용자 |
| **개요** | 현재 비밀번호를 확인한 뒤 새 비밀번호로 바꾼다 |
| **사전 조건** | 로그인 상태 / 이메일로 가입해 비밀번호가 있는 계정 / 현재 비밀번호를 알고 있음 |
| **사후 조건** | 비밀번호가 갱신되고, 해당 사용자의 리프레시 토큰이 전부 폐기되어 모든 기기에서 재로그인이 필요함 |

**기본 흐름**
1. 사용자가 계정 화면에서 "비밀번호 변경"을 선택한다
2. 사용자가 현재 비밀번호, 새 비밀번호, 새 비밀번호 확인을 입력한다
3. 시스템이 현재 비밀번호를 검증하고 새 비밀번호 형식(8~72자)을 확인한다
4. 시스템이 새 비밀번호를 BCrypt로 해시해 저장한다
5. 시스템이 그 사용자의 리프레시 토큰을 전부 폐기하고 쿠키를 만료시킨다
6. 사용자는 새 비밀번호로 다시 로그인한다

**대체 흐름**
- 1a. 구글로만 가입해 비밀번호가 없는 계정 → 이 메뉴를 표시하지 않는다(서버도 `400`으로 거절)

**예외 흐름**
- 2a. 새 비밀번호와 확인 값이 다름 → 화면에서 오류 표시 (서버로 보내지 않음)
- 3a. 현재 비밀번호 불일치 → `401 INVALID_CREDENTIALS`, 현재 비밀번호 칸에 오류 표시
- 3b. 새 비밀번호가 형식에 맞지 않거나 현재와 동일 → `400 VALIDATION_ERROR`

> API 명세서 4.8 참조. **5단계에서 세션을 전부 끊는 이유**: 비밀번호를 바꾸는 동기 중 하나가 "내 계정이 털린 것 같다"인데, 바꿔도 기존 리프레시 토큰이 살아 있으면 침입자가 그대로 남는다.
>
> **비밀번호를 잊어버린 경우(재설정)는 이 유스케이스가 아니다.** 그 경로는 아직 없으며 d1(배포 준비) 이후로 유예했다 — 재설정 링크를 보낼 HTTPS 도메인이 그때 생기기 때문이다(LOG-21). 그 전까지는 운영으로 대응한다.

### UC-02-01 운동 기록 ⭐

| 항목 | 내용 |
|---|---|
| **유스케이스 ID** | UC-02-01 |
| **명칭** | 운동 기록 |
| **액터** | 사용자 |
| **개요** | 운동을 수행하며 종목별 세트를 기록한다. 분석·추천의 원천 데이터를 생성하는 유스케이스이다. 기록은 **사용자의 하루에 하나**이고 시작·종료가 없다(LOG-39) |
| **사전 조건** | 로그인 상태 |
| **사후 조건** | 체크한 세트가 그날 기록에 저장되고, 세트 저장 시각으로 운동 시간이 계산됨 (뱃지 판정은 LOG-18로 제외) |

**기본 흐름**
1. 사용자가 기록 화면에 들어온다 (홈의 "직접 기록하기"·"이어서 기록", 오늘 루틴의 "이 루틴으로 기록", 홈 약점 카드의 부위 행에서 진입)
2. 시스템이 그날 기록을 연다 — 없으면 만들고, 있으면 그 기록이다. 같은 날 앞서 한 운동이 그대로 보인다
3. 사용자가 운동 종목을 선택한다 (종목 고르기 시트 — UC-02-05와 같은 부위 → 계열 → 변형 3단, 최근·즐겨찾기 탭, 이름 검색)
4. 시스템이 해당 종목의 직전 수행 기록(오늘 이전)을 세트 행에 자동으로 채운다
5. 사용자가 중량·횟수를 확인·수정하고 완료 체크한다
6. 시스템이 체크된 세트를 저장하고 저장 시각을 함께 기록한다
7. 본세트를 체크하면 휴식 타이머가 시작되고 다음 세트(종목·세트 번호)를 알려준다 — 세트마다 휴식 시간을 바꿀 수 있다
8. 3~7을 반복한다. 마지막으로 체크한 세트가 곧 끝이다 — 끝내는 단계가 없다
9. 시스템이 세트 저장 시각으로 그날 운동 시간을 계산해 보여준다(30분 넘는 공백에서 구간을 나눠 합한다)

> ~~10. 시스템이 뱃지 달성 여부를 판정한다 (UC-04-01)~~ — 뱃지 시스템 자체가 범위에서 제외되어(LOG-18) 이 단계는 없다.

**대체 흐름**
- 1a. 추천 루틴에서 진입한 경우 → 루틴의 종목과 세트 수만큼 행이 미리 표시된다. 표시된 행은 계획이며, 완료 체크한 세트만 저장된다
- 1b. 홈 약점 카드의 부위 행에서 진입한 경우 → 그 부위의 종목만 띄운 종목 고르기 시트가 열린 채로 시작한다
- 2a. 같은 날 두 번째로 운동하러 온 경우 → 아침 기록이 열리고 그 기록에 이어서 쌓인다
- 2b. 자정을 넘겨 운동하는 경우 → 어제 마지막 세트가 30분 안이면 어제 기록이 열린다
- 4a. 처음 하는 종목 → 빈 행 하나로 시작한다
- 5a. 워밍업 세트인 경우 → 사용자가 워밍업으로 표시하며, 해당 세트는 볼륨 집계에서 제외되고 휴식 타이머도 시작하지 않는다
- 5b. 측정 유형에 따라 입력 항목이 다르다 — 중량·횟수, 횟수만(맨몸), 추가 중량·횟수(중량 딥스 등), 시간만(플랭크 등)
- 5c. 같은 값으로 여러 세트를 채우는 경우 → 일괄 수정 시트로 한 번에 바꾼다
- 6a. 체크한 세트를 다시 누르면 → 체크를 취소하고 그 세트를 삭제한다

**예외 흐름**
- 5d. 값이 비어 있는 행을 체크하면 → 저장하지 않고 입력 칸을 펼친다
- 6b. 저장 실패(네트워크) → 오류 알림을 띄우고 행은 체크하지 않은 상태로 남긴다. 다시 체크하면 같은 세트 키(`clientSetId`)로 보내므로 두 번 저장되지 않는다
- 앱을 벗어났다 돌아온 경우 → 체크한 세트는 이미 저장되어 있고, 체크하지 않은 행은 브라우저에 그날까지 임시 저장되어 다시 나타난다

> 개정 전(LOG-39 이전)에는 "운동 종료"를 눌러야 세션이 완료되어 분석·그룹에 들어갔고, 종료하지 않고 나가면 재진입 시 "이어서 기록 / 종료"를 고르게 했다.

### UC-02-02 운동 기록 수정 / 삭제

| 항목 | 내용 |
|---|---|
| **액터** | 사용자 |
| **개요** | 저장된 세트의 값·워밍업 여부를 고치거나, 세트·종목 단위로 삭제한다 |
| **사전 조건** | 로그인 상태 / 본인 소유의 기록·세트 존재 |
| **사후 조건** | 수정·삭제 내용이 반영됨. 분석·통계는 온디맨드 재집계라 별도 처리 없이 다음 조회부터 자동 반영됨 |

**기본 흐름 (세트 수정)**
1. 사용자가 기록 탭 달력에서 날짜를 눌러(또는 오늘 기록에서) 그날 기록을 연다
2. 종목을 펼쳐 세트의 중량·횟수·시간을 고치거나 워밍업 표시를 바꾼다
3. 시스템이 이미 저장된 세트면 바로 서버 값도 고친다(`PATCH .../sets/{setId}`). 그날 추정 1RM 등 지표를 다시 읽는다

**기본 흐름 (세트 / 종목 삭제)**
1. 사용자가 세트 행을 지우거나, 체크한 세트를 다시 눌러 취소한다 → 그 세트가 삭제된다
2. 사용자가 종목을 빼면 → 체크한 세트가 있을 때만 되돌릴 수 없다고 한 번 확인하고, 그 종목의 세트를 한 번에 삭제한다(`DELETE .../exercises/{exerciseId}`)
3. 운동 시간은 읽을 때 세트 저장 시각으로 계산하므로 다음 조회에 바로 반영된다

**대체 흐름**
- 세트를 모두 삭제해도 기록 자체는 남는다. 세트가 없는 날은 히스토리·캘린더·분석에 나오지 않는다

**예외 흐름**
- 저장 실패 → 화면의 값을 고치기 전으로 되돌리고 오류를 알린다
- 삭제된 세트의 `setNo`는 재부여하지 않는다 — 화면은 서버 `setNo`가 아니라 배열 순번(1..N)으로 표시해 구멍을 감춘다

> API 명세서 6.9~6.13 참조. 분석이 온디맨드 집계이므로 수정·삭제 시 별도 재계산 배치가 필요 없다.
>
> **API만 있고 화면이 없는 것**(LOG-45): 하루 기록의 메모·날짜·운동 시간 보정 수정(`PATCH /workout-sessions/{id}`, 이미 기록이 있는 날짜로 옮기면 `409 DAY_ALREADY_RECORDED`)과 하루 기록 삭제(`DELETE /workout-sessions/{id}`)는 서버에 구현되어 있으나 화면에서 부르지 않는다. 사용자는 세트·종목을 지우는 것으로 하루를 비울 수 있다.

### UC-02-04 통계 조회 (종목별 추정 1RM 추이, 그날 종목 지표)

| 항목 | 내용 |
|---|---|
| **액터** | 사용자 |
| **개요** | 종목 하나의 추정 1RM 추이(kg, 시간축)를 보고, 기록 화면에서 종목마다 그날의 최대 무게·추정 1RM·볼륨을 본다 |
| **사전 조건** | 로그인 상태 / 해당 종목의 기록 존재 |
| **사후 조건** | 그래프·수치가 표시됨 |

**기본 흐름 (1RM 추이)**
1. 사용자가 분석 탭의 "통계"에 들어온다 — 최근 12주에 기록한 중량·횟수 종목이 칩으로 나온다
2. 사용자가 종목 칩을 고른다 (다른 종목은 종목 목록에서 고른다)
3. 시스템이 최근 12주의 `reps ≤ 12`인 세트에서 Epley 공식으로 날짜별 추정 1RM을 산출한다(그날 최댓값)
4. 날짜순 추이 그래프와 요약(현재 값, 어느 세트에서 추정했는지 등)을 표시한다

**기본 흐름 (그날 종목 지표)**
1. 사용자가 기록 화면에서 종목을 펼친다
2. 시스템이 그 종목의 그날 최대 무게, 추정 1RM(12회 이하 세트 기준), 볼륨(워밍업 제외 무게×횟수 합)을 표시한다. 세트를 저장·수정·삭제할 때마다 다시 계산한다

**대체 흐름**
- 같은 1RM 추이 패널이 종목 상세 화면에도 있다(UC-02-05)
- 12주 안에 12회 이하 세트가 없으면 → 빈 그래프 대신 그 이유("1RM은 12회 이하 세트로만 추정")를 안내한다
- 추가 중량 종목(중량 딥스 등) → 무게가 몸무게가 아니라 매단 무게라 추정 1RM을 내지 않는다

**예외 흐름**
- `measureType`이 `WEIGHT_REPS`가 아닌 종목으로 1RM 추이 요청 → `400 VALIDATION_ERROR`

> API 명세서 7.1·7.2 참조. 이전 명칭은 「통계 조회 (부위별 볼륨, 추정 1RM 추이, 세트별 강도)」였다. 부위별 볼륨은 UC-03-02(약점)가 보여 주고, 세트별 강도(%, `intensityPct`)는 API가 내려주지만 화면은 그날 추정 1RM 값만 쓴다. 톤 볼륨 그래프는 두지 않는다 — 맨몸 종목에서 무너지고 종목 간 무게 차이로 왜곡된다(LOG-45).

### UC-02-05 운동 종목 탐색 / 조회 (상세·종목 기록)

| 항목 | 내용 |
|---|---|
| **액터** | 사용자 |
| **개요** | 부위 → 계열 → 변형 3단계나 이름 검색으로 종목을 찾고, 종목 상세에서 동작 그림·내 최근 기록·1RM 추이를 본다. 기록 화면에서 종목을 고르면 직전 수행 기록을 프리필로 받는다 |
| **사전 조건** | 로그인 상태 (서버의 종목 목록 API는 비로그인도 열려 있으나, 앱 화면은 모두 로그인 뒤에 있다) |
| **사후 조건** | 종목 목록·상세가 표시되거나, 선택한 종목의 직전 세트가 기록 화면에 자동으로 채워짐 |

**기본 흐름 (탐색)**
1. 사용자가 홈의 "종목 둘러보기" 또는 기록 화면의 종목 고르기 시트를 연다
2. "부위" 탭에서 탐색 분류(13종, 부위 그림과 종목 수)를 고른다
3. 시스템이 그 분류의 계열(동작) 목록을 보여주고, 사용자가 계열을 고르면 변형 종목들을 보여준다 — 종목마다 시작·끝 자세 그림, 기구, 즐겨찾기
4. 이름을 입력하면 단계와 상관없이 이름으로 검색한다

**기본 흐름 (상세·종목 기록)**
1. 사용자가 둘러보기에서 종목을 누른다
2. 시스템이 종목 정보(동작 그림·부위·기구), 내 최근 기록 3일(날짜별 세트 칸), 중량·횟수 종목이면 추정 1RM 추이(UC-02-04)를 보여준다
3. 사용자가 "기록 더보기"를 누르면 그 종목을 한 날을 최신순으로 이어서 불러온다

**기본 흐름 (프리필)**
1. 사용자가 기록 화면에서 종목을 선택한다
2. 시스템이 본인의 오늘 이전 기록 중 그 종목을 가장 최근에 한 날의 세트를 조회한다
3. 조회된 세트(중량·횟수·워밍업 여부)를 세트 입력 행에 자동으로 채운다

**대체 흐름**
- "최근" 탭 → 최근에 기록한 종목을 최신순으로 보여준다
- "즐겨찾기" 탭 → 즐겨찾기한 종목만 보여준다. 즐겨찾기 등록/해제(`PUT`/`DELETE /users/me/favorite-exercises/{exerciseId}`)는 멱등이다
- 오늘 이전에 해당 종목 기록이 없으면(`204`) 빈 세트 행 하나로 시작한다 — 오류가 아니라 "처음 하는 종목"

**예외 흐름**
- 없는 종목 ID로 조회 → `404 RESOURCE_NOT_FOUND`, 이전 화면으로 돌아간다

> API 명세서 5.2~5.8 참조. 이전 명칭은 「운동 종목 검색 / 조회」였다. 목록 API는 기구·측정 유형 필터도 받지만 화면은 쓰지 않는다 — 109종을 필터로 고르기보다 부위에서 계열로 좁혀 들어가는 편이 찾기 쉽다(LOG-24). 종목 상세의 최근 기록과 종목 기록 페이지는 2026-10-25에 구현했고(PR #36), 이 명세에는 LOG-45에서 반영했다.

### UC-02-06 과거 운동 기록 사후 입력

| 항목 | 내용 |
|---|---|
| **액터** | 사용자 |

>
> 기록 누락은 분석에서 "볼륨 부족"으로 오판되므로, 사후 입력을 허용하는 것이 데이터 품질에 유리하다.

### UC-03-01 운동 습관 약점·불균형 분석

| 항목 | 내용 |
|---|---|
| **액터** | 시스템 자동 |
| **개요** | 사용자의 운동 기록을 집계해 부위별 부족·과다와 밀기/당기기·상하체 불균형을 판별한다 |
| **사전 조건** | 없음 — 기록이 없어도 판정은 나온다(전 부위 부족, 균형은 판정 불가). 분석 화면·홈을 열 때와 루틴을 요청할 때 그때그때 계산한다 |
| **사후 조건** | 부족·불균형 판정 결과가 산출되어 추천의 근거 및 조회 화면에 사용됨. 결과를 따로 저장하지 않는다 |

**기본 흐름**
1. 기준일(조회는 오늘, 루틴 추천은 어제 — UC-03-03)을 포함한 최근 4주(28일)의 본세트 기록을 조회한다 (워밍업 세트 제외. 오늘 체크한 세트도 포함 — 종료가 없다, LOG-39)
2. 각 세트를 종목의 주동근 기준으로 판정 부위 9개에 나눈다 — 가슴, 등, 어깨 전·측면, 어깨 후면, 삼두, 이두, 앞허벅지, 뒤허벅지·둔근, 코어. 종아리·전완은 세트 수만 세고 판정하지 않는다
3. 부위별 주간 평균 세트 수를 집계한다 — 기록을 시작한 지 4주가 안 됐으면 첫 기록일부터 지난 일수(최소 7일)로 나눈다
4. 판정 기준에 따라 상태를 분류한다
   - 주 4세트 미만 → 부족
   - 주 4세트 이상 10세트 미만 → 권장 이하
   - 주 10세트 이상 20세트 이하 → 최적
   - 주 20세트 초과 → 과다
5. 밀기(가슴·어깨 전·측면·삼두)와 당기기(등·어깨 후면·이두), 상체(6부위)와 하체(앞허벅지·뒤허벅지·둔근)를 **부위당 평균** 주간 세트로 맞대, 많은 쪽 ÷ 적은 쪽이 2배를 초과하면 불균형으로 판정한다 (정확히 2배는 정상)
6. 최근 4주 운동한 날 수로 판정 신뢰도를 매긴다 (6일 미만이면 낮음)
7. 판정 결과를 반환한다

**예외 흐름**
- 5a. 비교하는 양쪽 세트가 모두 0인 경우 → 불균형이 아니라 `INSUFFICIENT_DATA`(판정 불가)로 판정한다. 기록이 없는 것과 균형이 잡힌 것을 구분하기 위함이다
- 5b. 한쪽만 0인 경우 → `IMBALANCED`로 판정하되 비율 수치는 `null`(계산 불가)로 반환한다

> LOG-20에서 보강: 「운동 분석 로직 설계서」에도 없던 엣지 케이스다 — 어떤 상위 문서도 미리 정하지 않았고, `BalanceEvaluation.of`를 구현하며 실제로 마주쳐 처리한 뒤 이번에 문서로 역반영했다(LOG-07·LOG-13과 같은 패턴).
>
> LOG-45에서 고침: 2단계의 분류가 계획 시점의 6부위(가슴/등/하체/어깨/팔/코어)로 남아 있었다. 판정 부위 9개(LOG-09), 4주 미만 분모(LOG-31), 부위당 평균 비교(LOG-43), 기준일, 신뢰도를 구현대로 적었다. 4세트 경계는 ACSM 원문에 없는 본 작품의 경계다(LOG-44).

### UC-03-02 약점 분석 결과 조회

| 항목 | 내용 |
|---|---|
| **액터** | 사용자 |
| **개요** | UC-03-01이 산출한 부위별 볼륨 판정과 밀기/당기기·상하체 균형 판정을 화면에서 조회한다 |
| **사전 조건** | 로그인 상태 |
| **사후 조건** | 상위 6종/하위 9종 2계층 판정, 표시 전용 2종(종아리·전완)의 세트 수, 균형 판정이 표시됨 |

**기본 흐름**
1. 사용자가 분석 탭의 "약점"에 진입한다
2. 시스템이 최근 4주 부위별 볼륨 판정(상위 6종은 세트 수와 요약 배지, 하위 9종은 4단계 판정, 종아리·전완은 세트 수만)을 조회한다(`GET /analysis/muscle-volume`)
3. 시스템이 밀기/당기기·상체/하체 균형 판정(부위당 평균 세트, 비율, 불균형 여부, 구성 부위)을 조회한다(`GET /analysis/balance`)
4. 화면은 값을 그대로 표시할 뿐 합산·구간 분류·배지 계산을 하지 않는다(서버가 완성). 하위에 부족이 숨은 상위 부위만 처음부터 펼쳐 둔다

**대체 흐름**
- 홈의 약점 카드(부족·권장 이하 부위, 가장 덜 한 곳부터)와 균형 카드에서도 같은 결과를 요약해 보여준다. 약점 카드의 부위 행을 누르면 그 부위 종목으로 기록을 시작한다(UC-02-01 1b)
- 화면은 부족하다는 데까지만 알리고 "○○를 늘리세요" 같은 처방은 하지 않는다 — 무엇을 할지는 루틴 추천(UC-03-03)의 몫이다

**예외 흐름**
- 최근 4주 운동한 날이 하나도 없으면 → 전 부위 "부족" 대신 "기록한 운동이 없다"는 안내와 기록하기 버튼을 보여준다
- 최근 4주 운동한 날이 임계(기본 6일) 미만이면 `confidence.level = LOW`와 함께 "판정 신뢰도 낮음" 안내를 함께 표시한다
- 균형 판정에서 작은 쪽이 0이면 `ratio`는 `null`이며 화면은 "비율 계산 불가"로 표기한다

> API 명세서 8.1~8.3 참조. 판정 기준(경계값·배지 우선순위)은 서버가 단위 테스트로 고정한 것이라 화면은 재계산하지 않는다.

### UC-03-03 오늘의 루틴 추천 요청 ⭐

| 항목 | 내용 |
|---|---|
| **유스케이스 ID** | UC-03-03 |
| **명칭** | 오늘의 루틴 추천 요청 |
| **액터** | 사용자(주), LLM API(부) |
| **개요** | 운동하려는 시점에 그때까지 쌓인 기록을 분석해, 부족한 부위를 보완하는 오늘의 루틴을 만든다. 부위와 세트는 규칙이 정하고, LLM은 규칙이 준 후보 안에서 종목·순서·설명만 고른다(LOG-40) |
| **사전 조건** | 로그인 상태. 기록 수의 하한은 없다 — 기록이 없어도 첫 루틴이 나온다 |
| **사후 조건** | 루틴 하나가 그날 날짜로 저장되고, 그날 기록과 연결되어 화면에 표시됨 |

**기본 흐름**
1. 사용자가 "오늘 루틴 추천받기"를 선택한다
2. 시스템이 오늘 루틴이 이미 있는지 확인한다 — 루틴은 **하루에 하나**이고 다시 만들기는 없다
3. 시스템이 **어제를 기준일로** 부위별 주간 세트·판정과 불균형을 가져온다(UC-03-01). 오늘 체크한 세트가 오늘 루틴의 근거를 흔들지 않게 하기 위함이다
4. 시스템이 오늘 할 부위와 세트를 정한다 — 오늘·어제 운동한 부위의 묶음 제외, 부족 부위 정렬, 하체·밀기·당기기 중 묶음 하나 + 코어, 부위당 3~6세트, 하루 12~18세트(LOG-42, 「루틴생성_로직_설계서」 2·3장)
5. 시스템이 부위마다 후보 종목을 최대 5개 고른다 — 즐겨찾기 → 최근 8주에 해 본 종목(최대 3) → 안 해 본 종목(같은 설계서 4장)
6. 시스템이 정해진 부위·세트와 후보를 LLM API에 보내 종목·순서·설명을 고르게 한다. 응답 형식은 스키마로 묶는다 — 종목은 이번 후보 중에서만 고를 수 있고, 숫자를 쓰는 칸이 없다
7. 시스템이 LLM 응답을 L1~L6으로 검사한다(UC-03-04). 통과한 선택에 세트를 나눠 붙인다 — 세트는 규칙이 정한 값이다
8. 시스템이 완성된 루틴을 R1~R5로 검사하고(UC-03-04) 저장한 뒤, 그날 기록을 열어 루틴과 연결한다
9. 시스템이 루틴을 표시한다 — 항목마다 근거(그 부위의 주간 세트·판정)와 추천 설명을 함께 보여준다
10. 사용자는 필요에 따라 종목을 바꾸거나 세트를 조정한다 (UC-03-05)

**대체 흐름**
- 2a. 오늘 루틴이 이미 있으면 → 새로 만들지 않고 그 루틴을 표시한다
- 4a. 할 부위가 없으면(전부 회복 중이거나 충분) → 빈 루틴과 "쉬어 가도 좋다"는 설명을 표시한다
- 6a. LLM이 꺼져 있으면 → 규칙이 종목·순서·설명을 고른다(후보 1순위, 큰 근육 → 작은 근육 → 코어)
- 7a. L1~L5에 걸리면 → 틀린 이유를 붙여 다시 묻는다(최대 2번). 그래도 실패하면 규칙이 고른다
- 7b. L6(설명)만 걸리면 → 선택은 그대로 쓰고 설명만 규칙 문장으로 바꾼다
- 9a. 최근 4주 기록일이 적으면(6일 미만) → "기록이 쌓일수록 정확해진다"는 안내를 함께 표시한다

**예외 흐름**
- 6b. LLM API 호출 실패·시간 초과(10초) → 다시 묻지 않고 바로 규칙이 고른다
- 8a. 같은 날 요청이 동시에 두 번 들어오면 → 먼저 저장된 루틴 하나만 남고, 늦은 요청은 그 루틴을 받는다

> 2026-11-02 구현에 맞춰 다시 썼다(LOG-44). 처음에는 LLM이 운동·세트·횟수를 반환하고, 일정 횟수 이상의 기록이 있어야 추천하는 흐름이었다. LLM에 맡기는 범위를 줄인 이유는 LOG-40, 규칙이 실패를 대신하는 구조는 「LLM 연동 실험기록」 11장.

### UC-03-04 추천 루틴 품질 자동 검증

| 항목 | 내용 |
|---|---|
| **유스케이스 ID** | UC-03-04 |
| **명칭** | 추천 루틴 품질 자동 검증 |
| **액터** | 시스템 자동 |
| **개요** | 두 단계로 검사한다. ① LLM 응답이 정해진 범위를 지켰는지(L1~L6) ② 완성된 루틴이 운동량 규칙을 지키는지(R1~R5) |
| **사전 조건** | ① LLM이 응답을 반환함 ② 루틴의 종목·세트가 정해짐 (UC-03-03의 7·8단계) |
| **사후 조건** | ① 통과한 선택만 루틴에 쓰임 ② 검사 결과가 루틴과 함께 저장됨 |

**기본 흐름 — ① LLM 응답 검사 (L1~L6)**
1. L1: 응답이 `{items, comment}` 형식인가
2. L2: 고른 종목이 그 부위의 후보인가
3. L3: 모든 부위에 종목이 1~2개인가
4. L4: 같은 종목을 두 번 넣지 않았나
5. L5: 두 종목으로 나눌 수 없는 부위에 두 개를 넣지 않았나
6. L6: 설명이 120자 이하이고, 숫자·수량, 지시하는 말투, 의학 표현, 부위 이름 실수가 없는가

**기본 흐름 — ② 최종 루틴 검사 (R1~R5)**
1. R1: 부위당 3~6세트인가
2. R2: 루틴을 해도 부위별 주 20세트를 넘지 않는가
3. R3: 불균형의 많은 쪽에만 속한 부위에 세트가 없는가
4. R4: 후보 안의 종목이고, 부위별 세트 합이 계획과 같은가
5. R5: 하루 18세트 이하인가

**대체 흐름**
- ① L1~L5 실패 → 틀린 이유를 붙여 최대 2번 다시 묻고, 그래도 실패하면 규칙이 고른다(UC-03-03 7a). L6만 실패하면 설명만 바꾼다(7b)
- ② R1~R5 실패 → **루틴은 그대로 제공**하고 실패한 규칙을 저장한다. 세트는 규칙이 정하므로 대부분 구성상 통과하며, 규칙에 구멍이 있으면 실사용 데이터에서 드러나도록 통과율로 본다

> 기능명세서 2.3 참조. 규칙의 근거는 「루틴생성_로직_설계서」 6.1(L1~L6)·6.2(R1~R5). 2026-11-02 구현에 맞춰 다시 썼다(LOG-44) — 처음에는 검사 한 단계에서 실패하면 재생성하는 흐름이었다.

**기본 흐름**

- 3a. 지난 날짜의 루틴을 고치려 하면 → 거부한다. 후보정은 오늘 루틴만 가능하다

> 부상 부위나 보유 기구 등 개별 제약을 미리 입력받지 않는 대신, 이 후보정 과정을 통해 사용자가 직접 조정한다. 교체 후보에서 기구가 다른 종목을 앞에 두는 이유는 교체 사유(기구 사용 불가 등)를 해소하기 위함이다(LOG-08).

### UC-05-01 그룹 생성 및 초대 링크·코드 발급

| 항목 | 내용 |
|---|---|
| **액터** | 사용자 |
| **개요** | 그룹을 만들고 친구를 부를 초대 링크와 코드를 받는다 |
| **사전 조건** | 로그인 상태 / 들어간 그룹이 10개 미만 |
| **사후 조건** | 그룹이 생성되고 생성자가 방장이자 첫 멤버로 등록되며, 초대코드가 발급됨 |

**기본 흐름**
1. 사용자가 "그룹 만들기"를 선택하고 그룹 이름(1~20자)을 입력한다
2. 시스템이 그룹(`friend_groups`)을 만들고 6자리 초대코드를 발급한다(헷갈리는 글자 제외)
3. 시스템이 생성자를 방장이자 첫 멤버(`friend_group_members`)로 등록한다
4. 시스템이 그룹 화면을 열고 초대 시트(코드·링크)를 바로 띄운다
5. 사용자가 초대 링크를 공유하거나 링크·코드를 복사해 친구에게 보낸다

**예외 흐름**
- 1a. 이름이 비었거나 20자를 넘는 경우 → 입력 오류 표시
- 2a. 들어간 그룹이 이미 10개인 경우 → 한도 안내

> 기능명세서 2.6 참조. 초대는 방장만이 아니라 **멤버 누구나** 할 수 있다 — 친구가 친구를 부를 때마다 방장을 거칠 필요가 없다. 코드를 다시 만드는 것만 방장이 한다(UC-05-07).

### UC-05-02 초대 링크·코드로 그룹 참여

| 항목 | 내용 |
|---|---|

**기본 흐름**
1. 사용자가 초대 링크(`/join/코드`)를 누른다. 또는 그룹 탭의 "초대코드로 참여"에 코드(또는 링크)를 입력한다

**예외 흐름**
- 2a. 코드가 존재하지 않는 경우(바뀌었거나 그룹이 삭제됨) → "초대코드를 찾을 수 없다" 안내
- 2b. 이미 해당 그룹의 멤버인 경우 → 안내 후 그룹 화면으로 이동 (링크를 두 번 누르는 경우)
- 2c. 그룹 인원이 20명인 경우 → 참여 불가 안내
- 4a. 들어간 그룹이 이미 10개인 경우 → 한도 안내

### UC-05-03 그룹 멤버 활동 현황 조회 (오늘 운동 여부·주간 횟수·시간)

| 항목 | 내용 |
|---|---|
| **액터** | 사용자 |
| **개요** | 그룹 멤버별로 오늘 운동했는지와 이번 주(월~일) 운동한 날·횟수·시간을 본다 |
| **사전 조건** | 로그인 상태 / 해당 그룹의 멤버 |
| **사후 조건** | 멤버별 활동 현황이 표시됨 |

**기본 흐름**
1. 사용자가 그룹 화면에 진입한다
2. 시스템이 멤버들의 이번 주 `workout_sessions`를 한 번에 읽어 멤버별로 집계한다
   - 오늘: 오늘 기록에 세트가 있으면 "오늘 운동함", 없으면 비워 둔다. 친구가 운동하는 중이어도 체크한 세트가 있으면 "오늘 운동함"이다(LOG-39)
   - 이번 주: 운동한 날, 횟수(운동한 날 수 — 사후 입력 포함), 시간 합(시간 없는 사후 입력 제외)
3. 멤버를 들어온 순서로, 주간 점(월~일)·횟수·시간과 함께 표시한다. 오늘 운동한 멤버 옆에만 "오늘 운동함"과 응원 버튼이 붙는다(UC-05-06)

**대체 흐름**
- 1a. 그룹 탭의 그룹 목록 → 그룹마다 카드 한 장에 멤버 얼굴과 각자의 오늘 운동 여부를 보여준다. 그룹에 들어가기 전에도 누가 운동했는지 보인다
- 1b. 그룹에 혼자뿐이면 → "아직 혼자예요"와 함께 친구 초대를 권한다

**예외 흐름**
- 1a. 멤버가 아니거나(내보내짐) 그룹이 삭제된 경우 → 그룹을 찾을 수 없다는 안내 후 그룹 목록으로 이동

> 기능명세서 2.6 참조. 별도 집계 테이블 없이 온디맨드로 계산한다. "오늘 운동했나"를 손으로 체크하게 하지 않는 것은, 기록과 두 번 입력하게 되고 둘이 어긋날 수 있기 때문이다 — 기록해야 그룹에 뜨므로 기록을 이어 가게 하는 장치도 된다(LOG-38). 순위는 두지 않는다.

### UC-05-04 그룹 탈퇴

### UC-05-05 그룹 멤버 기록 조회 (읽기 전용)

**기본 흐름**
1. 사용자가 그룹 화면에서 멤버를 누른다
2. 시스템이 그 멤버의 월간 캘린더(운동한 날 표시)를 보여준다 — 내 기록 탭과 같은 달력이다
3. 사용자가 기록이 있는 날짜를 누른다
4. 시스템이 그날 기록을 보여준다 — 시작 시각·운동 시간·세트 수, 종목마다 카드(동작 그림, 세트별 무게·횟수). **메모는 보여주지 않는다.** 오늘 운동하는 중이면 그때까지 체크한 세트가 보인다(LOG-39)

**예외 흐름**
- 2a. 대상이 같은 그룹 멤버가 아닌 경우(나갔거나 내보내짐) → 찾을 수 없다는 안내 후 그룹 목록으로 이동
- 3a. 기록이 없는 날 → 누를 수 없다

> 메모는 "오늘 컨디션 최악" 같은 혼잣말일 수 있어 그룹에 보이지 않는다(LOG-38). 참여 화면(UC-05-02)과 개인정보처리방침이 이 공개 범위를 미리 알린다.

### UC-05-06 멤버 운동에 응원

| 항목 | 내용 |
|---|---|
| **액터** | 사용자 |
| **개요** | 그룹 멤버의 하루 기록에 응원을 보낸다 |
| **사전 조건** | 로그인 상태 / 대상 기록의 주인이 같은 그룹 멤버 / 내 운동이 아님 |
| **사후 조건** | 응원(`cheers`)이 기록되고 응원 수가 늘어남 |

**기본 흐름**
1. 사용자가 그룹 화면(오늘 운동한 멤버) 또는 멤버의 하루 기록에서 응원 버튼을 누른다
2. 시스템이 응원을 기록하고 바뀐 응원 수를 돌려준다
3. 화면이 응원 수와 "내가 응원함" 표시를 바꾼다

**대체 흐름**
- 1a. 이미 응원한 운동에서 다시 누른 경우 → 응원을 취소한다

**예외 흐름**
- 1b. 내 운동인 경우 → 버튼 대신 받은 응원 수만 보인다
- 2a. 연타로 같은 요청이 겹친 경우 → 한 번만 기록된다

> 응원은 그룹이 아니라 **하루 기록**에 붙는다 — 같은 사람과 그룹 두 개를 함께해도 그 사람의 운동은 하나다. 하루에 두 번 운동해도 응원은 그 하루에 하나다(LOG-39).

### UC-05-07 그룹 관리 (방장)

| 항목 | 내용 |
|---|---|
| **액터** | 사용자 (방장) |
| **개요** | 방장이 그룹 이름 변경, 초대코드 재발급, 멤버 내보내기, 그룹 삭제를 한다 |
| **사전 조건** | 로그인 상태 / 해당 그룹의 방장 |
| **사후 조건** | 각 작업이 반영됨 |

**기본 흐름**
1. 방장이 그룹 메뉴를 연다
2. 방장이 작업을 고른다
   - 이름 바꾸기 → 새 이름(1~20자) 저장
   - 초대코드 새로 만들기 → 확인 후 새 코드 발급. **옛 코드·링크로는 더 들어올 수 없다** (링크가 엉뚱한 곳에 퍼졌을 때)
   - 멤버 관리 → 멤버를 골라 확인 후 내보내기
   - 그룹 삭제 → 확인 후 삭제
3. 시스템이 반영하고 결과를 보여준다

**예외 흐름**
- 2a. 방장이 아닌 멤버가 시도한 경우 → 메뉴에 보이지 않으며, 서버도 거절한다
- 2b. 방장이 자신을 내보내려는 경우 → 거절하고 "그룹 나가기"(UC-05-04)를 안내한다

> 내보내진 멤버와 삭제된 그룹의 멤버는 그 그룹을 더 볼 수 없지만, 각자의 운동 기록은 그대로 남는다.

### UC-04-01 뱃지 달성 조건 판정 및 지급 — **범위에서 제외 (LOG-18)**

> 아래 명세는 제외 이전에 확정했던 설계를 보존한 것이며, 구현 대상이 아니다.

| 항목 | 내용 |
|---|---|
| **액터** | 시스템 자동 |
| **개요** | 운동 기록 저장 시 뱃지 달성 여부를 판정하고 자동 지급한다 |
| **사전 조건** | 운동 기록이 저장됨 |
| **사후 조건** | 조건 충족 시 뱃지가 지급되고 사용자에게 표시됨 |

**기본 흐름**
1. 운동 기록 저장 이벤트가 발생한다
2. 시스템이 미획득 뱃지의 달성 조건을 조회한다
3. 사용자 누적 기록과 조건을 비교한다 (예: 3대 500, 스쿼트 100회 등)
4. 조건을 충족한 뱃지를 지급하고 획득 이력에 저장한다
5. 사용자에게 뱃지 획득을 표시한다

### UC-06-01 알림 권한 요청 및 설정 — **미구현, 범위에서 제외 (LOG-45)**

> 아래 UC-06-01~03 명세는 계획 시점의 설계를 보존한 것이며, 구현되지 않았다.

| 항목 | 내용 |
|---|---|
| **액터** | 사용자 |

**예외 흐름**

## 4. 유스케이스 다이어그램 (구성 안내)

액터는 **사용자**(주), **LLM API**·**Google 인증**(외부)으로 구성한다. 알림(UC-06)이 미구현으로 빠지면서 FCM 액터도 그리지 않는다(LOG-45).

> **작도 원칙 — 원 하나 = 3장의 명세 하나.** 다이어그램의 타원과 명세 항목은 1:1로 대응해야 한다. 원 하나가 여러 유스케이스를 묶으면 그 원에 대응하는 사전조건·기본흐름·예외흐름이 무엇인지 특정할 수 없고, 대조(5장·LOG-20)도 성립하지 않는다. 아래 배치의 원은 전부 UC 번호를 하나씩만 갖는다.

```
                  ┌──────────────────── 시스템 경계 ────────────────────┐
                  │                                                    │
                  │  (회원가입 01-01)   (로그인/로그아웃 01-02) ─────────┼──── Google 인증
                  │  (개인정보 수정 01-03) (회원 탈퇴 01-04) ────────────┤
                  │  (비밀번호 변경 01-05)                               │
                  │                                                    │

                  │                                                    │
     사용자 ──────┤  (오늘의 루틴 추천 요청 03-03) ◀── 핵심             ├────── LLM API
```

**관계 표기**
- `오늘의 루틴 추천 요청(03-03)` → `약점·불균형 분석(03-01)` : **include** (항상 수행 — 어제 기준)
- `오늘의 루틴 추천 요청(03-03)` → `추천 품질 검증(03-04)` : **include** (항상 수행)
- `분석 결과 조회(03-02)` → `약점·불균형 분석(03-01)` : **include** (결과를 저장하지 않고 조회할 때마다 계산)
- `로그인/로그아웃(01-02)`·`회원 탈퇴(01-04)` — `Google 인증` : 구글 로그인과 탈퇴 본인 확인에서만 연결
- 뱃지(UC-04)와 알림(UC-06)은 범위에서 제외됐으므로(LOG-18, LOG-45) 작도 시 그리지 않는다
- `약점·불균형 분석(03-01)`·`추천 품질 검증(03-04)`은 시스템 자동 수행이라 사용자와 직접 연결선을 긋지 않는다

> 원 24개 = 3장의 활성 명세 24개 (UC-01 5 · UC-02 6 · UC-03 6 · UC-05 7). 작도 도구는 draw.io, StarUML 중 택1.
