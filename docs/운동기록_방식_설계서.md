# 운동 기록 방식 설계서
### 운동 습관 분석 기반 맞춤 루틴 추천 헬스 웹앱 — 기록 데이터 구조 및 입력 방식 설계

> 본 문서는 지도교수 피드백 1단계("운동 기록 방식을 구체화해 충실한 기록을 확보할 것")에 대응하는 설계 산출물이다.
> 「운동 분석 로직 설계서」 7.2에서 검토 항목으로 제시한 사항을 확정한 것이며, 분석·추천의 전제가 되는 기록 데이터의 구조와 입력 방식을 다룬다.
> 작성 시점: 2026년 8월 1주 (설계 확정 단계)

---

## 0. 설계 개요

### 0.1 이 문서를 우선 작성하는 이유

이 앱의 핵심 기능인 약점 분석과 루틴 추천은 모두 사용자의 운동 기록 위에서 동작한다. 기록이 부실하거나 필요한 항목이 빠져 있으면, 그 위에 올리는 분석 로직이 아무리 정교해도 결과가 무의미해진다. 반대로 기록 단계에서 필요한 데이터를 확보해 두면 이후 단계는 집계와 판정만 하면 된다.

또한 데이터 구조는 나중에 바꾸기 가장 어려운 부분이다. 9월에 운동 기록 기능을 구현한 뒤 10월에 "분석에 이 값이 필요한데 안 쌓여 있다"는 것을 발견하면, 이미 쌓인 기록을 되살릴 방법이 없다. 따라서 구현 전에 분석 요구사항에서 역산하여 구조를 확정한다.

### 0.2 설계 원칙

- **분석 요구사항에서 역산한다.** 일반적인 기록 앱의 기능을 나열하지 않고, 이 앱의 분석 로직이 실제로 필요로 하는 데이터가 무엇인지에서 출발한다.
- **입력 부담과 데이터 충실성의 균형을 잡는다.** 사용자가 운동 중에 조작하는 것이므로, 항목을 늘리는 대신 자동화·프리필로 조작 횟수를 줄인다.
- **기록되지 않은 것은 추론하지 않는다.** 앱이 알 수 없는 값(예: 좌우 차이)은 억지로 추정하지 않고 측정 범위 밖으로 둔다. 「운동 분석 로직 설계서」 0장의 "과한 정밀도를 피한다"는 원칙과 동일한 태도이다.

## 1. 분석 요구사항에서 역산한 기록 요건

각 기능이 요구하는 데이터를 정리하면 다음과 같다.

| 기능 | 필요한 데이터 | 기록 구조에 대한 함의 |
|---|---|---|
| 부위별 세트 집계 (분석 2장) | 운동 종목 + 세트 단위 카운트 | 세트 1개가 1행으로 저장되어야 함 |
| 추정 1RM 추이 (분석 1.3) | 중량, 횟수 | 세트별 중량·횟수 필요 |
| 세트별 강도(%) 표시 (분석 1.3) | 세트별 중량, 그날의 추정 1RM | 세트를 묶어서 요약 저장하면 산출 불가 |
| 최근 4주 평균 (분석 2.1) | 운동 수행 일자 | 저장 시각과 별개로 수행 일자(DATE)가 필요 |
| 빈도 판정 (분석 3장, Optional) | 부위별 "운동한 날짜 수" | 세트가 어느 날 세션에 속하는지 알아야 함 |
| 균형 판정 (분석 4장) | 부위별 세트 볼륨 | 위 항목으로 충족 |
| 그룹 활동 공유 (기능명세 2.6) | 세션별 총 운동 시간, 주간 운동 횟수 | **세션 단위 묶음이 필요** |
| 루틴 실제 수행률 (계획서 7장) | 추천 루틴과 실제 수행 기록의 대응 | 세션이 어느 루틴에서 시작되었는지 연결 필요 |

**결론**: 계획서 4.4의 `workout_logs` 단일 테이블로는 운동 시간·주간 횟수·수행률을 산출할 수 없다. 기록을 **세션(한 번의 운동) — 세트(개별 수행)** 의 2계층으로 분리한다.

## 2. 데이터 구조 — 세션·세트 2계층

### 2.1 workout_sessions (운동 세션)

한 번의 운동을 나타낸다. 운동 시간·주간 횟수·수행률의 산출 단위이다.

> **하루 여러 세션을 허용한다** (2026-08-31 확정). 오전·오후로 나눠 운동하는 경우, 한 세션에 몰아넣으면 중간 공백이 4.2의 15분 캡으로 잡혀 운동 시간이 왜곡된다. 다만 `DRAFT` 세션은 사용자당 하나로 유지한다(5.1).

| 컬럼 | 타입 | 설명 |
|---|---|---|
| id | PK | |
| user_id | FK → users | |
| performed_on | DATE | **분석 집계의 기준 일자.** 자정을 넘겨 운동한 경우에도 시작 일자로 귀속 |
| routine_id | FK → routines, NULL | 추천 루틴에서 시작한 경우 연결. 수행률 측정에 사용 |
| status | ENUM(DRAFT, DONE) | 진행 중/완료. 앱 이탈 대응 (5.1) |
| source | ENUM(LIVE, BACKFILL) | 실시간 기록 / 사후 입력. 시간 신뢰도 판단에 사용 (4.3) |
| started_at | TIMESTAMPTZ | 첫 세트 저장 시각 |
| ended_at | TIMESTAMPTZ, NULL | 마지막 세트 저장 시각 |
| duration_sec | INT, NULL | 자동 산출된 운동 시간 (4.2) |
| duration_override_sec | INT, NULL | 사용자 수동 보정값. 존재 시 우선 (4.4) |
| memo | TEXT, NULL | 자유 메모 |
| created_at / updated_at | TIMESTAMPTZ | |

### 2.2 workout_sets (세트 기록)

세트 1개가 1행이다. 계획서 4.4의 `workout_logs`를 대체한다.

| 컬럼 | 타입 | 설명 |
|---|---|---|
| id | PK | |
| session_id | FK → workout_sessions | |
| exercise_id | FK → exercises | 부위 분류는 조인으로 해결 |
| set_no | SMALLINT | 세션 내 해당 종목의 세트 순번 |
| weight_kg | NUMERIC(6,2), NULL | 맨몸운동은 NULL |
| reps | SMALLINT, NULL | 시간 기반 종목은 NULL |
| duration_sec | INT, NULL | 플랭크 등 시간 기반 종목 |
| is_warmup | BOOLEAN, default false | true인 세트는 볼륨 집계에서 제외 (3.5) |
| recorded_at | TIMESTAMPTZ | 세트 저장 시각. 운동 시간 산출에 사용 |

**인덱스**
- `workout_sessions (user_id, performed_on)` — 최근 4주 조회
- `workout_sets (session_id)` — 세션 상세 조회
- `workout_sets (exercise_id)` — 종목별 1RM 추이 조회

**분석 집계 형태 (예시)**

```sql
-- 최근 4주(오늘 포함 28일) 부위별 세트 수
SELECT e.body_part, COUNT(*) AS total_sets
FROM workout_sets s
JOIN workout_sessions ws ON ws.id = s.session_id
JOIN exercises e        ON e.id = s.exercise_id
WHERE ws.user_id = ?
  AND ws.performed_on >= CURRENT_DATE - 27
  AND ws.performed_on <= CURRENT_DATE
  AND ws.status = 'DONE'
  AND s.is_warmup = false
GROUP BY e.body_part;
```

> 하한이 `- 28`이 아니라 **`- 27`** 인 것에 유의한다. 양끝을 포함하므로 `CURRENT_DATE - 27 ~ CURRENT_DATE`가 정확히 28일이다(분석 2.1, API 명세서 8.2의 `[referenceDate - (weeks × 7 - 1)일, referenceDate]`와 같은 식). 상한을 명시한 것은 미래 날짜 세션을 배제하기 위함이다.
>
> `date` 컬럼에서 빼는 정수는 일 단위이므로 결과도 `date`다. `CURRENT_DATE - INTERVAL '28 days'` 형태는 `timestamp`를 만들어 암묵 캐스팅에 기대게 되므로 쓰지 않는다.

### 2.3 exercises 확장 — measure_type

종목마다 입력해야 할 항목이 다르다. 맨몸운동에 중량 입력을 요구하거나 플랭크에 횟수 입력을 요구하면 입력 부담이 커지고 데이터도 오염된다. 이에 종목별 측정 유형을 필드로 둔다.

| measure_type | 입력 항목 | 예시 | 1RM 추정 |
|---|---|---|---|
| WEIGHT_REPS | 중량 + 횟수 | 벤치프레스, 스쿼트 | 대상 |
| BODYWEIGHT_REPS | 횟수 | 푸시업, 크런치 | 제외 |
| WEIGHTED_BODYWEIGHT | 추가 중량 + 횟수 | 중량 딥스, 중량 턱걸이 | 제외 (체중 미반영으로 왜곡) |
| TIME | 시간(초) | 플랭크 | 제외 |

> **주의**: free-exercise-db에는 이 정보가 없다. 8월 2주 운동 종목 DB 정제 작업 시 한글 명칭·부위 매핑과 **함께** 채워야 한다. 이 필드가 없으면 입력 화면을 종목별로 분기할 수 없다.

### 2.4 exercises 확장 — equipment

루틴 후보정(기능명세 2.4)에서 운동을 교체할 때, 대체 후보를 `body_part`만으로 고르면 교체 사유를 해소하지 못한다. 사용자가 교체를 원하는 상황은 대개 기구를 쓸 수 없거나 특정 동작을 피해야 하는 경우인데, 같은 부위라는 이유로 동일한 기구의 종목을 제시하면 무의미하다.

| equipment | 예시 종목 |
|---|---|
| BARBELL | 벤치프레스, 바벨 스쿼트 |
| DUMBBELL | 덤벨 컬, 덤벨 플라이 |
| MACHINE | 랫풀다운, 레그프레스 |
| CABLE | 케이블 크로스오버 |
| BODYWEIGHT | 푸시업, 크런치 |
| PULLUP_BAR | 턱걸이 |

대체 후보는 **같은 `body_part`이면서 `equipment`가 다른 종목을 우선**한다. 후보정의 트리거 방식과 정렬 기준은 10월 루틴 추천 설계에서 확정한다.

> free-exercise-db 원본에 `equipment` 필드가 존재하므로, 정제 시 한글 매핑만 수행하면 된다. `measure_type`과 달리 값을 새로 만들 필요가 없다. 상세 근거는 「설계 변경 로그」 LOG-08 참조.

### 2.5 계획서 4.4와의 관계

계획서에 기재된 `workout_logs`는 본 설계에서 `workout_sessions` + `workout_sets`로 분해되었다. 엔티티 이름과 개수는 달라지지만, "사용자·종목·중량·세트·횟수·일자를 기록한다"는 역할 자체는 동일하다. 계획서는 계획 시점의 기록으로 그대로 두고, 변경 사항은 「설계 변경 로그」와 최종 보고서에 반영한다.

## 3. 세트 입력 방식

### 3.1 저장 단위 — 세트 1행

"3세트 × 60kg × 10회" 형태의 요약 입력이 아니라, 세트마다 개별 행으로 저장한다.

**근거**
- 세트별 강도(%) 표시(분석 1.3)가 세트 단위 데이터를 요구한다. 요약 저장으로는 산출이 불가능하다.
- 실제 운동에서는 세트마다 중량·횟수가 달라지는 경우가 많아(백오프 세트, 실패 세트), 요약 입력이 오히려 실제와 어긋난다.
- 상용 기록 앱 대부분이 세트 행 방식을 채택하고 있어 사용자에게도 익숙하다.

### 3.2 입력 화면 구조

종목 카드 안에 세트가 행으로 쌓이고, 각 행에 이전 기록·중량·횟수·완료 체크가 배치되는 구조이다.

```
[벤치프레스]                          … 워밍업 토글
 세트   이전기록      kg      회      ✓
  1     60 × 10      60      10      ☑
  2     60 × 10      60      10      ☐
  3     60 × 8       60      —       ☐
 + 세트 추가
```

**루틴 수행과 자유 기록은 같은 화면을 쓴다.** 완료 체크는 별도 화면이 아니라 세트 행 위에 얹히는 열이므로, 루틴에서 진입하면 행이 미리 채워진 상태로, 자유 기록이면 빈 행 하나로 시작하는 차이만 둔다. 화면을 하나만 만들면 되므로 개인 개발 조건에서도 유리하다.

### 3.3 행 확정 시점 — 체크한 세트만 저장

**루틴에서 미리 깔린 행은 저장된 기록이 아니라 화면 상태(계획)이다.** 완료 체크를 하는 순간에만 `workout_sets` 행으로 INSERT 한다.

**근거**
- 루틴 진입 시점에 계획 세트를 모두 INSERT 하면, 3세트 중 1세트만 수행하고 이탈한 사용자의 볼륨이 3세트로 집계된다. 이는 약점 판정을 직접 왜곡한다. 특히 **수행하지 않은 부위가 충분히 수행된 것으로 잡히는 방향**이라 오판의 성격이 나쁘다.
- 행의 존재 자체가 "수행함"을 의미하므로 `is_completed` 같은 별도 컬럼이 필요 없다.
- 체크 시각이 `recorded_at`으로 기록되어 운동 시간 산출(4장)에 그대로 이어진다.

### 3.4 입력 부담 완화 — 3단 프리필

세트 행 저장을 유지하면서 조작 횟수를 줄이는 장치이다.

| 단계 | 시점 | 동작 |
|---|---|---|
| ① 종목 프리필 | 종목 선택 시 | 해당 종목의 직전 수행 기록(중량·횟수·세트 수)을 그대로 채움 |
| ② 세트 복사 | 세트 추가 시 | 직전 세트 값을 복사 |
| ③ 루틴 프리필 | 루틴에서 시작 시 | 추천 루틴의 종목·세트 수만큼 행을 배치 (중량만 입력) |

**①의 데이터 원천**: `GET /exercises/{id}/last-performance`(API 명세서 5.5). 완료(`DONE`)된 세션 중 `performed_on`이 가장 늦은 것에서 그 종목의 전 세트를 돌려준다. 기록이 없으면 `204`이며 빈 행 하나로 시작한다. ②는 진행 중 세션 안의 값을 복사하는 것이므로 서버 호출이 없고, 그래서 ①은 `DRAFT` 세션을 대상에서 뺀다 — 두 장치의 담당 범위가 겹치지 않는다.

여기에 중량 ±2.5kg / 횟수 ±1 스테퍼와 최근·즐겨찾기 종목 상단 노출을 더하면, 값이 이전과 같은 세트는 체크 1탭으로 기록된다.

### 3.5 워밍업 세트 — 토글 제공, 볼륨 집계에서 제외

`is_warmup` 플래그를 두고(기본 false), true인 세트는 부위별 볼륨 집계에서 제외한다.

**근거**
- **기준의 단위를 맞추기 위함이다.** ACSM의 "주 10~20세트"는 실패 근처까지 수행하는 본세트를 센 값이다. 워밍업을 함께 집계하면 앱의 계산 단위가 기준값의 단위와 달라져, 판정 기준의 근거가 성립하지 않는다.
- **오판의 방향이 나쁘다.** 워밍업을 포함하면 볼륨이 부풀려져, 실제로 부족한 부위가 "권장 이하"나 "최적"으로 올라온다. 약점을 놓치는 쪽으로 틀리는 것은 이 앱의 목적을 직접 훼손한다.
- **균형 판정도 왜곡된다.** 워밍업은 모든 부위에 고르게 붙지 않고 스쿼트·벤치프레스 같은 고중량 복합운동에 집중되므로, 밀기·하체 볼륨이 상대적으로 과대 계상되어 2배 임계 판정에 영향을 준다.
- 구현 비용은 불리언 컬럼 하나와 집계 조건 한 줄로, 얻는 정합성 대비 매우 작다.

**입력 부담 고려**: 기본값을 false로 두고, 화면에서는 "본세트만 기록해도 무방하다"고 안내한다. 워밍업을 기록하는 사용자만 토글을 쓰는 선택적 장치이다.

**한계 인지**
- 사용자가 워밍업을 표시하지 않고 기록하면 볼륨이 과대 집계되며, 앱은 이를 판별할 수 없다.
- 자동 판별(예: 그날 해당 종목 최고 중량의 일정 비율 미만인 선행 세트를 워밍업으로 제안) 방식이 있으나, 임계 비율의 근거를 대기 어렵고 오탐 시 사용자가 이유를 이해할 수 없으므로 초기 구현에서는 채택하지 않는다. 확장 아이디어로 기록한다.

### 3.6 추정 1RM 산출 대상 세트

- `measure_type = WEIGHT_REPS`인 종목의 세트만 대상으로 한다.
- **`reps ≤ 12`인 세트만 사용**한다. 「운동 분석 로직 설계서」 1.3에서 인지한 대로 추정 공식은 고반복 구간에서 오차가 커지므로, 오차가 큰 구간을 애초에 계산에 넣지 않는다.
- 하루에 같은 종목의 세트가 여러 개인 경우, 각 세트의 추정값 중 **최댓값**을 그날의 추정 1RM으로 채택한다.
- 워밍업 세트는 중량이 낮아 추정값이 최댓값이 되지 않으므로 자동으로 배제된다.

### 3.7 휴식 타이머 — 표시(9월) / 알림(11월)

세트 사이 휴식을 화면에 표시한다. **기록 데이터가 아니다** — 서버로 보내지 않고 저장하지도 않으므로 스키마·API 변경이 없다. 초판에서 제외 항목(7장)이었던 것을 아래 근거로 되돌린 결정이다.

**분석에 쓰지 않는 이유**

휴식 시간 자체는 이미 `workout_sets.recorded_at`의 연속 세트 간격으로 들어온다(4.2가 운동 시간 산출에 쓰는 그 값). 즉 타이머는 데이터 수집 장치가 아니라 **화면 보조 장치**다. 그리고 그 간격 데이터는 판정에 쓸 수 없다 — 기록 지연·이탈이 섞여 있어 4.2가 15분 캡과 +90초 보정을 두어야 했고, 9장이 "참고 지표로만" 쓴다고 이미 한정했다. 휴식 구간 권고는 볼륨 기준(주 4/10~20세트)과 달리 문헌 합의도 약하다. 「운동 분석 로직 설계서」 0장의 "근거로 방어할 수 없는 정밀도를 피한다"에 걸린다.

> 따라서 초판이 제외 근거로 적었던 *"분석에 사용되지 않는다"* 는 타이머를 뺄 근거가 되지 못한다. 타이머는 애초에 데이터 장치가 아니어서 분석과 무관하다. 실제 판단 기준은 **9월 범위**이며, 화면 설계가 목업에 이미 있고 서버 계약 변경이 0이라는 점에서 범위 안으로 들였다.

**2단계 구성**

| 단계 | 내용 | 시점 |
|---|---|---|
| A. 표시 | 세트 완료 시 휴식 경과 시간 표시, 목표 시간 도달 시 화면 강조. 설정은 **기본 휴식 시간·자동 시작** 2종 | 9월 (화면 구현 시) |
| B. 알림 | 휴식 종료 시 소리·진동. 설정 2종 추가 | 11월 (PWA·FCM 묶음) |

**A를 타임스탬프 기반으로 만든다.** 브라우저는 탭이 백그라운드로 가거나 화면이 꺼지면 `setInterval`을 스로틀·정지시키므로, 카운터를 깎는 방식은 폰을 내려놓는 순간 어긋난다. 시작 시각(`restStartedAt`)과 목표 시간을 들고 매번 경과를 계산한다. LOG-12가 진행 중 세션 경과 시간을 `startedAt` 기준 계산으로 정한 것과 같은 방식이며, 기준점만 다르다. 이렇게 두면 B는 `restStartedAt + 목표시간` 시점에 알림을 예약하는 **추가 작업**이 되고, 카운터 방식이면 재작성이 된다.

**B를 11월에 두는 이유**: 소리·진동은 페이지가 얼면 발화하지 않아 서비스워커와 알림 권한이 필요한데, 서비스워커는 개발 중 캐시 문제로 11월에 배치했다(「개발환경_구축_기록」 11.1). FCM 권한 요청(UC-06-01)과 **같은 권한 하나**를 쓰므로 별도 요청 흐름을 만들지 않는다. iOS는 홈 화면 설치 시에만 웹 알림이 동작한다(기능명세 3.1).

**9월에 소리·진동 토글을 화면에 두지 않는다.** 동작하지 않는 토글을 노출하면 목업의 계정 삭제 버튼(핸들러 미연결, 대조 평가 C-23)과 같은 상태가 된다. 11월에 알림이 붙을 때 함께 추가한다.

**한계 인지**: A는 화면을 보고 있을 때만 의미가 있다. 폰을 내려놓으면 알려주지 않으므로, 실사용 가치의 상당 부분은 B에서 나온다. 9월 일정이 밀리면 A는 뒤로 미뤄도 다른 결정에 영향을 주지 않는 항목이다.

## 4. 운동 시간 기록

### 4.1 방식 선택 — 세트 시각 기반 자동 산출

세트 저장 시각(`recorded_at`)을 이용해 운동 시간을 자동으로 산출한다.

**근거**
- 명시적 시작/종료 버튼 방식은 사용자가 종료를 누르지 않으면 데이터가 통째로 유실되거나 비정상적으로 길어진다. 운동 중에는 버튼 조작을 잊기 쉽다.
- 총 시간을 사용자가 직접 입력하는 방식은 추가 입력 부담이 생기고 값이 부정확하다.
- 자동 산출은 추가 조작이 전혀 없으며, 세트 기록이라는 이미 존재하는 행위에서 부수적으로 얻어진다.
- 이 값은 그룹 활동 공유의 표시용이므로(분 단위 정밀도면 충분) 자동 산출의 오차가 허용된다.

### 4.2 산출 규칙

```
duration_sec = Σ(연속한 두 세트의 간격, 단 15분을 초과하면 15분으로 캡)
             + 90초 (마지막 세트 수행 시간 보정)

상한: 세션당 4시간
```

**보정 규칙의 이유**
- **간격 캡**: 앱을 닫고 나갔다가 몇 시간 뒤 마지막 세트를 입력하면 시간이 비정상적으로 부풀려진다. 이 값은 그룹에 공개되므로 이상치 방어가 필요하다. 15분은 일반적인 세트 간 휴식(1~5분)보다 충분히 크되, 이탈로 볼 만한 수준으로 설정하였다.
- **마지막 세트 보정**: 첫 세트~마지막 세트 시각 차이만 쓰면 마지막 세트의 수행 시간이 누락된다.
- **세션 상한**: 캡을 통과한 값들이 누적되는 극단적 경우에 대한 최종 방어선이다.

### 4.3 사후 입력(BACKFILL) 세션 처리

과거 기록을 나중에 몰아서 입력한 세션은 `recorded_at`이 실제 운동 시각과 무관하다. 따라서

- `source = BACKFILL`인 세션은 `duration_sec`을 산출하지 않고 NULL로 둔다.
- 그룹 활동 공유의 총 운동 시간 집계에서 제외한다. 단, 주간 운동 **횟수** 집계에는 포함한다(운동을 한 것은 사실이므로).
- 사용자가 시간을 직접 입력하면 `duration_override_sec`으로 저장하고 집계에 포함한다.

### 4.4 수동 보정

`duration_override_sec` 컬럼을 두고, 값이 존재하면 자동 산출값보다 우선한다. 초기 구현에서는 보정 UI를 만들지 않더라도 **컬럼은 미리 확보**한다. 실사용자 배포 후 시간이 부정확하다는 피드백이 나올 가능성이 있으며, 그때 스키마 변경 없이 화면만 추가할 수 있다.

## 5. 기록 수정 · 누락 처리

### 5.1 세션 상태 — DRAFT / DONE

운동 중 앱을 닫는 상황이 일상적이므로, 완료되지 않은 세션을 유지한다.

- 첫 세트 저장 시 세션이 `DRAFT`로 생성된다.
- 사용자가 종료하면 `DONE`으로 전환한다.
- `DRAFT` 상태에서 앱에 재진입하면 "이어서 기록 / 종료" 중 선택하게 한다.
- 자정이 지나도록 `DRAFT`인 세션은 자동으로 `DONE` 처리한다(마지막 세트 시각 기준).
- **분석 집계는 `DONE` 세션만 대상으로 한다.** 진행 중인 세션이 판정에 섞이면 오늘의 루틴 추천이 요동친다.

### 5.2 과거 기록 입력 (BACKFILL)

날짜를 선택해 과거 세션을 생성할 수 있게 한다.

**근거**: 기록 누락은 분석 관점에서 곧 "볼륨 부족"으로 오판된다. 실제로는 운동했으나 기록하지 못한 경우를 보정할 수단이 없으면, 판정 정확도가 사용자의 기록 성실성에 전적으로 좌우된다. 사후 입력을 막는 것이 오히려 데이터 품질을 떨어뜨린다.

### 5.3 수정 · 삭제와 재집계

- 세트·세션의 수정과 삭제를 허용한다.
- **분석은 온디맨드 집계로 구현한다.** 판정 시점에 원본 기록을 조회해 계산하므로, 수정·삭제가 자동으로 반영되고 별도의 재계산 로직이 필요 없다.
- 최근 4주 기록은 개인당 수백~수천 행 규모이므로 집계 성능에 문제가 없다. 통계 화면이 느려지는 경우에 한해 일별 집계 테이블 도입을 검토한다(현 시점 보류).

### 5.4 뱃지와의 관계

**이미 지급된 뱃지는 기록이 수정·삭제되어도 회수하지 않는다.**

**근거**: 뱃지는 달성 순간의 기록이라는 성격이 강하고, 회수 로직은 "어느 시점의 어떤 기록이 그 뱃지의 근거였는가"를 추적해야 하므로 구현 비용이 크다. 얻는 것에 비해 비용이 커서 회수하지 않는 쪽을 택한다. 미리 정하지 않으면 구현 중 애매해지는 지점이므로 명시해 둔다.

### 5.5 기록이 희박한 시기의 신뢰도 표시

계획서 4.3은 "기록이 4주에 미치지 못해도 누적 기간 기준으로 환산해 판정하되, 기록이 적은 시기에는 그 사실을 안내한다"고 정하였다. 이를 구체화한다.

- 최근 4주의 `DONE` 세션 수가 임계(예: 6회) 미만이면 분석 결과에 "기록이 적어 판정 신뢰도가 낮다"는 표시를 함께 제공한다.
- 임계값 자체는 실사용 데이터를 본 뒤 조정할 수 있도록 설정값으로 둔다.

## 6. 루틴 수행률 측정

계획서 7장의 실사용자 검증 항목 "추천 루틴 실제 수행률(사용 로그 기반 자동 측정)"은 본 구조에서 별도 로깅 없이 산출된다.

```
수행률 = 해당 세션에 실제 저장된 세트 수
       ÷ 연결된 루틴(routine_items)이 계획한 세트 수
```

- 세션의 `routine_id`가 루틴과의 연결을 제공한다.
- 3.3에 따라 체크한 세트만 저장되므로, 저장된 세트 수가 곧 실제 수행량이다.
- 루틴 후보정(기능명세 2.4)으로 운동을 교체한 경우, 분모는 후보정 **이후**의 `routine_items` 기준으로 한다. 사용자가 조정한 루틴이 그 사용자에게 실제로 제시된 계획이기 때문이다.

## 7. 제외 사항

| 항목 | 결정 | 사유 |
|---|---|---|
| 좌우 분리 기록 | 제외 | 「운동 분석 로직 설계서」 4.1에서 이미 측정 불가로 제외. 입력 부담만 두 배가 된다 |
| 드롭세트 · 슈퍼세트 구분 | 제외 | 분석 로직에서 사용하는 곳이 없고, 구분해도 세트 수 집계 결과가 달라지지 않는다 |
| RPE(운동자각도) 입력 | 제외 | 「운동 분석 로직 설계서」 1.3에서 추정 1RM 방식을 채택하며 이미 배제. 매 세트 주관적 입력은 사용성을 크게 해친다 |
| 오프라인 기록 보존 | 제외 (**온라인 전용**) | 아래 7.1 |

> **휴식 시간 타이머는 이 표에서 제외 해제되었다.** 초판은 "분석에 사용되지 않는다"를 근거로 제외했으나, 타이머는 데이터 장치가 아니라 화면 보조 장치여서 그 문장이 제외 근거가 되지 못한다. 서버 계약 변경이 0이고 화면 설계가 목업에 이미 있어 범위 안으로 들였다. 표시는 9월, 알림은 11월이며 상세는 **3.7**에 있다.

### 7.1 오프라인 기록 보존을 제외하는 근거

세트는 완료 체크 시점에 서버로 전송되며(3.3), **네트워크가 없으면 저장되지 않는다.** 실패한 입력을 로컬에 쌓아두었다가 연결 후 재전송하는 장치(오프라인 쓰기 큐)는 두지 않는다.

**근거**

- **웹앱의 통상적인 기대치와 맞는다.** 상용 헬스 기록 앱 몇 종을 데이터를 끈 상태로 실행해 확인한 결과, "동기화가 실패했습니다" 안내와 함께 기록이 로딩되지 않았다. 사용자는 네트워크 없이 기록 앱이 온전히 동작할 것을 전제하지 않는다.
- **실패가 조용하지 않다.** 저장이 안 되면 화면에서 즉시 드러난다. 잘못된 값이 조용히 저장되는 종류의 문제(LOG-02·LOG-05가 막은 것들)와 성격이 다르다.
- **작품의 논지와 무관하다.** 이 작품이 주장하는 것은 기록에서 약점을 판정하고 근거 있는 루틴을 추천하는 것이며, 동기화 인프라는 여기에 기여하지 않는다. 「기능명세서」 4장의 범위 원칙("미완성 다수 기능보다 완성된 핵심 기능이 우선")을 적용한 판단이다.
- **노출 구간이 좁다.** 신호가 있으면 세트는 체크 즉시 저장되므로, 이후 앱이 종료되거나 새로고침되어도 잃는 것이 없다. 손실은 *오프라인* **이면서** *새로고침·앱 종료*가 겹칠 때만 발생한다. 신호가 잠시 불안정한 정도(타임아웃 후 재시도)는 세트 저장의 멱등 키(API 명세서 6.4 `clientSetId`)가 중복 없이 처리한다.

**한계 인지**

- 그 좁은 구간에 걸리면 손실 단위가 **세션 하나 전체**다. 오프라인 상태로 여러 세트를 기록한 뒤 앱이 정리되면 그때까지의 입력이 사라진다.
- 미완료 입력을 `localStorage`에 남겨 최악의 손실만 막는 방안(자동 재전송 없이 사용자가 "다시 저장"을 누르는 형태)이 있다. UC-02-01 예외 흐름 6a의 "입력값을 화면에 유지"를 메모리 대신 로컬 저장소로 바꾸는 정도이며, 화면 구현 시 여유가 있으면 추가한다.
- 완전한 오프라인 기록(네트워크 없이 세션 시작까지)은 세션 임시 ID와 서버 ID의 매핑 계층이 필요하다. 실사용자 피드백에서 요구가 확인되면 그때 판단한다.

## 9. 한계 인지

- **워밍업 표시는 사용자에게 의존한다.** 표시하지 않으면 볼륨이 과대 집계되며 앱이 판별할 수 없다.
- **운동 시간은 추정값이다.** 세트 사이에 실제로 무엇을 했는지 알 수 없으므로, 보정 규칙으로 이상치만 막는 수준이다. 그룹 공유의 참고 지표로만 사용한다.
- **사후 입력 기록의 정확도는 사용자의 기억에 좌우된다.** 이를 막으면 누락이 발생하므로, 정확도보다 누락 방지를 우선한 선택이다.
- **분석 결과의 품질은 결국 기록의 성실성에 비례한다.** 본 설계는 입력 부담을 낮춰 성실한 기록을 유도할 뿐, 기록하지 않은 운동을 복원할 수는 없다.
