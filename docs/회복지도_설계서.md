## 1. 목적

- 어느 부위가 아직 회복 중인지 한눈에 보여 준다. 오늘 운동할 부위를 고를 때 근거가 된다.
- **오늘의 루틴과 같은 판정을 쓴다.** 루틴은 오늘 포함 2일 안에 한 부위와 그 부위의 묶음을 뺀다(`app.routine.recovery-days`). 지도에서 "회복됨"인데 루틴이 그 부위를 빼면 두 화면이 서로 다른 말을 한다 — 그래서 회복 중인지도, 오늘 루틴에서 빠지는지도 루틴이 쓰는 함수로 정한다(3장).
- 통계 서브탭(종목별 추정 1RM 추이)은 종목 상세 화면에도 같은 패널이 있어서 빼도 잃는 기능이 없다.

## 2. 결정

| 항목 | 결정 | 이유 |
|---|---|---|
| 기준 | **날짜 + 세트 수**. 무게는 쓰지 않는다 | 무게×횟수는 부위끼리 비교가 안 된다. 스쿼트 100kg×10회는 1,000, 사이드 레터럴 8kg×15회는 120이라 하체만 늘 빨갛게 나온다. 세트 수는 분석·루틴이 이미 쓰는 단위다 |
| 시간 단위 | **날짜**(`performed_on`) | 지난 기록을 나중에 입력하면 저장 시각이 실제 운동 시각과 다르다. 분석·루틴도 날짜로 센다 |
| 회복 중 | 오늘 포함 `recovery-days`(2)일 안에 한 부위 | 루틴의 회복 제외와 **같은 함수**를 쓴다(`RecoveryEvaluation.recovering`) |
| 루틴에서 빠짐 | 회복 중인 부위 + 그 부위와 **같은 묶음**의 부위. 응답에 이유와 함께 싣는다 | 루틴이 묶음을 통째로 빼므로, 부위 하나의 회복 여부만으로는 "오늘 루틴에서 빠지는지"를 말할 수 없다. 루틴과 **같은 함수**를 쓴다(`RoutineExclusion.of`) |
| 많이 함 | 회복 중 기간의 본세트 합이 `per-muscle-max-sets`(6) 이상 | 루틴이 한 부위에 한 번에 주는 최대치를 채웠으면 많이 한 것으로 본다 |
| 이름 | "회복 상태", 서브탭 이름 "회복" | 피로도는 잰 값이 아니라 기록으로 짐작한 값이다. 근거를 보여 주는 앱 성격에 맞게 단정하지 않는 이름을 쓴다 |
| 색 | 빨강 → 주황 → 노랑 → 기본 회색, 범례를 붙인다. 밝기도 같은 순서로 올라간다 | 빨강→초록은 색약 사용자가 구분하기 어렵다. 밝기가 차례로 달라지면 색을 못 가려도 진한 쪽이 더 지친 쪽으로 읽힌다 |
| 부위 | 앱의 11개(판정 9 + 표시 전용 종아리·전완). 종목의 **주동근만** 칠한다 | 분석과 같은 단위. 보조근은 종목 데이터에 없다 — 보강은 다음 과제(8장) |
| 그림 | `react-muscle-highlighter` 1.2.0(MIT)의 남성 앞·뒤 SVG 경로를 복사해 자체 컴포넌트로 그린다 | 곡선 경로라 품질이 좋고, 의존성으로 넣지 않으면 색·터치·유리 테마를 직접 다룰 수 있다. 라이선스 문구를 함께 둔다 |
| 2D / 3D | 2D 앞·뒤 두 장 | 뒤쪽 근육을 돌리지 않고 본다. 계산·API는 3D로 바꿔도 그대로 쓴다 |

## 3. 계산

부위마다 최근 `app.analysis.weeks`(4)주 안의 마지막 운동일과, 회복 중 기간(오늘 포함 R일, R = `recovery-days`)의 본세트 수를 센다. 세트 조건은 분석과 같다 — 워밍업 제외, `performed_on` 기준, 오늘 체크한 세트 포함.

`daysSince` = 오늘 − 마지막 운동일

| 상태 | 조건 | 색 | 화면 표기 |
|---|---|---|---|
| `HIGH` | `daysSince < R` 이고 최근 세트 ≥ 6 | 빨강 | 회복 중 · 많이 함 |
| `MEDIUM` | `daysSince < R` 이고 최근 세트 < 6 | 주황 | 회복 중 |
| `LOW` | `daysSince = R` | 노랑 | 거의 회복 |
| `RECOVERED` | `daysSince > R`, 또는 4주 안에 기록 없음 | 회색 | 회복됨 |

- R = 0이면 회복 중인 부위가 없다(전부 `RECOVERED`). 루틴도 그때는 회복 제외를 하지 않는다.
- 예시(R = 2, 오늘 11/10): 어제 가슴 7세트 → `HIGH`. 오늘 이두 3세트 → `MEDIUM`. 11/8에 하체 → `LOW`. 11/6에 등 → `RECOVERED`.
- 어깨는 분석처럼 `delt_region`으로 앞(전·측면)·뒤(후면)를 가른다. `delt_region`이 없는 어깨 종목은 세지 않는다(분석 8.1과 같다).

**오늘 루틴에서 빠지는지** (`routine.domain.RoutineExclusion.of` — 루틴의 `SlotPlanner`와 회복 API가 같이 부른다)

| 부위 | 빠지는지 | 이유 |
|---|---|---|
| 회복 중인 판정 부위 | 빠진다 | `SELF_RECOVERING` |
| 회복 중인 부위와 같은 묶음(밀기: 가슴·어깨 전·측면·삼두 / 당기기: 등·어깨 후면·이두 / 하체: 앞허벅지·뒤허벅지·둔근)의 다른 부위 | 회복됐어도, 기록이 없어도 빠진다 | `BUNDLE_RECOVERING` + 그 묶음에서 회복 중인 부위 |
| 코어 | 코어가 회복 중일 때만. 묶음이 없어 다른 부위 때문에 빠지지 않고, 다른 부위를 빼지도 않는다 | `SELF_RECOVERING` |
| 종아리·전완 | 빠진다고 하지 않는다(늘 `false`) — 루틴이 원래 고르지 않는 부위다. 다른 부위를 빼지도 않는다 | — |

- 본인도 회복 중이고 묶음의 다른 부위도 회복 중이면 이유는 `SELF_RECOVERING`이다.
- R = 0이면 아무것도 빠지지 않는다.
- 예시(R = 2): 어제 가슴만 했다 → 가슴 `SELF_RECOVERING`, 사흘 전에 한 삼두와 기록이 없는 어깨 전·측면은 `BUNDLE_RECOVERING`(가슴). 등·하체·코어는 빠지지 않는다.
- "빠지지 않는다"가 "오늘 루틴에 들어간다"는 뜻은 아니다. 루틴은 남은 묶음 중 하나만 고른다(루틴 설계서 2.4).

## 4. API

`GET /api/v1/analysis/recovery` — 인증 필요, 파라미터 없음(오늘 기준).

```json
{
  "date": "2026-11-10",
  "recoveryDays": 2,
  "heavySets": 6,
  "muscles": [
    { "key": "CHEST", "label": "가슴", "judged": true,
      "state": "HIGH", "stateLabel": "회복 중 · 많이 함",
      "lastTrainedOn": "2026-11-09", "daysSince": 1, "recentSets": 7,
      "routineExcluded": true, "routineExclusionReason": "SELF_RECOVERING", "routineExcludedBy": [] },
    { "key": "TRICEPS", "label": "삼두", "judged": true,
      "state": "RECOVERED", "stateLabel": "회복됨",
      "lastTrainedOn": "2026-11-07", "daysSince": 3, "recentSets": 0,
      "routineExcluded": true, "routineExclusionReason": "BUNDLE_RECOVERING", "routineExcludedBy": ["CHEST"] }
  ]
}
```

| 필드 | 설명 |
|---|---|
| `muscles` | 11개 부위가 `MuscleGroup` 순서대로 **항상 모두** 온다. 기록이 없어도 빠지지 않는다 |
| `judged` | 부족 판정 대상인지. 종아리·전완은 `false`(분석과 같다) |
| `lastTrainedOn` · `daysSince` | 최근 4주 안에 기록이 없으면 둘 다 `null` |
| `recentSets` | 오늘 포함 `recoveryDays`일 동안의 본세트 수 |
| `recoveryDays` · `heavySets` | 화면이 범례·상세 문구("2일 안에 6세트 이상")를 만들 때 쓴다 |
| `routineExcluded` | 회복 때문에 오늘 루틴에서 빠지는지(3장). 종아리·전완은 늘 `false` |
| `routineExclusionReason` | `SELF_RECOVERING` 이 부위가 회복 중 / `BUNDLE_RECOVERING` 같은 묶음의 다른 부위가 회복 중. 안 빠지면 `null` |
| `routineExcludedBy` | `BUNDLE_RECOVERING`일 때 같은 묶음에서 회복 중인 부위의 `key`(`MuscleGroup` 순서). 그 밖에는 빈 배열 |

## 5. 화면

- 분석 탭 서브탭: **약점 | 회복**. 주소는 `/analysis?view=recovery`이고, 예전 통계 주소 `?view=stats`로 들어오면 회복을 연다.
- 위에서부터 **그림 판(앞·뒤 + 범례) → 고른 부위 카드 → 색이 칠해진 부위 이름 → 판정 기준 한 줄** 순서다. 부위 카드를 그림 바로 아래에 둔 것은, 이름 목록 아래에 두면 휴대폰 첫 화면에서 카드가 가려져 그림을 눌러도 바뀐 게 안 보이기 때문이다. 그래도 가려지는 작은 화면에서는 그림을 누르면 카드가 보이는 데까지 화면을 올린다.
- 앞·뒤 그림을 나란히 놓는다. 폭 360px에서 한 장이 140px쯤이다. 원본 칸(724×1448)의 빈 가장자리는 잘라 내 몸을 크게 그린다. 아래에 4단계 범례.
- 부위를 누르면 카드에 부위 이름, 상태, 마지막 운동(날짜·며칠 전), 최근 세트, 한 줄 설명을 보여 준다. 처음 열면 가장 지친 부위가 골라져 있고, 색이 칠해진 부위가 없으면 "그림에서 부위를 누르면…" 안내를 둔다.

  | 부위 | 한 줄 설명 |
  |---|---|
  | 회복 중(`HIGH`·`MEDIUM`)인 판정 부위 — `SELF_RECOVERING` | 오늘 루틴에서 빠져요 |
  | 회복됐지만 묶음 때문에 빠지는 부위 — `BUNDLE_RECOVERING` | 가슴이 회복 중이라 오늘 루틴에서 같이 빠져요 (이유가 둘이면 "어깨 전·측면, 삼두가 …") |
  | 거의 회복(`LOW`)인데 묶음 때문에 빠지는 부위 | 회복 기간은 끝났지만 가슴이 회복 중이라 오늘 루틴에서 같이 빠져요 |
  | 회복 중인 종아리·전완 | 루틴이 따로 고르지 않는 부위예요 — 루틴이 원래 고르지 않으니 "빠진다"고 하면 틀린 말이다 |
  | 거의 회복(`LOW`)이고 빠지지 않는 부위 | 회복 기간이 막 끝났어요 |
  | 회복됨이고 빠지지 않는 부위 | 없음. "오늘 루틴에 들어가요"라고 적지 않는다 — 회복 때문에 빠지지 않는다는 것까지만 알고, 루틴이 오늘 어느 묶음을 고를지는 이 화면이 모른다 |

  빠지는지와 이유는 응답(`routineExclusionReason`·`routineExcludedBy`)을 그대로 적는다. 화면은 묶음이 무엇인지 모른다. 맨 아래 판정 기준에도 "루틴은 회복 중인 부위와 같은 날 하는 부위도 함께 빼요"를 한 줄 둔다.

- 그림만으로는 화면 읽기 프로그램이 알 수 없으므로 색이 칠해진 부위를 글로도 나열한다 — "회복 중" 줄과 "거의 회복" 줄. **이름은 누를 수 있는 단추다.** 그림의 팔 부위는 폭 360px에서 10×20px쯤이라 손가락으로 정확히 누르기 어려워서, 이름을 눌러도 같은 부위가 골라지게 했다. 회복 중인 부위가 없으면 "회복 중인 부위가 없어요".
- 4주 안에 기록이 없으면 그림은 전부 회색이고(누를 수 없다) "운동을 기록하면 회복 상태가 보여요"와 기록하기 단추를 띄운다.
- 앱이 세지 않는 곳(머리·목·손·발·무릎·정강이 앞)은 실루엣 기본색으로 칠하고 누를 수 없다.
- 색은 토큰(`--recovery-high`·`-medium`·`-low`·`-none`)으로 두고 그림·범례·이름·카드가 같이 쓴다. 네 색은 어느 둘을 맞대도 색각이상(적·녹) 모의에서 ΔE 15 이상이다. 노랑과 회색은 흰 바탕 대비가 낮아(1.4:1) 색만으로 읽히지 않으므로 범례와 이름 목록을 늘 같이 둔다.
- 그림 경로(약 60KB)는 회복 서브탭을 열 때 따로 받는다(`body/BodyMap` 청크). 앱 본체에 실으면 모든 화면의 첫 로딩이 그만큼 무거워진다. 경로와 라이선스 원문은 `frontend/src/screens/analysis/body/`에 있다.
- **배포본의 라이선스 고지.** 빌드하면 코드의 주석이 지워져서(`/*!`·`@license`도 Vite 8에서 지워진다) 배포된 파일에는 고지가 남지 않는다. 그래서 같은 원문을 `frontend/public/licenses/react-muscle-highlighter.txt`로 같이 내보내고(`/licenses/react-muscle-highlighter.txt`), 설정 › **오픈소스 라이선스**(`/settings/licenses`)에서 연다. 그 화면에는 같은 처지인 것들도 함께 적었다 — 종목 동작 그림의 출처(everkinetic CC BY-SA 4.0, free-exercise-db), 앱에 들어간 라이브러리(빌드가 `licenses/npm-packages.txt`로 모은다 — `vite.config.ts`의 `build.license`), 글꼴(Pretendard).

## 6. 완료 기준

**API (PR 1)**
- 순수 함수 단위 테스트: `daysSince` 0·1·2·3, 기록 없음, 6세트 경계, R = 0
- 루틴의 회복 제외(`SlotPlanner`)가 같은 함수를 부른다. 기존 루틴 테스트가 그대로 통과한다
- API 테스트: 11개 부위 순서, 상태 판정, 워밍업 제외, 다른 사용자 기록 제외, 기록 없음
- API 명세(3장 목록, 8.6) 반영, 백엔드 전체 테스트 통과

**화면 (PR 2)**
- 앞·뒤 그림, 4단계 색, 범례, 부위 상세, 회복 중 부위 글 목록, 기록 없음 상태
- 폭 360·390·430px 캡처로 확인(유리 테마)

## 8. 다음 과제 (이번에 하지 않음)

- 보조근 반영 — 종목 데이터에 보조근을 더해야 한다(원본 free-exercise-db에 `secondaryMuscles`가 있다). 벤치프레스가 삼두·앞어깨도 칠하게 된다
- 3D 모형 — 근육이 나뉜 모형 파일·라이선스·용량 문제가 먼저다
- 여성 그림 선택 — 같은 패키지에 경로가 있다. 프로필에 성별이 없어 설정이 필요하다
- 무게·강도 반영 — 같은 세트라도 무거운 날을 더 지친 것으로 보려면 사용자별 기준(추정 1RM 대비)이 필요하다

- 지도에 "루틴에서 같이 빠지는 부위"를 한눈에 — 지금은 회색 부위를 눌러 카드를 봐야 묶음 때문에 빠지는 것을 안다. 이름 목록에 한 줄을 더하거나 그림에 표시를 둘 수 있다
